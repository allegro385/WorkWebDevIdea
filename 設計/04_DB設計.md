## 1. DB基本方針

- SQL Server上に営業支援システム専用DBを用意する。
- ポータルと各ツールは、営業支援システム共通のアプリケーション用DBユーザーで接続する。
- 営業支援システムに不要な他システムのDBへ直接アクセスしない。
- DBユーザーには必要最小限の権限のみ付与する。
- 接続文字列や認証情報は各アプリケーションの設定からDependency Injection等で共通DLLへ渡し、Common.dll内へ埋め込まない。
- ポータルが所有・管理するテーブルには`portal`スキーマを使用する。本資料で定義するユーザー管理、ユーザー設定、お気に入り、ツール管理、お知らせ、FAQ、問い合わせ、ログ、コードマスタおよびシステム設定の各テーブルを対象とする。
- 各ツール固有の業務テーブルおよび上記以外のテーブルは`dbo`スキーマを使用し、ツール単位のスキーマは設けない。
- `portal`スキーマはテーブルを整理・識別しやすくするために使用し、DB権限の分離には使用しない。ポータルと各ツールは共通のアプリケーション用DBユーザーで必要なテーブルへアクセスする。
- 本資料では可読性のためテーブル名のスキーマ表記を省略する場合があるが、実際のDDLおよびSQLでは対象に応じて`portal`または`dbo`を明示する。

## 2. 共通テーブルカラム

Identity管理テーブルを除くすべてのシステムテーブルに次の共通監査列を設ける。個別テーブルの項目一覧には、これらの共通監査列を記載しない。

| 項目 | 内容 |
| --- | --- |
| UpdateCount | 更新回数。登録時は0とし、更新ごとに加算する |
| CreatedAt | 作成日時 |
| CreatedBy | 作成時のDBユーザー |
| UpdatedAt | 更新日時 |
| UpdatedBy | 更新時のDBユーザー |

- 共通監査列はDEFAULT制約またはDBトリガー等によりDB側で自動設定する。
- 共通監査列とトリガーは共通のDDLテンプレートから作成し、テーブルごとに個別仕様を持たせない。
- トリガーの共通動作はテンプレートに対する共通テストで確認する。
- アプリケーションの内部ユーザーIDをDBセッションへ受け渡して監査列へ設定する仕組みは設けない。
- アプリケーション上の送信者、担当者、修正担当者等、業務上必要なユーザー情報は各テーブルの業務項目として保持する。
- 日時の基準、DBユーザー名の取得方法およびトリガーの共通化方法は詳細設計で決定する。
- `AspNetUsers`、`AspNetUserClaims`、`AspNetUserLogins`および`AspNetUserTokens`はIdentity管理テーブルとし、共通監査列およびDBトリガーの対象外とする。

## 3. ユーザーデータ

- ユーザーごとにシステム内部で一意の内部ユーザーIDを付与する。
- 内部ユーザーIDは、メールアドレスや表示名が変更されても変更しない。
- ASP.NET Core IdentityのUserManagerを使用してユーザー情報と認証情報を登録・更新する。
- Identityのロール系テーブルは作成せず、権限はAspNetUsers.RoleCodeで管理する。
- Identity管理テーブルとして`AspNetUsers`、`AspNetUserClaims`、`AspNetUserLogins`および`AspNetUserTokens`の4テーブルを使用する。

### ユーザーテーブル（AspNetUsers）

| 項目 | 内容 |
| --- | --- |
| UserId | `uniqueidentifier`型の内部ユーザーID。IdentityのIdプロパティをこの物理列へ割り当てる |
| UserName | ログイン名。メールアドレスと同じ値を設定する |
| NormalizedUserName | Identityが使用する正規化済みログイン名 |
| Email | ログインおよび通知に使用するメールアドレス |
| NormalizedEmail | Identityが検索と重複確認に使用する正規化済みメールアドレス |
| EmailConfirmed | メールアドレス確認済みフラグ |
| PasswordHash | Identityが生成するパスワードハッシュ。初回設定前はNULL |
| SecurityStamp | 認証情報変更時に更新するセキュリティスタンプ |
| ConcurrencyStamp | Identityが同時更新検出に使用する値 |
| PhoneNumber | Identity標準の電話番号。初期機能では使用しない |
| PhoneNumberConfirmed | Identity標準の電話番号確認済みフラグ。初期機能では使用しない |
| TwoFactorEnabled | Identity標準の二要素認証フラグ。初期機能では使用しない |
| LockoutEnd | 一時ロックの終了日時。未ロックの場合はNULL |
| LockoutEnabled | ログイン失敗による自動ロックの対象か。初期値は有効 |
| AccessFailedCount | 連続ログイン失敗回数 |
| DisplayName | 画面表示用の氏名 |
| RoleCode | USERまたはADMIN。表示名称はCodeMasterのUSER_ROLEから取得する |
| IsActive | ユーザーの有効・無効 |
| LastAccessAt | 最終利用日時。未利用の場合はNULL |

- ApplicationUserは`IdentityUser<Guid>`を継承し、IdプロパティをAspNetUsers.UserIdへマッピングする。
- UserIdには`DEFAULT NEWSEQUENTIALID()`を設定し、UserManagerによる登録時にSQL Server側で生成する。
- UserNameとEmailには同じメールアドレスを設定する。
- NormalizedUserNameおよびNormalizedEmailはUserManagerにより設定し、それぞれに一意制約を設ける。
- 初回パスワード設定が完了するまでPasswordHashはNULL、EmailConfirmedは無効とする。
- 初回パスワード設定完了時にPasswordHashを保存し、EmailConfirmedを有効とする。
- RoleCodeはUSERまたはADMINだけを許可する。
- IsActiveの初期値は有効とする。
- 初期段階では一般ユーザーとシステム管理者の二種類とし、独立した権限マスタおよびIdentityのロール系テーブルは設けない。表示名称だけをCodeMasterで共通管理する。
- LastAccessAtの更新タイミングは[ログ・最終利用日時の仕様](02_画面・機能設計.md#logs-usage)に従う。

### ユーザークレームテーブル（AspNetUserClaims）

| 項目 | 内容 |
| --- | --- |
| Id | クレームを識別するID |
| UserId | AspNetUsers.UserIdへの外部キー |
| ClaimType | クレームの種類 |
| ClaimValue | クレームの値 |

- Identity標準構成として作成する。
- 初期段階の権限はAspNetUsers.RoleCodeで管理するため、個別権限の保存には使用しない。

### 外部ログインテーブル（AspNetUserLogins）

| 項目 | 内容 |
| --- | --- |
| LoginProvider | 外部ログインプロバイダー名 |
| ProviderKey | 外部プロバイダー側の識別子 |
| ProviderDisplayName | 外部ログインの表示名 |
| UserId | AspNetUsers.UserIdへの外部キー |

- LoginProviderとProviderKeyを複合主キーとする。
- 初期段階では外部認証を使用しないため、レコードは登録しない。

### ユーザートークンテーブル（AspNetUserTokens）

| 項目 | 内容 |
| --- | --- |
| UserId | AspNetUsers.UserIdへの外部キー |
| LoginProvider | トークンのプロバイダー名 |
| Name | トークン名 |
| Value | トークン値 |

- UserId、LoginProviderおよびNameを複合主キーとする。
- Identity標準のトークン保存領域として作成する。

### ユーザー設定テーブル（UserPreferences）

| 項目 | 内容 |
| --- | --- |
| UserId | 内部ユーザーID。主キー兼AspNetUsers.UserIdへの外部キー |
| SystemNoticeMailEnabled | システムお知らせメールの受信要否 |
| FavoriteToolNoticeMailEnabled | お気に入りツールお知らせメールの受信要否 |

- AspNetUsersと一対一で保持する。
- 通知設定の初期値はいずれも有効とする。

### お気に入りテーブル（UserToolFavorites）

| 項目 | 内容 |
| --- | --- |
| UserId | 内部ユーザーID |
| ToolId | ツールID |

- UserIdとToolIdの組み合わせを複合主キーとする。
- 同一ユーザーが同一ツールを重複登録できないようにする。
- AspNetUsersおよびToolsへの外部キーを設定する。
- ツールが非公開となった場合もレコードを削除しない。

- 初期ユーザーのTSV項目・検証・登録処理は[一括登録仕様](02_画面・機能設計.md#bulk-registration)を参照する。
- ユーザー無効化・権限変更時の動作とSecurityStampの更新は[認証構成](03_システム構成・開発標準.md#authentication)を参照する。

## 4. ツール管理データ

### ツール分類マスタ（ToolCategories）

| 項目 | 内容 |
| --- | --- |
| CategoryId | 分類を識別するID |
| CategoryName | 一覧に表示する大分類名 |
| SortOrder | 分類の表示順 |

### ツールマスタ（Tools）

| 項目 | 内容 |
| --- | --- |
| ToolId | ツールを識別するID |
| CategoryId | 所属する分類ID |
| ToolName | ツール名 |
| ToolSummary | ツール概要 |
| Remarks | ツール詳細に表示する利用者向け備考 |
| OwnerUserId | 担当者となるシステム管理者の内部ユーザーID |
| ToolType | DESKTOPまたはWEB。CodeMasterのTOOL_TYPEに対応するコード値 |
| Status | CodeMasterのTOOL_STATUSに対応するコード値。Public公開、Private公開、非公開 |
| SortOrder | 分類内の表示順 |

- バージョンおよび更新日はツールマスタへ重複して保持せず、最新フラグが設定されたツール履歴から取得する。
- 新規ツールのStatusの初期値は非公開とする。登録手順は[マスタ更新方針](05_導入・運用.md#master-data)を参照する。
- OwnerUserIdには、有効かつRoleCodeがADMINのユーザーだけを設定できるようにする。

### ツール履歴（ToolVersionHistories）

| 項目 | 内容 |
| --- | --- |
| ToolHistoryId | ツール履歴を識別するID |
| ToolId | 対象ツールID |
| Version | バージョン |
| ModifiedByUserId | 修正担当者の内部ユーザーID |
| ChangeDescription | 更新内容 |
| ReleasedAt | バージョン更新日 |
| IsCurrent | 一覧・概要へ表示する最新履歴かを示すフラグ |

- 一つのツールに対して、最新フラグを設定できる履歴は一件のみとする。
- 最新フラグの更新はトランザクション内で行い、最新履歴が複数発生しないようDB制約も設ける。
- バージョン文字列や更新日の大小だけでは最新を判定しない。
- 履歴は更新せず追加を基本とし、過去のバージョン更新情報として詳細画面へ表示する。
- ToolIdとVersionの組み合わせに一意制約を設定する。

### ツール提供内容（ToolResources）

| 項目 | 内容 |
| --- | --- |
| ToolResourceId | 提供内容を識別するID |
| ToolId | 対象ツールID |
| ResourceType | Webページ、デスクトップアプリ、マニュアル、データリンク等の区分 |
| DisplayName | 詳細画面に表示する名称 |
| ResourceLocation | URLまたは管理ファイルを参照する情報 |
| SortOrder | 詳細画面内の表示順 |
| IsEnabled | 提供内容の有効・無効 |

- ToolTypeがWEBの場合は、デスクトップアプリケーションの提供内容を登録・有効化できないようにする。
- ファイルの実体管理に必要なファイル名、保存先等の詳細項目は詳細設計で決定する。
- 配布ファイルとマニュアルは最新版だけを参照し、旧版ファイルの世代を管理するカラムおよびテーブルは設けない。
- ファイル格納先の総容量および使用量を管理するカラムおよびテーブルは設けない。

- ツール状態の利用可否は[共通利用制御](02_画面・機能設計.md#access-control)、バージョン登録時の操作は[ツール管理画面](02_画面・機能設計.md#tool-admin)を参照する。

## 5. お知らせデータ

### お知らせテーブル（Notices）

| 項目 | 内容 |
| --- | --- |
| NoticeId | お知らせID |
| NoticeType | SYSTEMまたはTOOL |
| ToolId | ツールお知らせの場合の対象ツールID。システムお知らせの場合はNULL |
| Title | タイトル |
| Content | お知らせ内容 |
| IsPublished | 公開フラグ。初期値は非公開 |
| MailSentAt | メール送信日時。未送信の場合はNULL |

- システムお知らせとツールお知らせを一つのNoticesテーブルで管理する。
- NoticeTypeがSYSTEMの場合はToolIdをNULL、TOOLの場合はToolIdを必須とするDB制約を設ける。
- お知らせを非公開にしてもレコードを削除しない。

- 公開範囲、通知対象、送信・再送時のMailSentAtの更新条件は[お知らせ共通仕様](02_画面・機能設計.md#notices)を参照する。

## 6. FAQデータ

### FAQカテゴリマスタ（FaqCategories）

| 項目 | 内容 |
| --- | --- |
| CategoryId | FAQカテゴリを識別するID |
| CategoryName | FAQ画面に表示するカテゴリ名 |
| SortOrder | カテゴリの表示順 |

### FAQテーブル（FaqItems）

| 項目 | 内容 |
| --- | --- |
| FaqId | FAQを識別するID |
| CategoryId | 所属するFAQカテゴリID |
| Question | 質問内容 |
| Answer | 回答内容 |
| SortOrder | カテゴリ内の表示順 |
| IsPublished | FAQを一般ユーザーへ表示するかを示すフラグ |

- 画面上は質問と回答を二段で表示するが、DB上は一つのFAQを一レコードとして保持する。
- 質問と回答を`QorA`で別レコードに分割しない。
- 同一カテゴリ内では、FAQのソート順が重複しないようにする。
- 利用マニュアルPDFのURLはDBで管理せず、利用マニュアル・FAQ画面にサイト内相対URLとして記載する。
- 登録・更新方法は[マスタ更新方針](05_導入・運用.md#master-data)、表示仕様は[利用マニュアル・FAQ画面](02_画面・機能設計.md#manual-faq)を参照する。

## 7. 問い合わせデータ

### 問い合わせテーブル（Inquiries）

| 項目 | 内容 |
| --- | --- |
| InquiryId | 主キー兼、画面とメールに表示する問い合わせID |
| CategoryCode | CodeMasterのINQUIRY_CATEGORYに対応するコード値。質問、要望、意見、不具合報告、その他 |
| TargetType | システム、ツール、その他 |
| ToolId | 対象がツールの場合のツールID。その他の場合はNULL |
| SubmittedByUserId | 問い合わせを送信した内部ユーザーID |
| Content | 問い合わせ内容 |
| Status | CodeMasterのINQUIRY_STATUSに対応するコード値。要対応、対応中、検討中、完了、対応不要。初期値は要対応 |
| AssigneeUserId | 担当者の内部ユーザーID。未割当を許可する |
| AdminNote | 管理者用備考 |

- 表示専用の問い合わせ番号や別の内部IDは設けず、InquiryIdを主キー兼問い合わせ番号として使用する。
- AssigneeUserIdには、有効かつRoleCodeがADMINのユーザーだけを設定できるようにする。
- 添付ファイルの内容、ファイル名および保存先はDBへ保持しない。
- 添付ファイル用テーブルは設けない。

- 初期担当者の設定、送信処理および管理操作は[問い合わせ管理](02_画面・機能設計.md#inquiry-admin)と[問い合わせ送信処理](02_画面・機能設計.md#inquiries)を参照する。

## 8. ログテーブル

| テーブル | 用途 |
| --- | --- |
| ToolUsageLogs | デスクトップツールのダウンロード要求、Webツール起動、Webツール計算実行 |
| UserAccessLogs | ログイン成功、ログイン失敗、アカウントロック、ログアウト、アクセス拒否等 |
| SystemErrorLogs | ポータル、共通API、各Webツールのシステムエラー |

- 内部ユーザーID、ツールID、発生日時、イベント種別、処理結果等を記録する。
- 必要に応じて相関IDを付与する。
- システムエラーログはSQL ServerのSystemErrorLogsテーブルに記録する。
- ファイルログやWindowsイベントログへの二重記録は行わない。
- DB接続障害等によってSystemErrorLogsへ書き込めない場合の代替ログは、費用対効果を考慮して初期実装には設けない。
- ツール別利用者数は、削除せず保持している全期間のToolUsageLogsをツール単位で集計し、重複しない内部ユーザー数を算出する。
- 初期段階では集計専用テーブルを設けず、ToolUsageLogsから都度集計する。
- UserAccessLogsおよびSystemErrorLogsは、保持期間による削除後に残っている全明細をTSV出力する。
- 全期間集計および全明細出力に必要なインデックスは、実データ件数を確認して設計する。

- 保持期間と定期削除の対象は[要件定義](01_要件定義.md#retention)に集約する。
- 記録方法は[共通ログ実装](03_システム構成・開発標準.md#logging)、集計・出力は[ログ管理](02_画面・機能設計.md#logs-usage)を参照する。

## 9. 汎用コードマスタ（CodeMaster）

小規模な選択肢の表示名称、並び順および表示色を、一つのコードマスタで共通管理する。

| 項目 | 内容 |
| --- | --- |
| CodeType | コード区分。例：TOOL_STATUS、SITE_STATUS |
| CodeValue | 区分内で一意のコード値 |
| CodeName | 画面に表示する名称。汎用的なValue列ではなく、用途が分かる名称とする |
| SortOrder | コード区分内の表示順 |
| ColorCode | バッジ背景色。varchar(7)、#RRGGBB形式。色が不要な場合はNULL |

- CodeTypeとCodeValueの組み合わせを複合主キーとする。
- コード値は原則として変更・再利用せず、名称や並び順の変更と区別する。
- ColorCodeには有効な#RRGGBB形式だけを許可し、任意のCSS文字列は保持しない。
- 表示名称と色から権限や動作を判定しない。状態・権限等のコード値はC#側でも定数等で定義し、対応する処理を実装する。
- コード行の追加だけで新しい状態遷移や権限が有効になる構成にはしない。
- ツール分類マスタ（ToolCategories）およびFAQカテゴリマスタ（FaqCategories）は、個別マスタを維持する。
- 参照先はCodeValue単独ではなくCodeTypeとの組み合わせで特定する。DB制約を含む参照整合性の具体方式は詳細設計で決定する。

### 共通管理するコード区分

| CodeType | 対象 | 利用箇所 |
| --- | --- | --- |
| TOOL_STATUS | Public公開、Private公開、非公開 | Tools.Status |
| SITE_STATUS | Public公開、Private公開 | SystemSettings.SiteStatusCode |
| TOOL_TYPE | デスクトップ、Web | Tools.ToolType |
| INQUIRY_CATEGORY | 質問、要望、意見、不具合報告、その他 | Inquiries.CategoryCode |
| INQUIRY_STATUS | 要対応、対応中、検討中、完了、対応不要 | Inquiries.Status |
| USER_ROLE | 一般ユーザー、システム管理者 | AspNetUsers.RoleCodeの表示名称 |

### 状態コード・表示色の初期設定案

| CodeType | CodeValue | CodeName | SortOrder | ColorCode |
| --- | --- | --- | --- | --- |
| TOOL_STATUS | PUBLIC | Public公開 | 10 | #2E7D32 |
| TOOL_STATUS | PRIVATE | Private公開 | 20 | #6A1B9A |
| TOOL_STATUS | HIDDEN | 非公開 | 30 | #616161 |
| SITE_STATUS | PUBLIC | Public公開 | 10 | #2E7D32 |

<a id="system-settings"></a>

## 10. システム設定（SystemSettings）

| 項目 | 内容 |
| --- | --- |
| SystemSettingId | システム設定を識別する固定ID |
| SiteStatusCode | CodeMasterのSITE_STATUSに対応する現在のサイト公開状態 |
| AccessRestrictionMessage | 入場制限時の案内文。未設定の場合は共通の既定メッセージを表示する |

- サイト全体で一レコードを保持し、ポータルと各Webツールから同じ設定を参照する。
- CodeMasterは状態の定義を保持し、現在どの状態であるかはSystemSettingsに保持する。
- SiteStatusCodeはPUBLICまたはPRIVATEのいずれかとし、初期構築時はPrivate公開（PRIVATE）で登録する。
- 案内文は未認証ユーザーにも表示されるため機密情報を含めず、プレーンテキストとして扱う。
- 設定ファイルで管理する本番・開発の環境区分とは別に扱い、サイトの公開状態を変更しても環境区分および帯色は変更しない。

- 画面からの更新は[サイト管理](02_画面・機能設計.md#site-admin)、運用は[サイト公開状態の変更](05_導入・運用.md#site-status-operation)を参照する。
