# 営業支援ポータル 要件定義

[資料一覧へ戻る](README.md)

システムの目的、対象範囲、利用者に提供する機能および品質上の条件を定義する。画面の詳細動作や実装手順は関連資料を参照する。

## 1. システム概要

### 1.1 目的

- 既存の営業支援用デスクトップツール群と、新たに開発するWebツールを一つのポータルへ集約する。
- 利用者がツールの実装方式を意識せず、同じサイトから必要なツールを利用できるようにする。
- 各ツールを独立したソリューションとして開発し、複数開発者による並行開発・保守を可能にする。
- 認証、ユーザー管理、ツール管理、お知らせ、通知、ログ、共通UI等はポータル側へ集約する。

### 1.2 想定利用規模

| 項目 | 想定 |
| --- | --- |
| 登録ユーザー数 | 約200名 |
| 同時利用ユーザー数 | 約5名 |
| 初期ツール数 | 約20ツール |
| ツール種別 | Webツール / デスクトップツール |

### 1.3 初期対象外

- ツール単位の利用者権限管理
- ツール一覧のキーワード検索
- 利用状況集計のシステム内グラフ表示
- ポータル管理画面からのWebアプリケーション本体の配備
- 配布ファイルおよびマニュアルの旧版保存・世代管理、ファイル格納先の総容量・使用量管理
- 問い合わせメールへの一時添付を除く、一般ユーザー向けファイルアップロードおよびファイルの恒久保存
- CI/CD
- ポータルおよび各ツールへのバックアップ機能実装
- 計算結果および帳票データの恒久保存
- 厳密なレスポンスタイムおよび可用性SLAの数値化

## 2. 機能要件

### 一般ユーザー向け機能

- メールアドレスとパスワードでログインし、ログアウトできる。
- メールの案内から初回パスワードを設定し、パスワードの変更・再設定ができる。
- ユーザーの有効状態、権限、サイト公開状態およびツール状態に応じて利用を制限する。
- サイト公開状態はPublic公開とPrivate公開の2種類とし、Private公開ではシステム管理者だけが入場できる。
- ツール状態はPublic公開、Private公開、非公開の3種類とし、Private公開ではシステム管理者だけが参照・利用でき、非公開では管理画面からの確認・編集だけを許可する。
- ポータルトップからツール一覧、サポートおよび権限に応じた管理機能へ移動できる。
- Webツールとデスクトップツールを区別せず、同じ一覧から探せる。
- ツールをお気に入りへ登録・解除し、自分のお気に入り一覧を利用できる。
- ツールの概要、備考、お知らせ、バージョン更新情報およびマニュアルを確認できる。
- 提供内容に応じてWebツールを使用し、デスクトップアプリケーションを取得できる。
- システムお知らせと、お気に入りツールのお知らせのメール受信要否を設定できる。
- ポータルの利用マニュアルとFAQを同じ画面で確認できる。
- 問い合わせ・ご意見を送信でき、必要に応じて許可されたファイルをメールに添付できる。

### システム管理者向け機能

- サイト公開状態と入場制限時の案内文を管理できる。
- ツールの基本情報、提供内容、バージョン、お知らせおよび状態を更新できる。
- デスクトップアプリケーションと、両種別のツールのマニュアルをアップロード・更新できる。
- システム・ツールのお知らせを登録・編集・公開し、明示的な操作でメール送信できる。
- ユーザーの追加、情報変更、権限変更、無効化、パスワード再設定案内およびロック解除ができる。
- ユーザーの最終利用日時を確認できる。
- 問い合わせを検索し、担当者・ステータス・備考を更新できる。
- ツール利用履歴を全保持期間で集計し、ツールごとの利用者数をTSVで出力できる。
- ユーザーアクセスログおよびシステムエラーログについて、保持している全期間の明細をTSVで出力できる。
- 初期ユーザーをTSVから一括登録し、初回パスワード設定リンクをメールで案内できる。

### システム自動機能

- ツール利用履歴、ユーザーアクセスログ、システムエラーログを区別して記録する。
- ログイン失敗が規定回数に達したユーザーを一定時間ロックする。
- 問い合わせの登録後に、送信者と対象に応じた担当者へメールを送信する。
- 問い合わせメールの送信は一回だけ試行し、失敗時のシステムによる再送は行わない。
- 管理者が送信を指示したお知らせを、通知設定に応じた利用者へ送信する。
- 不要な一時ファイルおよび保持期間を超えたログを削除する。

状態別の利用可否、画面項目、入力制限、送信条件および失敗時の動作は、[画面・機能設計](02_画面・機能設計.md)で定義する。

## 3. 非機能要件

### セキュリティ

- HTTPSを使用し、未認証ユーザーから通常機能へのアクセスを制限する。
- 管理機能はシステム管理者のみ利用可能とする。
- サイト・ツールの状態と権限をサーバー側で確認し、直接URL、APIおよび保護対象ファイルからも制限を回避できないようにする。
- 認証・パスワード管理には標準機能を使用し、独自の暗号処理を実装しない。
- パスワードや認証トークン等の機密情報を不必要に表示・出力しない。
- DBユーザーには必要最小限の権限のみ付与する。
- 接続文字列やパスワード等をソースコードへ直接記述しない。
- SQLインジェクション、XSS、CSRFへの対策を実施する。
- 管理者のアップロードと問い合わせ添付は、許可する拡張子・1ファイル当たりの最大容量をサーバー側で検証する。

認証の実装、Cookie、トークンおよび鍵の取扱いは、[認証構成](03_システム構成・開発標準.md#authentication)を参照する。

### 対応クライアント

- 会社支給のWindows端末を対象とする。
- 会社標準のMicrosoft Edgeを対応ブラウザとする。

### 可用性・性能

- 登録ユーザー約200名、同時利用約5名を前提とする。
- 大規模な分散システムやオートスケーリングは前提としない。
- 保守性と運用のしやすさを優先する。
- 画面ごとの厳密なレスポンスタイムは定義しない。
- 通常操作に支障がないことを検証環境で確認する。
- 長時間計算、大量データ処理、大容量帳票生成はツール単位で要件を定める。

### 共通エラー処理

- 本番環境では、例外の詳細およびスタックトレースを画面へ表示しない。
- 利用者には共通エラー画面と問い合わせ用の識別番号を表示する。
- 問い合わせ用の識別番号をシステムエラーログへ記録する。
- ポータルおよび各Webツールで共通のエラー表示形式を使用する。

### 障害分離

- 一つのWebツールの障害によって、ポータルや他のWebツールを停止させない。
- サイトへの入場が許可されている場合は、ツール停止中もポータルのツール一覧、詳細、お知らせを利用できる構成とする。
- Webツールごとに独立して停止、更新、再起動できる構成とする。
- メール送信の失敗によって、お知らせの登録・更新を失敗させない。
- 共通API障害時の影響範囲を設計工程で明確にする。

### 保守性・拡張性

- ポータルと各ツールを個別のソリューションに分割する。
- ツール単位で改修、テスト、リリースできる構成とする。
- 共通処理は共通APIまたは共通ライブラリとして提供する。
- 各ツールの実装方式を可能な限り統一する。
- ツール開発用の標準テンプレートとサンプルツールを用意する。

<a id="retention"></a>

### データ・ログ保持

- 計算結果および帳票データは原則としてシステム側へ保持しない。
- 問い合わせの添付ファイルはメール送信時だけ一時保存し、恒久保存しない。
- 入力内容、計算結果、帳票内容、パスワード、接続文字列、認証情報をログへ記録しない。
- ツール利用履歴は原則として削除せず保持する。
- ユーザーアクセスログは6か月間保持する。
- システムエラーログは6か月間保持する。
- 保持期間を超えたユーザーアクセスログおよびシステムエラーログは定期削除する。

<a id="theme"></a>

### 環境識別・画面テーマ

- 開発環境と本番環境は設定ファイルの値によって判定する。
- 環境の判定をビルド構成、URLまたは利用者の選択だけに依存させない。
- 画面上部の帯は、本番環境では青、開発環境では赤を既定色とする。
- 利用者に環境区分を意識させないため、帯に「本番環境」「開発環境」等の環境名は表示しない。
- 本文領域には社内システム統一テーマを固定して適用し、テーマを切り替える設定は設けない。
- 開発環境では赤い帯、本番環境では青い帯を固定表示する。
- ポータルおよび各Webツールで同じ環境判定と帯の表示ルールを使用する。
- 利用者ごとのテーマ選択およびダークモード等は対象外とする。
- サイト公開状態、ツール状態等の業務上の状態は、色だけで表現せず表示名称を併記する。環境区分を示す帯はこの限りではない。
- コードごとの表示色は、環境を示す帯の色および画面全体のテーマ設定とは分離する。
