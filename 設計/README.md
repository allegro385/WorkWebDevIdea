## 2. 読む順番

- 利用者との要件確認：要件定義 → 画面・機能設計。
- 開発準備・実装：システム構成・開発標準 → DB設計 → 対象機能の画面・機能設計。
- 初期導入・配備・公開状態の変更：導入・運用 → 参照されている設計資料。
- 未確定部分の相談：検討事項 → 関連資料。

## 3. 更新ルール

- 要件定義には「何を実現するか」と品質・対象範囲を記載し、細かな画面動作や実装手順を持ち込まない。
- 状態別の利用可否表、入力条件、メール送信条件などの動作ルールは画面・機能設計を正とする。
- 共通処理の実装方式はシステム構成・開発標準、カラム・キー・制約はDB設計を正とする。
- 担当者が実行する登録・配備・復旧手順は導入・運用に記載する。
- 同じ詳細仕様を複数ファイルへコピーせず、関連箇所へリンクする。要件の要約や運用確認項目は、詳細仕様と矛盾しないようにする。
- 未決定事項を確定仕様として書き込まない。決定したら関連資料と検討事項をまとめて更新する。
- 共通監査列はDB設計の共通項だけに記載し、各テーブルの項目一覧へ重複記載しない。
- 参照はファイル名・見出しへのリンクを使用し、旧資料の章番号だけで案内しない。
- 画面ID、テーブル名、カラム名、コード値は、別の決定がない限り分割を理由に変更しない。
