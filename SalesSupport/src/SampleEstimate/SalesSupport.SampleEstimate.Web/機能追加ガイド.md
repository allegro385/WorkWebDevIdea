# サンプルから機能を追加する順序

このサンプルは新しいツールへコピーする完成品ではなく、変更箇所を辿る教材です。最初に[設計方針](../../../../設計書/12_サンプル・テンプレートツール設計方針.md)と[Common詳細設計](../../../../設計書/10_Common詳細設計.md)を確認します。新規ツールは`New-SalesSupportTool.ps1`でテンプレートから生成し、ToolId・業務仕様を個別に決めてください。

1. 入力項目を増やすときは`Models/EstimateModels.cs`に表示名・型・入力属性を追加し、`Views/Tool/Index.cshtml`に欄を置きます。`Services/EstimateService.cs`でサーバー側の範囲・選択肢を再検証します。画面属性だけで受理条件を決めないでください。
2. 計算内容を変えるときは`EstimateService.CalculateAsync`と`EstimateResult`を変更し、画面結果とTSV出力の両方を揃えます。金額の丸め、日付基準、NULLの意味を設計・テストに書きます。
3. 永続化が必要なときだけ、ツール固有Entity・DbContext・Serviceを追加します。SQLの列・制約・索引とEFマッピングを同時に更新し、Portal/Commonの表をツール側へ集約しません。既存DBには新規構築SQLを再実行せず、専用の移行SQLを作ります。
4. 更新時には本人の条件を常に付け、DB監査列`UpdateCount`の元の値で競合を検出します。副作用のあるPOSTにはCSRF、送信IDの一意制約、成功後のGETへの遷移を組み合わせます。ブラウザーのボタン無効化だけに依存しません。
5. ファイルを使う場合はCommonの`IFileStorage`とDBの`TOOL`＋`TOOL_INPUT`条件を使い、一時ファイルを`finally`で破棄します。結果や入力ファイルを恒久保存しない設計を維持します。CSV/TSVはCommonの出力処理を使います。
6. ControllerはHTTPと画面遷移、Serviceは業務判断に分けます。入口の`WEB_OPEN`、実行の`WEB_EXECUTE`、共通認可とCSRFを残します。例外時に成功ログを先に書かないでください。
7. 対応する単体テスト、SQLの安全ゲート、設計書、READMEを更新してから`dotnet build`・`dotnet test`を行います。実DB、Portal、IIS、Cookie往復は別の結合検証として記録し、未実施なら成功と書かないでください。
