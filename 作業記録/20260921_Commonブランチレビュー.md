# CommonブランチのPR前レビュー

## 判定

元の差分には修正すべき問題があり、そのままの取り込みは非推奨。下記を独立cloneの同名ブランチ作業ツリーで修正した。push・PR作成は未実施。

## 修正した問題

| 優先度 | 問題 | 修正 |
| --- | --- | --- |
| P1 | 保存ルート自身・祖先のリンクを検査せず、公開・配置先配下も指定可能 | 全祖先の再解析ポイント検査と起動時の領域重複検証。未定義領域・用途も拒否 |
| P1 | 保存前にFileIdを要求し、新規保存→ToolFiles登録の順序で呼び出せない | GUID名で先に保存し、DB採番への依存を除去 |
| P1 | ResponseHeadersRead後の本文受信にHttpClient.Timeoutが適用されない | 本文読み取りまで同じ制限時間・キャンセルを渡す |
| P1 | ログの許可キーへ任意のメール・パス・秘密値を渡せる。パスの推測マスクでは漏れる | 固定値／数値のみ採用、要求パスはルートテンプレートを記録 |
| P2 | 開発宛先置換が先行し、実宛先0件・上限超過・形式不正を見逃す | 実宛先検証後に置換。SMTP有効時の上限とTLS方式を必須化 |
| P2 | 共通APIが指定するX-CSRF-TOKENと標準のヘッダー名が不一致 | 共通登録でヘッダー名を設定 |
| P2 | HTTPがエンコードされた親移動を受け入れ、登録クライアントが自動転送・Cookieを使用 | 経路を検証し、名前付きクライアントの転送・Cookieを無効化 |
| P2 | 清掃例外や途中ファイルの削除失敗が記録されない | 元の業務結果を変えず一度だけログ試行 |
| P2 | 中間の明るさのバッジが白文字になり読みづらい | 背景色は維持し、黒／白の高コントラスト側を選択 |

API変更：`PermanentFileRequest`からFileIdを除去。`SystemErrorEvent`は自由文字列Messageではなく許可値用Detailsを受け付ける。Mail有効時はMaxRecipients、TlsModeを明示設定する。
