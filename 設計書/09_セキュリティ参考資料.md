# 営業支援ポータル セキュリティ参考資料

作成日：2026-09-13。設計者・運用担当者向けに、採用した設定の意味と制約を説明する資料。

仕様の正本は[画面・機能設計](02_画面・機能設計.md#login)、[認証構成](03_システム構成・開発標準.md#authentication)、[DB設計](04_DB設計.md#users)、[導入・運用](05_導入・運用.md)。本資料は規格への完全準拠や攻撃の完全防止を宣言するものではない。

## 1. 判断の基準

一般公開しない、重要度の高い個人情報を扱わない前提で、基本防御を維持しながら「実装・運用の軽さ → 利便性 → 追加のセキュリティ強化」を優先する。非公開という前提はURLを秘密にするだけではなく、ネットワークの到達範囲で確認する。

認証・権限確認・入力検証・総当たり対策は実装に残す。鍵管理やレート制限は標準機能を使い、専用の攻撃検知基盤・分散キャッシュ・監視画面は初期実装に追加しない。

## 2. 認証の全体像

```text
利用者 → ポータルでメールアドレス・パスワードを入力
       → Identityが検証 → ブラウザーへ認証Cookieを発行
       → ポータル・各WebツールがCookieとDBの最新状態を確認
       → 利用可能な画面・処理・ファイルだけを提供
```

認証Cookieは「ログイン済みの証明」で、利用者のパスワードそのものではない。ユーザーのログイン認証と、サーバーからSQL Serverへ接続するDB認証は別の仕組み。

ポータルと各ツールでCookie名、認証スキーム、Data Protectionのアプリケーション名・鍵を共有する。同じIISサイトの配下に置くだけでは共有認証は成立しない。[Microsoft：Cookie共有](https://learn.microsoft.com/en-us/aspnet/core/security/cookie-sharing?view=aspnetcore-10.0)

## 3. ①〜③ ログイン期限とブラウザー終了

| 項目 | 採用内容 | 利用者から見た動作 |
| --- | --- | --- |
| 最大期限 | 初回認証から8時間 | 操作中でも8時間を過ぎれば再ログイン |
| Cookie有効期間 | 60分・標準のスライド更新 | 画面遷移・検索・保存・計算等の対象要求で標準条件に従って更新。最後の操作から厳密に60分は保証せず、最大8時間は超えない |
| Cookie保存 | 非永続のセッションCookie | 「ログイン状態を保持する」機能は設けない |
| 期限切れ表示 | 次のリクエストで案内 | 放置中の画面を自動で切り替えるタイマーは設けない |

9時にログインした場合、操作を続けても17時が上限。途中の期限はCookieの発行・更新時刻により決まり、最後の操作時刻に60分を足した時刻と必ずしも一致しない。入力だけでサーバー通信がない時間、自動ポーリング、静的ファイル取得では延長しない。

セッションCookieはブラウザーの復元機能で復元される場合がある。タブを閉じるだけで削除されるわけでもない。終了検知の独自処理は設けず、確実に終える場合はログアウト操作を使う。サーバー側の期限は復元後も確認する。[MDN：Cookieとセッション復元](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie)

実装の簡素化を優先し、共有Cookieの標準スライド更新を採用する。初回認証時刻は保護されたチケットへ保持し、更新時にも維持してCommonで8時間の上限を確認する。最終操作時刻共有の専用DBテーブルは設けない。

## 4. ④ Cookieを送る条件

| 設定 | 採用値 | 意味 |
| --- | --- | --- |
| SameSite | Lax | 別サイトから通常のリンクで移動した場合もログイン状態を利用しやすい |
| Secure | 有効 | HTTPSで送る |
| HttpOnly | 有効 | ページのJavaScriptからCookieを直接読み取らせない |
| Path | / | 同じホストのポータルと各ツールで共有 |
| Domain | 指定しない | 現在のホストに限定する |

Laxは、別サイトからのあらゆる通信へCookieを付ける設定ではない。また、SameSiteだけをCSRF対策とせず、更新要求にはASP.NET Coreの標準対策を組み込む。GETで変更を実行しない。[MDN：各Cookie属性](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie)

## 5. ⑤⑥ 古い権限・公開状態の失効

保護された画面・API・ファイルのリクエストごとにDBを参照し、IsActive、RoleCode、SecurityStamp、サイト・ツール公開状態を確認する。SecurityStampは「認証情報の世代を判別する値」であり、画面編集の競合検出に使うConcurrencyStampとは役割が異なる。

無効化や降格・パスワード変更等でSecurityStampを更新したら、旧Cookieとの不一致により利用を拒否する。単にDBの値を書き換えるだけでなく、各アプリのリクエスト検証を実装することが必要。

これらの情報はリクエストをまたいでキャッシュしない。同一リクエスト内だけ再利用する。DB参照は増えるが、想定同時利用5名の構成で、複雑な失効通知やキャッシュ同期を避ける判断。通常負荷で検証する。DBから判定情報を取得できない場合は利用を許可しない。

画像・CSSのブラウザーキャッシュはこの判断とは別である。

## 6. ⑦ 初回設定・再設定リンク

初回設定は14日、再設定は1時間。Identityの保護・期限検証に、ユーザー・用途別の最新発行番号の照合を組み合わせる。

```text
発行   → AspNetUserTokensの用途別番号を更新
使用   → Identity検証と最新番号の一致を確認
再発行 → 番号が変わるので以前のリンクは拒否
完了   → パスワード更新と番号消費を一括確定
```

専用の発行履歴テーブルや管理画面は作らない。番号とIdentityトークンの結び付け、並行発行・同時使用でも一度だけ完了する原子的更新は実装が必要。再設定メールの最終受付時刻も同じ既存テーブルの別項目で保持する。単なる「新しいトークン生成」だけで旧リンク失効済みとは扱わない。

## 7. ⑧ 総当たり・メール連打・DoS対策

| 対象 | 採用する初期値 | 保存・拒否方法 |
| --- | --- | --- |
| アカウントの連続ログイン失敗 | 5回で30分ロック | IdentityのDB管理。ユーザー管理画面から管理者が解除可能 |
| ログイン要求 | 30回/1分/IP | メモリ内の固定時間窓。超過はHTTP 429 |
| 再設定メール要求 | 30回/1時間/IP | 同上 |
| 同一アカウントへの再設定要求 | 直近受付から5分に1回 | DBの受付時刻を原子的更新。抑制時も共通受付文言 |

IP単位の値は検証用の初期値であり、安全性の普遍的な基準ではない。社内で同じIPを共有する利用者がいるため通常操作で確認・調整する。固定時間窓は境界の前後に要求が集中する可能性がある。待機キューは設けない。

メモリ内カウントはプロセス再起動で消え、別プロセスとは共有されない。この制約を受け入れ、認証要求はポータルへ集約する。DBのアカウントロックは再起動で消えない。

不存在・無効・間隔制限中でも同じ受付文言にし、登録有無や送信結果を画面へ出さない。有効だが初回未設定なら初回設定用リンクを発行する。接続元制限は登録状態に関係なく適用する。

頻度制限にはASP.NET Core標準機能を利用する。DoSはIIS・ネットワーク側の要求頻度・接続数等の制限と分担する。レート制限だけで回線を飽和させる大規模DDoSまで防げるとは扱わない。[Microsoft：レート制限](https://learn.microsoft.com/en-us/aspnet/core/performance/rate-limit?view=aspnetcore-10.0)

## 8. ⑨ Cookie等を保護する鍵

Data Protectionの鍵を、Web公開領域・配備フォルダー外の共通フォルダーへ永続化する。単一Windowsサーバー上で、マシン単位のDPAPIによって保存時に暗号化する。

```text
共通Config         接続先・動作設定
共通鍵フォルダー   Cookie・設定トークン等を保護する鍵
```

PersistKeysToFileSystemで保存先を指定するだけでは暗号化の設定は完了しないため、ProtectKeysWithDpapi(protectToLocalMachine: true)も明示する。マシン単位DPAPIは、そのサーバーの他のアカウントから暗号化ファイルを取得できた場合の復号を妨げないため、NTFS権限も必須。関係するIISアカウントに鍵の読取・生成に必要な権限、運用管理者に管理権限を付ける。[Microsoft：鍵の保存時暗号化](https://learn.microsoft.com/en-us/aspnet/core/security/data-protection/implementation/key-encryption-at-rest?view=aspnetcore-10.0)

鍵の生成・更新は標準機能へ任せ、配備で消去しない。別サーバーへコピーするだけで復旧できるとは考えず、移行時は再ログイン・必要なリンクの新規再発行を伴う手順を採用する。

## 9. 既に採用した関連事項

- パスワードは14〜64文字、ASCII英数字・記号を許可し、スペース等は禁止。文字種の混在は強制しない。これは本システムで決めた条件であり、特定規格への準拠宣言ではない。
- 禁止パスワードはWeb公開領域外のUTF-8テキスト（1行1件）を起動時に読み込み、完全一致で拒否する。運用担当が手動差し替え・再起動で更新する。照合リストにない弱いパスワードの検出は保証しない。
- 担当管理者は引継ぎ後に無効化・降格する。権限変更のDB運用ではSecurityStamp・ConcurrencyStampも更新する。
- メールアドレス変更の本人・新アドレス確認は社内運用で行い、整合更新・既存セッション・リンクの失効はアプリで行う。
- ログ抽出・削除・残存ファイル清掃・監視は[導入・運用](05_導入・運用.md#maintenance)に従う。

## 10. 実装・導入で残る確認

共有Cookieの標準スライド更新と最大8時間の上限は採用済み。初回認証時刻の保持項目、対象要求の判定、発行番号の具体形式と原子的更新、実際の共有IPと制限値、鍵フォルダーとACL、信頼するプロキシ、IIS・ネットワーク制限の具体値は残る詳細設計。
