## 1. サーバー環境確認チェックリスト

### OS・基本情報

- [ ] Windows Serverの製品名、バージョン、エディション、OSビルドを確認した
- [ ] OSがx64であることを確認した
- [ ] 対象OSが.NET 10の正式なサポート対象であることを確認した
- [ ] Windows Serverのサポート期限が運用予定期間を満たすことを確認した
- [ ] OSのセキュリティ更新を継続して適用できることを確認した
- [ ] CPU、メモリ、ディスク容量を確認した

### IIS・.NET

- [ ] Web Server（IIS）サーバーロールを利用できることを確認した
- [ ] IISのバージョンと現在の構成を確認した
- [ ] IIS有効化後に.NET 10 Hosting Bundleをインストールできることを確認した
- [ ] ASP.NET Core Module V2を利用できることを確認した
- [ ] .NET 10の月次パッチを継続して適用できることを確認した
- [ ] Hosting Bundleの導入・更新に必要な権限と承認手続きを確認した
- [ ] 導入・更新後にサーバーまたはIISサービスを再起動できることを確認した
- [ ] IISサイトとツールごとのアプリケーションプールを作成できることを確認した

### ネットワーク・セキュリティ

- [ ] DNS名とHTTPS用サーバー証明書を取得・更新できることを確認した
- [ ] 利用者端末からポータルへの通信経路を確認した
- [ ] SQL Serverへの接続経路とファイアウォール設定を確認した
- [ ] SMTPサーバーへの接続可否を確認した
- [ ] 初回パスワード設定メールおよびパスワード再設定メールを送信できることを確認した
- [ ] 初回設定・再設定リンクについて、設計どおりの有効期限、再発行後の旧リンク無効化、使用済みリンクの拒否を確認した
- [ ] アカウント単位のロックと接続元単位の試行制限が機能し、社内の共有接続元からの通常利用を妨げないことを確認した
- [ ] ポータルと各Webツールから参照できるData Protectionキーの共通保存先を用意できることを確認した
- [ ] Data Protectionキーの保存先へ必要なアプリケーションプールだけがアクセスできることを確認した
- [ ] ポータルと各Webツールから参照できるCommonの共通設定ファイルを、Web公開領域と配置フォルダーの外へ用意できることを確認した
- [ ] 共通設定ファイルへ必要なアプリケーションプールだけがアクセスでき、環境変数`SalesSupport__CommonConfigPath`で各アプリから同じファイルを参照できることを確認した（配置フォルダー外かどうかは起動時に自動検査されない）
- [ ] 機密情報を安全に保管できることを確認した
- [ ] 配置先、ログ、マニュアル、配布ファイルのアクセス権限を確認した

### 検証・運用

- [ ] 本番相当の構成で事前検証できることを確認した
- [ ] 本番環境と開発環境の設定ファイルに正しい環境区分が設定されていることを確認した
- [ ] 本番環境で青帯、開発環境で赤帯が表示され、環境名を示す文字が表示されないことを確認した
- [ ] 本文に社内システム統一テーマが固定適用されることを確認した
- [ ] ASP.NET Core 10アプリをIISで起動できることを確認した
- [ ] HTTPS、Identityログイン、共有Cookie、SQL Server接続およびメール送信を確認した
- [ ] サイトのPublic公開・Private公開について、一般ユーザーと管理者の入場可否を確認した
- [ ] ポータル、各Webツール、APIおよび保護対象ファイルへの直接URLアクセスにも利用制御が適用されることを確認した
- [ ] Webツール・配布アプリ・参考資料のURLを直接入力またはブックマークから開いた場合、利用条件を満たすユーザーは利用でき、未認証・無効ユーザーや公開状態・権限による制限対象者は利用できないことを確認した
- [ ] 限定公開ツールは両権限の通常一覧・お気に入りに薄いグレーで表示され、一般ユーザーは詳細・起動・取得不可、管理者は可能であることを確認した
- [ ] 非公開ツールは両権限の通常一覧に表示されず、管理画面でのみ確認・編集できることを確認した
- [ ] 非公開のツールは管理画面でのみ参照・編集でき、管理者も起動・取得できないことを確認した
- [ ] ログイン済みでも、次のリクエストからサイト公開状態の変更が適用されることを確認した
- [ ] CodeMasterの背景色と白文字が読みやすく、色を使わなくても表示名称から状態を判別できることを確認した
- [ ] アプリケーションログを参照できることを確認した
- [ ] サーバー側でファイル・DBバックアップを実施できることを確認した
- [ ] サーバー監視、ディスク監視、障害通知の方法を確認した
- [ ] 手動でのビルド、テスト、発行、本番反映手順を確認した

## 2. 配布・配置方針

- デスクトップアプリケーションは管理画面からアップロード・公開する。
- Webツールとデスクトップツールの参考資料は管理画面から追加・差し替え・削除・並べ替えを行う。配布アプリは提供内容でバージョン履歴とは独立して初回登録・差し替えを行い、削除操作は設けない。
- 資料提供型はWeb URLと配布アプリを持たず、関連資料だけを管理する。一般公開へ変更する前に関連資料が1件以上登録されていることを確認する。
- ファイル種別・容量は[提供内容の仕様](02_画面・機能設計.md#tool-admin)に従い、保存領域・IIS要求サイズ上限を準備する。
- 管理画面では配布ファイルおよびマニュアルの現在配布するファイルだけを管理し、旧版の保存・世代管理および復元機能は設けない。デスクトップ配布ファイルはツールごとに最大1件とする。
- 切戻しでは管理者が外部で保管した旧ファイルを提供内容から再アップロードし、バージョン更新情報欄で対応する現在のバージョンを選択・保存する。実ファイル、選択バージョン、利用者向け表示を管理者が確認する。
- ファイル格納先の総容量および使用量はサイト側で管理せず、サーバー運用のディスク監視で管理する。
- 旧版が必要な場合の保管と復元は、サーバー側のバックアップ運用で行う。
- Webツール本体は`dotnet publish`済み成果物をサーバーへ手動配置する。
- [全体のURL・IIS構成](03_システム構成・開発標準.md#urls)に従い、ポータルをIISサイトに登録し、各Webツールをその配下のアプリケーションとして手動登録する。専用アプリケーションプールと発行成果物の物理フォルダーを割り当てる。
- 接続文字列を含むCommonの共通設定ファイルは、Web公開領域と各アプリの配置フォルダーの外へ1つだけ置く。雛形は`SalesSupport/config/salessupport.common.sample.json`とし、実値を記入したファイルをリポジトリへ含めない。
- ポータルと各WebツールのIISアプリケーションへ、共通設定ファイルへの相対パスを環境変数`SalesSupport__CommonConfigPath`で設定する。基準は各アプリの実行フォルダーで、全アプリが同じファイルを指す。Webツール固有の`SalesSupport__Application__ToolId`と`SalesSupport__Application__Name`はアプリごとに設定する。
- 共通設定ファイル内のフォルダー（鍵共有フォルダー、保存領域）は共通設定ファイルからの相対パスで指定する。アプリと設定ファイルの配置階層を揃えると、環境ごとに値を書き換えずに済む。配置例と基準フォルダーは[共通設定ファイル](../SalesSupport/config/README.md)に従う。
- 共通設定ファイルのアクセス権は、対象アプリケーションプールの読取りと運用管理者だけに限定する。Data Protectionキーと同じ秘密情報として保管し、内容を作業記録・ログへ残さない。
- 共通設定ファイルを変更した場合はポータルと全Webツールを再起動する。アプリは実行中に再読込みしない。
- IISの設定後、ポータルのツールマスタ・提供URLを別途登録する。IISへの登録だけでポータルのツール一覧へ自動追加はしない。
- 新規Webツールは[テンプレート方針](12_サンプル・テンプレートツール設計方針.md)に従い、`SalesSupport/scripts/new-tool.bat`へToolIdを渡してソース一式を生成する。生成スクリプトは開発用ソリューション作成までとし、DB登録・SQL適用・IIS設定・本番配備は行わない。
- サンプルツール用のツール登録、`TOOL_INPUT`ポリシー、実演用テスト表1つとデータは開発環境専用のSQLで分離する。環境指定とDB側の開発許可標識を検証して手動適用し、本番の初期構築・リリースへ含めない。SQLの実体と適用・清掃手順はサンプル実装時に作成する。
- Webツール本体を管理画面からアップロード・配備する機能は設けない。
- ポータル自身の更新もサーバーへ手動配置する。
- IIS側での停止はアプリケーション障害や配備作業時の運用手段とし、通常の状態切替には使用しない。

## 3. 手動リリース

- DB構造の変更はレビューした版付きSQLをリリース担当者が適用し、適用順序と適用済み版を記録する。アプリ起動時の自動DB更新は行わない。EF Coreマイグレーションは必要に応じてSQL生成に利用できるが、適用は手動とする。

- 初期段階ではCI/CDを利用しない。
- リリースに使用する.NET SDKのバージョンを定める。
- `restore`、`build`、`test`、`publish`の手順を文書化する。
- Commonを更新した場合は、影響を受けるポータルおよび各ツールの`.slnx`で`restore`、`build`、`test`を実行し、対象アプリケーションを改めて`publish`する。Commonは各ソリューションに含まれるソースプロジェクトへの`ProjectReference`としてビルドするため、参照パッケージの版数更新は行わない。
- 稼働中の`bin`フォルダーへCommon.dllだけを一括上書きする運用は行わない。
- 配布成果物と変更内容を保管する。
- 本番反映の担当者と承認方法を定める。
- Webツールの旧バージョンへの切り戻し手順を用意する。
- DB変更についても事前バックアップと切戻し手順を確認する。起動時の自動DB復旧は設けない。

## 4. サービス開始時のユーザー登録

- 一括登録のDBエラー時はユーザー単位で確定した結果と元TSVの行番号を確認し、未登録分のみでTSVを作り直す。自動再開や登録済み行の統合は行わない。登録済みでメールだけが失敗したユーザーは再取込せず、既存のリンク新規再発行ルールに従う。

- 初期システム管理者を別の導入手順で一名以上登録する。導入用処理の設計は[Portal詳細設計](11_Portal詳細設計.md)第6節を参照する。
- [初期ユーザー一括登録仕様](02_画面・機能設計.md#bulk-registration)に従ってTSVを準備する。
- 事前作成した管理者でユーザー管理の「新規登録（TSV取り込み）」を開き、TSVを選択する。検証結果・登録予定件数を確認して実行する。Identityとメール送信の処理仕様は02の一括登録仕様に従う。
- 事前検証の結果と登録予定件数を確認し、エラーを解消してから登録を開始する。
- 登録後に予定件数、登録件数、重複件数およびユーザー設定作成件数を確認する。メール送信結果の失敗表示は行わない。
- メール送信失敗時はシステムエラーログテーブルへの記録だけとし、失敗を理由とする再送作業は行わない。利用者からの依頼等による初回設定リンクの新規再発行はユーザー管理から行う。
- ユーザーをDBへ直接INSERTする運用は行わない。
- 初期登録後に追加するユーザーは、原則としてユーザー管理画面から登録する。
- 開発専用DBでのログイン試験に限り、Portalの`add-test-user`対話コマンドで複数の一般ユーザーを作成できる。ASP.NET CoreとPortalの両環境設定を開発用にした場合だけ使用し、本番のユーザー追加・メール確認手順には流用しない。

## 5. マスタの初期登録・直接更新

- 新規ツールは所定のSQLスクリプトまたはストアドプロシージャでDBへ直接登録する。
- 新規ツールの登録時は有効なシステム管理者のOwnerUserIdを必須指定し、担当者未設定では登録しない。
- 新規ツールは管理画面ではなく所定SQL等の手動運用で登録し、状態には非公開（HIDDEN）を明示的に設定する。WEBのページURLは登録時または登録後に手動設定する。配布アプリ・URL・現在版未登録でも通常更新・一般公開への状態変更を許可する。所定SQL等での更新も[ツール管理](02_画面・機能設計.md#tool-admin)に従う。
- 初期SQLではToolFilesの空レコードを作らない。Web起動URLは新規ツール登録時に設定し、以後は管理画面で入力・更新する。参考資料は提供内容セクションから追加する。デスクトップ配布アプリは提供内容で初回アップロードする。バージョン履歴を別途登録し、バージョン更新情報欄で現在のバージョンを手動選択する。
- 資料提供型はToolType=`DOCUMENT`、WebAppUrl=NULL、Status=`HIDDEN`で登録する。関連資料は登録後に管理画面から追加し、1件以上を確認してから一般公開へ変更する。
- WebツールはIISへの手動登録・配置も別途行い、非公開のまま管理画面で設定を確認してから、必要に応じて限定公開または一般公開へ変更する。
- デスクトップツールをWeb化する場合は、当面は既存ツールの種別を変更せず、新しいWebツールとして別のToolIdで登録する。
- デスクトップツールからWebツールへの切替手順とデータの扱いは、[移行運用](#tool-migration-operation)に従う。
- FAQカテゴリとFAQは管理画面を設けず、検証済みの所定SQLで登録・更新する。
- CodeMasterは管理画面を設けず、所定のSQLで登録・更新する。
- 初期DB構築では`SalesSupport/sql/001_CreateTables.sql`、`002_SeedMasterData.sql`の順に実行する。`900_SeedDummyData.sql`は開発環境だけで使用し、本番環境では実行しない。
- SystemSettingsは[DB設計第10節](04_DB設計.md#system-settings)の3設定を所定SQLで初期登録する。既存データがある場合は旧公開状態・案内文を対応キーのSettingValueへ移し、値を維持する版付き移行SQLを用意する。公開状態・日付形式・必須条件とUpdateCountを検証する。テスト用業務日付は開発環境の対応業務処理だけに適用し、本番では参照しない。
- FileUploadPoliciesとFileUploadPolicyExtensionsは所定SQLで同一トランザクション内に登録・変更する。共通監査列・UpdateCountによる競合確認を適用し、用途と対象の組合せ、重複、拡張子形式、正の容量上限、拡張子が1件以上あることを検証する。管理画面・更新APIは設けない。
- 問い合わせ添付・参考資料・配布アプリの共通ポリシーを初期登録し、処理用一時アップロードを使うツールには個別のTOOL_INPUTポリシーを用意する。初期値は[ファイル制限テーブル](04_DB設計.md#upload-policies)に従う。IIS・アプリ・SMTPの実際の上限との整合を変更前に確認し、設定反映後に画面案内とアップロード検証を確認する。
- ErrorCodesは所定の登録SQLで初期登録・文言更新する。共通システムコードは既存のコード表記を維持し、ツール固有コードはToolIdとErrorNoから生成する。登録時に所属ツール・番号範囲・コード重複を検証する。
- コードのキー・許容値・変更時の注意事項は[コードマスタ](04_DB設計.md#code-master)に従う。
- ユーザー情報は原則としてUserManagerで更新する。ただし、登録後の権限変更は例外として所定のDB更新手順で行う。ユーザーの直接INSERTやパスワードハッシュの直接編集は行わない。
- 権限変更時はRoleCode、SecurityStamp、ConcurrencyStampを一つのトランザクションで更新する。最後の有効な管理者を降格させない。
- 管理者を無効化・降格する前に、担当するツールと問い合わせを別の有効な管理者へ引き継ぐ。Tools.OwnerUserIdとInquiries.AssigneeUserIdを対象とし、担当解除で済ませず、対象者への割当が残っていないことを確認してから変更する。
- 引継ぎは既存のツール管理・問い合わせ管理の担当者変更操作で行い、自動引継ぎや専用の一括引継ぎ機能は設けない。無効化・降格の作業中は他の管理者による対象者への新規割当を止めるよう作業調整する。
- 問い合わせの現在担当者は引き継ぐが、送信者やバージョン履歴の修正担当者など、過去の実績を表すユーザー項目は変更しない。

<a id="tool-migration-operation"></a>

## 6. デスクトップツールからWebツールへの移行

- 新しいWebツールは、既存のデスクトップツールとは別のToolIdで登録する。
- 新しいWebツールを非公開として手動登録し、起動URLを設定する。IISへの配置・登録を完了した状態で、システム管理者が管理画面から設定を確認する。
- 切替時は、旧デスクトップツールを非公開へ変更してから、新しいWebツールを一般公開へ変更する。
- 旧デスクトップツールのお気に入り、利用履歴、お知らせ、バージョン履歴および提供内容は、新しいWebツールへ引き継がない。
- 旧デスクトップツールのレコードと履歴は削除せず、非公開のまま保持する。

<a id="site-status-operation"></a>

## 7. サイト公開状態の変更

- Public公開とPrivate公開（限定公開）の変更は、DB運用担当者が所定SQLでSystemSettingsのSITE＋PUBLICATION_STATUSのSettingValueを更新して行う。サイト画面・APIからの変更機能は設けない。
- Private公開では一般ユーザーの入場を拒否し、システム管理者は通常画面、管理画面および管理APIを利用できる。
- Public公開へ変更する前に、管理者がPrivate公開の状態でポータルと各Webツールを確認する。Private公開への変更前には、一般ユーザーが入場できなくなることを作業担当者が確認する。
- 所定SQLは設定区分・キーとUpdateCountを条件に対象レコードだけを更新し、許可値を検証して共通監査列を更新する。公開状態はSITE＋PUBLICATION_STATUS、入場制限時の案内文はSITE＋PRIVATE_MESSAGEを対象とし、他の設定を上書きしない。状態変更後は管理者・一般ユーザーの入場可否と各Webツールへの直接アクセス制御を確認する。
- 初期構築時はPrivate公開で登録し、管理者による動作確認後にPublic公開へ変更する。

利用可否と管理画面の動作は[共通利用制御](02_画面・機能設計.md#access-control)、更新対象のカラムは[システム設定](04_DB設計.md#system-settings)を参照する。

## 8. バックアップ運用

- ファイルバックアップとDBバックアップはサーバー側の運用機能で実施する。
- タスクスケジューラ等によるバックアップ運用を前提とする。
- ポータルおよび各ツールにはバックアップ機能を実装しない。
- システム側は、バックアップ対象となるDBとファイル格納先をサーバー管理者へ提示する。

## 9. 定期処理・保守・ログ抽出

- log.UserActivityLogsとlog.SystemErrorLogsは、保持期間6か月に従う所定SQLをサーバーの定期タスクから実行して削除する。log.ToolUsageLogsは削除対象にしない。実行周期・日時基準・結果確認方法は運用詳細で定める。
- IISのWeb.configには`Portal__EnvironmentCode`を設定し、本番は`PRODUCTION`、開発は`DEVELOPMENT`とする。反映後に帯色が本番で青、開発で赤であることを確認する。直接SQLによる変更はUserActivityLogsの対象外のため、実施者、日時、対象、理由および結果を運用作業記録へ残す。
- 残存ファイルは保守時に候補を抽出し、DB参照と使用中の処理を確認して清掃する。作業中のファイルを削除しないよう対象処理の停止等を作業手順に含める。通常の一時ファイル破棄はアプリの責務として維持する。
- ログ明細とツール別利用者数のTSV出力は、システム管理者がログ管理画面でログ種別・抽出内容を選択して実行する。出力条件・形式は[出力仕様](02_画面・機能設計.md#logs-usage)に従う。
- 監視はサーバー監視基盤とログ確認手順で行い、ポータル専用の監視画面・通知基盤は実装しない。担当者・通知先・確認頻度は環境確認時に定める。
- ログ削除用のアプリ内スケジューラー・設定画面、残存ファイルの自動修復・監視・起動時清掃は設けない。アプリのエラー記録と正常系のファイル差し替え・旧ファイル削除は維持する。
- TSVは直接ダウンロードしサーバーへ恒久保存しない。一時ファイル使用時の削除と残存分清掃は既存方針に従う。運用で必要になった集計方法は仕様を定義して順次追加する。

## 10. 認証関連の運用

- ログイン要求30回/分/IP、再設定要求30回/時/IP、同一アカウントへの再設定要求5分に1回を検証用初期値とする。共有IP下の通常利用を確認し、必要なら共通設定の値を運用変更する。接続元カウントはアプリ再起動で消失するが、IdentityのロックはDBに残る。
- Data Protectionキーは共通フォルダーへ永続化し、対象IISアカウントと運用管理者にだけ必要な権限を付与する。保存時の暗号化はWindowsのマシン単位DPAPIを使用し、暗号化済みファイルにもACLを適用する。
- 配備時に鍵フォルダーを消去しない。別サーバーへの移行・鍵喪失時は既存Cookie・設定リンクが利用できなくなる前提で、再ログインと必要な設定リンク新規再発行を案内する。DPAPIで保護した鍵ファイルの単純コピーだけで別サーバーへ復旧できるとは扱わない。

- 禁止パスワードはアプリ同梱のUTF-8テキスト（1行1件）で管理し、Web公開領域外へ配置する。内容を確認したファイルへ手動で差し替え、認証アプリの再起動後に反映を確認する。DB登録・オンライン同期・自動更新は行わない。初期リストの出所と更新の担当・周期は運用詳細で定める。
- メールアドレス変更は管理者が社内の連絡経路で依頼元と新アドレスを確認してから実施する。認証情報の整合更新と失効処理は[画面仕様](02_画面・機能設計.md#users-admin)に従い、直接SQL更新には置き換えない。
- アカウントロックは30分経過で満了する。必要な場合は管理者がユーザー管理の編集画面で「ロック解除」を実行する。ロック終了日時をクリアし失敗回数を0にするが、有効・無効やパスワードの状態は変更しない。手動DB解除には置き換えない。
- 禁止リストに実ユーザーのパスワードを保存しない。設定時の照合は実装に残し、禁止リストの管理画面・外部照合は設けない。
- メールアドレス変更の確認メール・承認待ち状態・承認画面は設けない。重複検証、UserManagerによる更新、既存セッション・設定リンクの失効は実装に残す。
- パスワード再設定でロックを早期解除しない。ロック終了日時・失敗回数の参照と管理者による明示的な解除は[ユーザー管理仕様](02_画面・機能設計.md#users-admin)に従う。
