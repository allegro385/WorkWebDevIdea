# サンプルツール・テンプレートツール設計方針

ツール実装者はシステムの開発経験が約1年の担当者を想定する。テンプレート、生成スクリプト、見積試算・案件記録のサンプル、開発専用SQL、機能追加手順書の範囲を定義する。認証・利用制御などの共通契約は[システム構成・開発標準](03_システム構成・開発標準.md)、[Common詳細設計](10_Common詳細設計.md)を正とする。

## 1. 役割と構成

| 成果物 | 目的 | 内容の境界 |
| --- | --- | --- |
| テンプレートツール | ToolIdを決めて複製し、新しいWebツールの開発を開始する | 共通基盤の組込みと、入力→実行→結果表示または直接ダウンロードの最小例を動作させる。題材は`TemplateExample`へ隔離し、生成後に削除する前提とする。ツール固有DB表は持たない |
| サンプルツール | Commonの使い方と標準的な実装をソース・開発用サイトで学ぶ | テンプレートの流れに加え、EF Coreの検索・登録・更新・集計・同時更新検出、開発専用DB・ファイル処理・ログ記録を実演する |
| 機能追加手順書 | 初学者が変更箇所と確認方法を追えるようにする | 画面項目、Service、DB、設定、ログ、テスト、配置の追加手順を小さな作業単位で示す |

- サンプルとテンプレートはPortalとは別のWebアプリケーション、別の`.slnx`とする。各ソリューションには対象ツール、`SalesSupport.Common`、対象ツールのテストプロジェクトを登録し、Commonを`ProjectReference`する。Commonからツールを参照しない。
- テンプレートの元となるソリューション名は`template.slnx`とする。生成後のツールは固有名のソリューション・プロジェクト・フォルダーを持つ。
- Commonの共通レイアウト・ヘッダー・CSS・エラー表示、共有Cookie、サイト・ツール状態の利用制御を使う。ツール側にパスワード画面や独自セッション同期機構を作らない。
- テンプレートが持つ骨組み（Commonの組込み、認可、ログ、CSRF、画面の作法）と、差し替える前提の題材（入力項目・計算・画面文言）を物理的に分ける。題材は`TemplateExample`の名前空間・フォルダーと`TemplateExample`で始まるView名だけに置き、骨組みのフォルダーへ混ぜない。生成したツールでは題材が残ったままReleaseビルドできないようにする。配置と検出の条件は第2節の[題材の隔離と残存の検出](#題材の隔離と残存の検出)に従う。
- サンプルの説明用コードには、処理の目的、入力、検証、後処理、失敗時の動きを日本語で補足する。単なる名前の言い換えではなく、初心者が変更してよい箇所と変更してはいけない共通契約を示す。

## 2. テンプレートに最初から含める流れ

テンプレートとサンプルは「単独開発」（`standalone`）と「ポータル連携」（`portal`）の2つの起動プロファイルを持ち、生成直後の既定（Visual StudioのF5）は単独開発とする。単独開発はホスト設定`SalesSupport:Tool:ExecutionMode=Standalone`で選び、ポータル・DB・SMTP・共通設定ファイル・共有鍵フォルダーなしで入力画面・計算・TSV出力を動かす。業務日付は現在のJST日付を使い、DBログは保存せず、明細ファイルのアップロードと案件の保存・検索・更新は利用させない。以下の通常フローは連携モード（本番・結合試験）に適用する。詳細は[Commonの起動モード](10_Common詳細設計.md#ツールの起動モード)と[設定手順](../SalesSupport/config/README.md#ツールを単独で開発する)に従う。

1. 起動時に起動モードを確定し、連携モードでは環境・ToolId・Portal URL・DB接続・Data Protection鍵領域・一時保存領域など必要な設定を検証する。`AddSalesSupportCommon(ApplicationKind.Tool, environment, configuration)`を含むDIを登録し、要求パイプラインは`UseSalesSupportTool()`の1回の呼出しで組み込む。ミドルウェアの順序、セキュリティヘッダー、CSRFフィルターはCommonが所有し、ツール側へ展開しない。機密値はソース・配布用設定例へ書かない。ツール固有の`ToolId`と障害ログに使用する`Application:Name`は各アプリの環境変数（ローカルでは起動プロファイル）で与える。一時保存領域を使う場合はCommonの`RequireTemporaryStorage()`を呼び、検証式をツール側へ書き写さない。
2. 入口のGETで共有Cookieの現行ユーザー、サイト公開状態、対象ツールの種別・公開状態を確認する。直接URL・API・保護対象ファイルも同じ利用制御を受ける。入口アクションへCommonの`WebOpenLoggingFilter`を適用し、入口の利用を`WEB_OPEN`として一度記録する。
3. 共通レイアウトへ渡す表示情報はCommonの`IToolPageShell.Build(title, …)`で組み立て、Portal側のトップ・ツール一覧のパンくずをツール側へ書き写さない。入力画面に文字列、数値、日付、ラジオボタン、ドロップダウン、ファイル選択の代表例を置く。静的なRazorフォームを基本とし、入力項目を動的生成する汎用フォーム基盤は作らない。必須・形式・範囲をサーバー側で再検証し、項目エラーを画面へ返す。
4. 実行ボタンはCSRF付きPOSTとし、ControllerがHTTP入力と画面遷移、Serviceが計算・業務処理を担当する。ブラウザー側の二重送信防止だけに依存して副作用の重複を許可しない。
5. アップロードはToolIdに対応する`TOOL`＋`TOOL_INPUT`のポリシーをCommonから取得し、許可形式・実測容量を検証する。一時領域だけに保存し、正常・異常の双方で処理終了時に削除する。入力・結果のファイル内容をログへ残さない。
6. 実行結果をCommonの`IToolUsageLogger.WriteExecuteAsync(succeeded, ct)`で`WEB_EXECUTE`へ成功・失敗として一度記録する。ログ書込み失敗によって業務処理の成功を失敗へ変えない。
7. 画面結果がある場合は実行POSTの応答で結果画面を表示する。ファイル出力の場合は同じPOSTの応答でCSV/TSV等を直接ダウンロードさせる。出力にはCommonの区切りテキスト処理と数式対策を使い、結果・帳票を恒久保存しない。後から同じファイルを取得するための結果保管機構は初期テンプレートへ含めない。

入力画面と結果画面には、再送信や再実行の扱いを分かるように記載する。計算例は小さく副作用のないものにし、ツール固有のDB更新・外部通信・重い計算は複製後に個別設計する。長時間入力中も無条件でセッションを延長する独自処理は設けず、Commonの共有Cookie、有効期間60分のスライド更新と初回認証から最大8時間の上限に従う。

### 題材の隔離と残存の検出

生成したツールで、差し替える前提の題材が放置されたまま機能だけを足されることを防ぐ。注意書きでは防げないため、配置とビルドで検出する。

| 区分 | 置き場所 | 生成後の扱い |
| --- | --- | --- |
| 骨組み | `Program.cs`、`Bootstrap/ToolServiceExtensions.cs`、`Controllers/ToolController.cs`、`Views/_ViewImports.cshtml`、`Views/_ViewStart.cshtml`、`.csproj`、`Properties/launchSettings.json` | そのまま使う。ToolControllerは本体だけ自分の題材へ書き替える |
| 題材 | `TemplateExample/`配下の入力モデルとService、`Views/Tool/TemplateExample*.cshtml`、`wwwroot/css/site.css`の題材向け指定 | 削除し、自分の題材へ置き換える |

- 題材の型は`SalesSupport.<名称>.Web.TemplateExample`名前空間へ置き、骨組みの`Models`・`Services`フォルダーへ混ぜない。題材であることが型名とフォルダー名から分かるようにし、業務名に見える名前を付けない。
- `Controllers/ToolController.cs`は題材のServiceと入力モデルを参照する。題材を削除するとコンパイルが通らないため、Controllerの本体を書き替えずに放置できない。`WebOpenLoggingFilter`の適用、`WriteExecuteAsync`の記録単位、`IToolPageShell`の利用、CSRFとモデル検証の作法は骨組みとして残す。
- `.csproj`に`CheckTemplateExample`ターゲットを置き、`TemplateExample/**/*`または`Views/Tool/TemplateExample*.cshtml`が残っていればビルド時に通知する。Debugは警告とし、`standalone`のF5で動く教材としての価値を保つ。Releaseはエラーとし、[手動リリース](05_導入・運用.md#release)の`dotnet publish -c Release`で必ず止める。
- テンプレート自身は題材を持つことが目的のため、`.csproj`のプロパティ`TemplateExampleAllowed`を`true`としてターゲットを無効にする。生成スクリプトはこの値を`false`へ置き換え、生成したツールでだけ検出を有効にする。
- 生成したツールはテストプロジェクトを持たないため、この検出はビルドで行う。CIは初期対象外であり、検出をCIへ依存させない。開発者が`.csproj`からターゲットを外した場合は検出できない。完全な強制にはCIが必要であり、初期実装の対象外とする。

## 3. ToolIdからの新規ツール生成

- 利用者の入口はWindowsの`.bat`とし、コピー、テキスト置換、検証はPowerShellで行う。元の`template.slnx`とテンプレートのソースを変更せず、新しい場所へ生成する。
- ToolIdを一度入力すれば、定めた命名規則から生成先フォルダー、`.slnx`、プロジェクト名、名前空間、設定内ToolId、URL例を導出する。C#識別子に使えないToolIdの文字、長さ、予約値`SYSTEM`、生成先の既存ファイル、別ToolIdとの名称衝突は生成前に検出する。
- 任意の文字列を全面置換せず、専用プレースホルダーと置換対象の一覧を管理する。生成後はプレースホルダー、旧テンプレート名、旧ToolIdの残存、`.slnx`と`ProjectReference`のパスを検査し、`restore`・`build`で確かめる。生成したツールはテストプロジェクトを持たないため、生成物に`test`は実行しない。失敗した生成物を完成品として扱わない。
- 置換対象に`.csproj`の`TemplateExampleAllowed`を含め、生成したツールでは`false`にする。生成直後は題材が残っているため、生成後の確認ビルドはDebugで行い、Releaseでは確認しない。生成したREADMEには題材の削除手順と、残したままReleaseビルドが止まることを記載する。
- スクリプトはDB、IIS、証明書、環境変数、本番配置先を自動変更しない。接続先、鍵・保存先、ツールマスタと起動URL、アップロードポリシー、IISアプリケーションとプールは[導入・運用](05_導入・運用.md)に沿って別途準備する。

### 命名規則と生成先

ToolIdをハイフンと下線で区切り、各語の先頭だけを大文字にして連結した名称`<名称>`を導出する。例：`T001`は`T001`、`TOOL_001`は`Tool001`、`DMY-WEB`は`DmyWeb`。

| 生成物 | 名称 |
| --- | --- |
| ソリューション | `SalesSupport/<名称>.slnx` |
| プロジェクト・ルート名前空間 | `SalesSupport/src/<名称>/SalesSupport.<名称>.Web` |
| Portalからの起動URL例 | `/tools/<ToolId>/app` |

ToolIdはソースへ書かず、ローカル起動用の`launchSettings.json`と生成したREADMEにだけ記載する。配置環境ではIISの環境変数で与える。スクリプトの使い方、置換対象および検査項目は[生成スクリプトのREADME](../SalesSupport/scripts/README.md)に従う。

## 4. サンプル専用の開発データ

- サンプルをPortalから参照・起動できるよう、開発専用DBにWebツールのマスタ行と起動URLを登録する。アップロード実演用に当該ToolIdの`TOOL_INPUT`ポリシーと許可拡張子も登録する。
- ツール固有のテスト用テーブルは**1表だけ**とする。この表でEF Coreによる検索・登録・更新・集計と同時更新検出を実演する。入力ファイル本体や生成ファイルをこの表へ恒久保存しない。表名・列・サンプル値は第6節と開発専用SQLに従う。
- サンプルのツール行、ポリシー、テスト表とそのデータを作るSQLは開発専用として分離し、接続先・環境指定とDBの開発用許可標識を確認してから手動適用する。本番の初期DDL・マスタSQLへ混ぜず、アプリ起動時にも自動適用しない。投入・再実行・清掃は[サンプルSQLの手順](../SalesSupport/sql/sample/README.md)に従う。
- IdentityユーザーをSQLで作らない。DBを使う開発用ユーザーはPortalのIdentity API（開発限定の`add-test-user`・`import-test-users`）を使う。連携モードの開発確認では認証・認可・公開状態・アップロードポリシーを省略しない。第2節の単独開発では認証ユーザーや仮ユーザーを作らず、アップロードポリシーを固定値で代用しない。

## 5. Common変更と確認項目

- まず既存Commonを使用する。サンプルとテンプレートで同じ必須組込みが重複し、既存APIでは安全に表現できない場合だけCommonの追加を検討する。ツール固有Entity、業務ロジック、全ツール共通の汎用RepositoryはCommonへ移さない。
- 検証では、生成スクリプトの改名漏れ・衝突・再実行、各ソリューションのビルドとテスト、開発用SQLの本番拒否、Portal→ツールの共有Cookie往復、直接URL・API・ダウンロードの認可、ログの記録単位、アップロード境界と一時ファイル清掃を区別して確認する。
- 題材の検出は、生成したツールでDebugビルドが警告付きで通ること、Releaseビルドがエラーで止まること、題材だけを削除するとゲートは発火しなくなるが骨組みがコンパイルエラーになること、骨組みを自分の題材へ書き替えるとDebug・Releaseとも警告・エラーなく通ることを確認する。テンプレート自身では`TemplateExampleAllowed`によりDebug・Releaseとも止まらないことを確認する。
- 要求パイプラインの結合テストは、実際のProgram.csを`WebApplicationFactory`で起動する形でテンプレートのテストプロジェクトに置く。連携モードで未認証の画面要求がPortalのログインへ誘導されること、単独開発でCSRFトークンのない更新要求が400になり、トークンを付けた要求はControllerへ届くことを、DB・Portal・SMTPなしで確認する。Commonの振る舞いの確認でありホスト1つで足りるため、同じ内容をサンプルへ複製しない。ヘッダーの値などCommonが持つ値はツール側のテストで固定しない。テストから参照する`Program`は.NET 10のWeb SDKが公開クラスとして自動生成するため、ツールの`Program.cs`へ`public partial class Program;`を宣言しない。
- 実DB、IIS、SMTP、複数アプリのCookie往復を実施していない段階では結合検証済みと報告しない。Common変更時はPortalと利用する各ツールへの影響も検証する。

## 6. サンプル固有の仕様

サンプル固有の値は以下のとおりとする。テンプレートの題材は差し替え前提であり、この値を他ツールの恒久仕様にはしない。

| 項目 | サンプルでの値 |
| --- | --- |
| ToolId・URL | `SAMPLE-ESTIMATE`、`/tools/SAMPLE-ESTIMATE/app`。初期状態は`PRIVATE` |
| 専用表 | `dbo.SampleEstimateRecords`の1表。案件ID、送信ID、所有者、案件名、適用日、区分、数量、単価、小計、割引額、合計、明細行数、共通監査5列。監査列はCommonの`ConfigureAuditColumns`へ`dbo`を指定して対応付け、ツール側へ書き写さない |
| 競合と重複 | 本人の案件だけを検索・更新。編集時はDBトリガーで加算する`UpdateCount`をEF Coreの同時更新トークンとして使い、別画面の更新を上書きしない。保存POSTはフォームごとの送信IDを一意索引で抑え、成功時は詳細GETへリダイレクトする |
| ファイル | `.tsv`、最大1,048,576バイト。Commonの一時保存を使い、非空行数だけを要約へ記録し、本体と出力を保存しない |
| 計算と出力 | 通常は小計=数量×単価、キャンペーンは小計の10%を円未満切捨てで割引。画面表示、TSV直接出力、要約保存の3択 |
| 検索・集計 | 適用日の開始・終了と区分で検索。件数と合計は該当全件、一覧は更新の新しい100件 |
| 初期データ | ADMIN所有の標準案件10万円とキャンペーン案件2万7千円の2件。IdentityユーザーはSQLでは作らない |

開発用SQLは`EnvironmentName=DEVELOPMENT`と`SalesSupport.AllowSampleData=1`のDB拡張プロパティ、接続中DBとスクリプトへ記入した期待DB名の一致をすべて要求する。適用・清掃手順は[サンプルSQLのREADME](../SalesSupport/sql/sample/README.md)を参照する。
