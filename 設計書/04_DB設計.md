## 1. DB基本方針

- SQL Server上に営業支援システム専用DBを用意する。
- アプリケーションのDB操作はEF Coreを基本とし、テーブルとエンティティの対応を定義する。構成は[アプリケーション構成](03_システム構成・開発標準.md#application-structure)に従う。
- Identity管理テーブルの更新はUserManager等を介して行う。初期構築・マスタ登録用のSQL運用は継続し、EF Coreの採用だけを理由に既存のDB制約・トリガー方針を変更しない。
- ポータルと各ツールは、営業支援システム共通のアプリケーション用DBユーザーで接続する。
- 営業支援システムに不要な他システムのDBへ直接アクセスしない。
- DBユーザーには必要最小限の権限のみ付与する。
- 現時点では検索・集計・ログ削除等の性能改善を目的とする追加インデックスを設けない。主キー・一意制約に伴うインデックスと、決定済みの重複禁止条件を保証する条件付き一意インデックスは維持する。同じ列構成のインデックスを重複追加しない。運用・検証で性能上の必要性が判明した場合に追加を検討する。
- 接続文字列や認証情報は各アプリケーションの設定からDependency Injection等で共通DLLへ渡し、Common.dll内へ埋め込まない。
- ポータルが所有・管理する業務・マスタテーブルには`portal`スキーマを使用する。ログ3テーブルは例外として`log`スキーマに配置する。ErrorCodesはログではなくマスタのため`portal`に配置する。
- 各ツール固有の業務テーブルおよび上記以外のテーブルは`dbo`スキーマを使用し、ツール単位のスキーマは設けない。
- `portal`スキーマはテーブルを整理・識別しやすくするために使用し、DB権限の分離には使用しない。ポータルと各ツールは共通のアプリケーション用DBユーザーで必要なテーブルへアクセスする。
- 本資料では可読性のためテーブル名のスキーマ表記を省略する場合があるが、実際のDDL・SQL・EF Coreのマッピングでは対象に応じて`portal`、`log`または`dbo`を明示する。ログのスキーマ分離は整理目的とし、共通DBユーザーの接続方針は変更しない。

## 2. 共通テーブルカラム

Identity管理テーブルおよびToolUsageLogs・UserActivityLogs・SystemErrorLogsを除くすべてのシステムテーブルに次の共通監査列を設ける。個別テーブルの項目一覧には、これらの共通監査列を記載しない。

| 項目 | 内容 |
| --- | --- |
| UpdateCount | 更新回数。登録時は0とし、更新ごとに加算する |
| CreatedAt | 作成日時 |
| CreatedBy | 作成時のDBユーザー |
| UpdatedAt | 更新日時 |
| UpdatedBy | 更新時のDBユーザー |

- 共通監査列はDEFAULT制約またはDBトリガー等によりDB側で自動設定する。
- 共通監査列とトリガーは共通のDDLテンプレートから作成し、テーブルごとに個別仕様を持たせない。
- トリガーの共通動作はテンプレートに対する共通テストで確認する。
- アプリケーションの内部ユーザーIDをDBセッションへ受け渡して監査列へ設定する仕組みは設けない。
- アプリケーション上の送信者、担当者、修正担当者等、業務上必要なユーザー情報は各テーブルの業務項目として保持する。
- 日時・監査列の型は[暫定仕様](#physical-columns)に従う。DBユーザー名の取得方法およびトリガーの共通化方法は詳細設計で決定する。
- `AspNetUsers`、`AspNetUserClaims`、`AspNetUserLogins`および`AspNetUserTokens`はIdentity管理テーブルとし、共通監査列およびDBトリガーの対象外とする。

## 3. ユーザーデータ

- ユーザーごとにシステム内部で一意の内部ユーザーIDを付与する。
- 内部ユーザーIDは、メールアドレスや表示名が変更されても変更しない。
- ASP.NET Core IdentityのUserManagerを使用してユーザー情報と認証情報を登録・更新する。
- Identityのロール系テーブルは作成せず、権限はAspNetUsers.RoleCodeで管理する。
- Identity管理テーブルとして`AspNetUsers`、`AspNetUserClaims`、`AspNetUserLogins`および`AspNetUserTokens`の4テーブルを使用する。

### ユーザーテーブル（AspNetUsers）

| 項目 | 内容 |
| --- | --- |
| UserId | `uniqueidentifier`型の内部ユーザーID。IdentityのIdプロパティをこの物理列へ割り当てる |
| UserName | ログイン名。メールアドレスと同じ値を設定する |
| NormalizedUserName | Identityが使用する正規化済みログイン名 |
| Email | ログインおよび通知に使用するメールアドレス |
| NormalizedEmail | Identityが検索と重複確認に使用する正規化済みメールアドレス |
| EmailConfirmed | メールアドレス確認済みフラグ |
| PasswordHash | Identityが生成するパスワードハッシュ。初回設定前はNULL |
| SecurityStamp | 認証情報変更時に更新するセキュリティスタンプ |
| ConcurrencyStamp | Identityが同時更新検出に使用する値 |
| PhoneNumber | Identity標準の電話番号。初期機能では使用しない |
| PhoneNumberConfirmed | Identity標準の電話番号確認済みフラグ。初期機能では使用しない |
| TwoFactorEnabled | Identity標準の二要素認証フラグ。初期機能では使用しない |
| LockoutEnd | 一時ロックの終了日時。手動解除時はNULL。ロック中かは現在時刻との比較で判定 |
| LockoutEnabled | ログイン失敗による自動ロックの対象か。初期値は有効 |
| AccessFailedCount | 連続ログイン失敗回数。管理者によるロック解除時は0へリセット |
| DisplayName | 画面表示用の氏名 |
| RoleCode | USERまたはADMIN。表示名称はCodeMasterのUSER_ROLEから取得する |
| IsActive | ユーザーの有効・無効 |
| LastAccessAt | 最終利用日時。未利用の場合はNULL |

- ApplicationUserは`IdentityUser<Guid>`を継承し、IdプロパティをAspNetUsers.UserIdへマッピングする。
- UserIdには`DEFAULT NEWSEQUENTIALID()`を設定し、UserManagerによる登録時にSQL Server側で生成する。
- UserNameとEmailには同じメールアドレスを設定する。
- NormalizedUserNameおよびNormalizedEmailはUserManagerにより設定し、それぞれに一意制約を設ける。
- 初回パスワード設定が完了するまでPasswordHashはNULL、EmailConfirmedは無効とする。
- 初回パスワード設定完了時にPasswordHashを保存し、EmailConfirmedを有効とする。
- RoleCodeはUSERまたはADMINだけを許可する。
- IsActiveの初期値は有効とする。
- 初期段階では一般ユーザーとシステム管理者の二種類とし、独立した権限マスタおよびIdentityのロール系テーブルは設けない。表示名称だけをCodeMasterで共通管理する。
- LastAccessAtの更新タイミングは[ログ・最終利用日時の仕様](02_画面・機能設計.md#logs-usage)に従う。

### ユーザークレームテーブル（AspNetUserClaims）

| 項目 | 内容 |
| --- | --- |
| Id | クレームを識別するID |
| UserId | AspNetUsers.UserIdへの外部キー |
| ClaimType | クレームの種類 |
| ClaimValue | クレームの値 |

- Identity標準構成として作成する。
- 初期段階の権限はAspNetUsers.RoleCodeで管理するため、個別権限の保存には使用しない。

### 外部ログインテーブル（AspNetUserLogins）

| 項目 | 内容 |
| --- | --- |
| LoginProvider | 外部ログインプロバイダー名 |
| ProviderKey | 外部プロバイダー側の識別子 |
| ProviderDisplayName | 外部ログインの表示名 |
| UserId | AspNetUsers.UserIdへの外部キー |

- LoginProviderとProviderKeyを複合主キーとする。
- 初期段階では外部認証を使用しないため、レコードは登録しない。

### ユーザートークンテーブル（AspNetUserTokens）

| 項目 | 内容 |
| --- | --- |
| UserId | AspNetUsers.UserIdへの外部キー |
| LoginProvider | トークンのプロバイダー名 |
| Name | トークン名 |
| Value | トークン値 |

- UserId、LoginProviderおよびNameを複合主キーとする。
- Identity標準のトークン保存領域として作成する。
- 初回設定・再設定の最新発行番号は、LoginProviderをポータルの設定リンク用途として固定し、Nameを用途別に分けてValueへ保持する。設定完了時に対応する番号を消費し、再発行時に上書きする。発行履歴は保持しない。
- 再設定メール要求の最終受付時刻も、別のNameで保持する。5分間隔の受付判定と時刻更新を原子的に行う。Valueの形式・固定名、Identityとの同一トランザクション・同時使用防止の具体方式は詳細設計で定める。

### ユーザー設定テーブル（UserPreferences）

| 項目 | 内容 |
| --- | --- |
| UserId | 内部ユーザーID。主キー兼AspNetUsers.UserIdへの外部キー |
| SystemNoticeMailEnabled | システムお知らせメールの受信要否 |
| FavoriteToolNoticeMailEnabled | お気に入りツールお知らせメールの受信要否 |

- AspNetUsersと一対一で保持する。
- 通知設定の初期値はいずれも有効とする。

### お気に入りテーブル（UserToolFavorites）

| 項目 | 内容 |
| --- | --- |
| UserId | 内部ユーザーID |
| ToolId | ツールID |

- UserIdとToolIdの組み合わせを複合主キーとする。
- 同一ユーザーが同一ツールを重複登録できないようにする。
- AspNetUsersおよびToolsへの外部キーを設定する。
- ツールが非公開となった場合もレコードを削除しない。

- 初期ユーザーのTSV項目・検証・登録処理は[一括登録仕様](02_画面・機能設計.md#bulk-registration)を参照する。
- ユーザー無効化・権限変更時の動作とSecurityStampの更新は[認証構成](03_システム構成・開発標準.md#authentication)を参照する。

## 4. ツール管理データ

### ツール分類マスタ（ToolCategories）

| 項目 | 内容 |
| --- | --- |
| CategoryId | 分類を識別するID |
| CategoryName | 一覧に表示するカテゴリ名 |
| SortOrder | 分類の表示順 |

### ツールマスタ（Tools）

| 項目 | 内容 |
| --- | --- |
| ToolId | ツールを識別するID |
| CategoryId | 所属する分類ID |
| ToolName | ツール名 |
| ToolSummary | ツール概要 |
| Remarks | ツール詳細に表示する利用者向け備考 |
| OwnerUserId | 担当者となるシステム管理者の内部ユーザーID。NOT NULL、portal.AspNetUsers.UserIdへの外部キー |
| ToolType | DESKTOP、WEBまたはDOCUMENT。CodeMasterのTOOL_TYPEに対応する提供種別コード |
| WebAppUrl | Webツールの起動URL。WEBのみ最大1件で、新規ツール登録時に設定する。未登録状態、DESKTOPおよびDOCUMENTではNULL |
| Status | CodeMasterのTOOL_STATUSに対応するコード値。一般公開、限定公開、非公開 |
| SortOrder | 分類内の表示順 |

- バージョンおよび更新日はツールマスタへ重複して保持せず、現在のバージョンとして手動選択されたツール履歴から取得する。
- WEBは新規登録時にWebAppUrlを設定する。WebAppUrlのNULL可は維持する。配布アプリ・URL未登録を理由とする通常更新・状態変更の禁止は設けない。保存条件は[ツール管理](02_画面・機能設計.md#tool-admin)に従う。
- DOCUMENTは関連資料だけを提供し、WebAppUrlおよびAPPファイルを持たない。StatusをPUBLICへ変更する際はREFERENCEが1件以上存在することをサービス層で検証する。
- 新規ツールは所定SQL等の手動運用で登録し、Statusは非公開（HIDDEN）を明示的に設定する。DBのDEFAULTだけに初期状態を依存させない。登録手順は[マスタ更新方針](05_導入・運用.md#master-data)を参照する。
- OwnerUserIdには、有効かつRoleCodeがADMINのユーザーだけを設定できるようにする。
- Tools.OwnerUserIdにはNOT NULL制約と外部キー制約を設け、担当者の削除を連鎖させない。新規ツールの直接登録時にも担当者を必須とする。
- 外部キーとNOT NULLはユーザーの存在を保証するが、有効状態や管理者権限は保証しない。担当者の無効化・降格前に別の有効な管理者へ担当を引き継ぐことを[運用手順](05_導入・運用.md#master-data)で保証する。

### ツール履歴（ToolVersionHistories）

| 項目 | 内容 |
| --- | --- |
| ToolHistoryId | ツール履歴を識別するID |
| ToolId | 対象ツールID |
| Version | バージョン |
| ModifiedByUserId | 修正担当者の内部ユーザーID |
| ChangeDescription | 更新内容 |
| ReleasedAt | バージョン更新日 |
| IsCurrent | 管理者が一覧・概要へ表示する現在のバージョンとして選択した履歴かを示すフラグ |

- 一つのツールに対してIsCurrentを設定できる履歴は最大一件とする。バージョン更新情報欄で管理者が手動選択し、保存時にトランザクションと条件付き一意制約で複数選択を防ぐ。新規履歴はIsCurrent=falseとし、自動選択しない。
- 現在のバージョンはIsCurrentで判定する。「最新」の順位はVersionをピリオド区切りの数値として比較した降順とし、文字列比較やReleasedAtでは判定しない。
- 履歴は登録・編集できる。削除はバージョン番号が最大かつIsCurrent=falseの履歴だけに許可し、サーバー側で再確認する。ただし履歴が1件だけの場合は削除を許可しない。履歴の編集・削除、現在のバージョンの変更は同時更新と競合を検出する。削除による自動付替えは行わない。
- IsCurrentが未選択または履歴0件でもTools.Statusを一般公開へ変更できる。利用者向けの`Ver.1.0.0`は表示層の補完値であり、ToolVersionHistoriesへの自動追加やIsCurrentの自動更新は行わない。
- 履歴と配布ファイルの更新は独立した操作とし、ファイルとの対応は管理者が確認する。履歴編集・削除によるファイル変更は行わない。
- ToolIdとVersionの組み合わせに一意制約を設定する。

### ツールファイル（ToolFiles）

配布アプリと関連資料を同じテーブルで管理する。従来案のToolResourcesは本テーブルへ置き換え、Web起動URLはTools.WebAppUrlへ分離する。

| 項目 | 内容 |
| --- | --- |
| FileId | ファイルを識別する主キー。差し替え時も維持する。検討時のReferenceIDに相当 |
| ToolId | 所属ツールID。Toolsへの外部キー |
| FileCategory | APP：配布アプリ、REFERENCE：関連資料。登録後の区分変更は不可 |
| DisplayName | 利用者へ表示する名称。操作マニュアル、計算根拠、過去の実績等 |
| OriginalFileName | アップロード時の元ファイル名。安全なダウンロードファイル名の生成に使用 |
| RelativePath | 専用保存領域からの相対パス。システムが生成する |
| Extension | 拡張子。先頭のドットを含む小文字として保持 |
| FileSizeBytes | ファイル容量（バイト） |
| SortOrder | 関連資料の表示順。APPでは0とする |

- ToolIdごとのREFERENCEは複数登録可能。APPは最大1件とし、条件付き一意制約で重複を防ぐ。
- APPはDESKTOPツールにだけ登録できる。WEBおよびDOCUMENTには登録できない。REFERENCEはすべての提供種別に登録できる。
- FileCategoryはAPPまたはREFERENCEのみを許可する。許可値とツール種別との整合性を検証する。
- RelativePathは一意とし、URLや任意の絶対パスを格納しない。保存先の構成と取得処理は[ファイル管理](03_システム構成・開発標準.md#temporary-files)を参照する。
- 差し替え時は同じFileIdのファイル名・パス・拡張子・容量等を更新する。配布アプリの更新はバージョン履歴およびIsCurrentの更新と独立して確定する。ファイルの保存・参照更新・旧ファイル削除の手順はファイル管理の規定に従う。
- REFERENCEは管理画面からレコードと実ファイルを削除できる。APPの削除操作および個別ファイルのIsEnabled列は設けない。
- 旧版の世代管理テーブルは設けず、最新版だけを参照する。総容量・使用量の集計管理は設けない。FileSizeBytesは個別ファイルの属性として保持する。
- 登録操作、許可拡張子・容量の初期値、表示順は[ツール管理画面](02_画面・機能設計.md#tool-admin)を参照する。実行時の許可拡張子・容量は[ファイル制限テーブル](#upload-policies)から取得する。
- ツール状態による利用可否は[共通利用制御](02_画面・機能設計.md#access-control)に従う。

## 5. お知らせデータ

### お知らせテーブル（Notices）

| 項目 | 内容 |
| --- | --- |
| NoticeId | お知らせID |
| NoticeType | SYSTEMまたはTOOL |
| ToolId | ツールお知らせの場合の対象ツールID。システムお知らせの場合はNULL |
| Title | タイトル |
| Content | お知らせ内容 |
| IsPublished | 公開フラグ。初期値は非公開 |
| MailSentAt | 最終送信成功日時。成功歴がない場合はNULL。再送失敗時は以前の値を維持 |

- システムお知らせとツールお知らせを一つのNoticesテーブルで管理する。
- NoticeTypeがSYSTEMの場合はToolIdをNULL、TOOLの場合はToolIdを必須とするDB制約を設ける。
- お知らせを非公開にしてもレコードを削除しない。

- チェックボックスで選択したお知らせを手動送信する。サイト管理ではシステムのお知らせの選択分を1通、ツール編集ではそのツールの選択分を1通へまとめる。複数ツールを横断して選択しない。成功したグループの全お知らせのMailSentAtを同じ日時へ更新する。
- 自動再送は行わず、手動再送は許可する。送信試行済み列は追加しない。公開範囲・通知対象・送信操作は[お知らせ共通仕様](02_画面・機能設計.md#notices)を正とする。

## 6. FAQデータ

### FAQカテゴリマスタ（FaqCategories）

| 項目 | 内容 |
| --- | --- |
| CategoryId | FAQカテゴリを識別するID |
| CategoryName | FAQ画面に表示するカテゴリ名 |
| SortOrder | カテゴリの表示順 |

### FAQテーブル（FaqItems）

| 項目 | 内容 |
| --- | --- |
| FaqId | FAQを識別するID |
| CategoryId | 所属するFAQカテゴリID |
| Question | 質問内容 |
| Answer | 回答内容 |
| SortOrder | カテゴリ内の表示順 |
| IsPublished | FAQを一般ユーザーへ表示するかを示すフラグ |

- 画面上は質問と回答を二段で表示するが、DB上は一つのFAQを一レコードとして保持する。
- 質問と回答を`QorA`で別レコードに分割しない。
- 同一カテゴリ内では、FAQのソート順が重複しないようにする。
- 利用マニュアルPDFのURLはDBで管理せず、利用マニュアル・FAQ画面にサイト内相対URLとして記載する。
- 登録・更新方法は[マスタ更新方針](05_導入・運用.md#master-data)、表示仕様は[利用マニュアル・FAQ画面](02_画面・機能設計.md#manual-faq)を参照する。

## 7. 問い合わせデータ

### 問い合わせテーブル（Inquiries）

| 項目 | 内容 |
| --- | --- |
| InquiryId | 主キー兼、画面とメールに表示する問い合わせID |
| CategoryCode | CodeMasterのINQUIRY_CATEGORYに対応するコード値。質問、要望、意見、不具合報告、その他 |
| TargetType | システム、ツール、その他 |
| ToolId | 対象がツールの場合のツールID。その他の場合はNULL |
| SubmittedByUserId | 問い合わせを送信した内部ユーザーID |
| Content | 問い合わせ内容 |
| Status | CodeMasterのINQUIRY_STATUSに対応するコード値。要対応、対応中、検討中、完了、対応不要。初期値は要対応 |
| AssigneeUserId | 担当者の内部ユーザーID。未割当を許可する |
| AdminNote | 管理者用備考 |

- 表示専用の問い合わせ番号や別の内部IDは設けず、InquiryIdを主キー兼問い合わせ番号として使用する。
- AssigneeUserIdには、有効かつRoleCodeがADMINのユーザーだけを設定できるようにする。
- 添付ファイルの内容、ファイル名および保存先はDBへ保持しない。
- 添付ファイル用テーブルは設けない。

- メール送信失敗時は該当するInquiriesレコードを削除し、失敗したInquiryIdは欠番として再利用しない。削除失敗への追加対処は設けない。一覧プレビューはContentから生成し、専用列は追加しない。
- 管理者はCategoryCode、TargetTypeおよびToolIdを問い合わせ管理画面から更新できる。変更前の値をInquiriesや専用履歴テーブルへ保持せず、変更操作はUserActivityLogsへ記録する。対象変更による通知メールの再送およびAssigneeUserIdの自動変更は行わない。
- 初期担当者の設定、送信処理および管理操作は[問い合わせ管理](02_画面・機能設計.md#inquiry-admin)と[問い合わせ送信処理](02_画面・機能設計.md#inquiries)を参照する。

## 8. ログテーブル

- 物理名は`log.ToolUsageLogs`、`log.UserActivityLogs`、`log.SystemErrorLogs`とする。EF Coreのマッピング、DDL、保持期間による削除、TSV集計・出力もこのスキーマを使用する。

| テーブル | 用途 |
| --- | --- |
| ToolUsageLogs | デスクトップツールのダウンロード要求、Webツール起動、Webツール計算実行 |
| UserActivityLogs | 認証・認可イベントおよびアプリケーションを介した主要なユーザー操作 |
| SystemErrorLogs | ポータル、共通API、各Webツールのシステムエラー |

### ToolUsageLogs

利用状況集計の元データを追記する。

| カラム | SQL Server型 | NULL | 内容 |
| --- | --- | --- | --- |
| ToolUsageLogId | bigint IDENTITY(1,1) | 不可 | 主キー |
| ToolId | varchar(20) | 不可 | 対象ツール |
| UserId | uniqueidentifier | 不可 | 利用ユーザー |
| OccurredAt | datetime2(3) | 不可 | 発生日時 |
| EventType | varchar(30) | 不可 | イベント種別 |
| ResultCode | varchar(20) | 不可 | 処理結果 |
| CorrelationId | uniqueidentifier | 可 | 一連の処理を追跡するID |

- EventTypeはDESKTOP_DOWNLOAD、WEB_OPEN、WEB_EXECUTEとする。
- ResultCodeはSUCCESS、FAILUREとする。各許可値はCHECK制約で保証する。

### UserActivityLogs

認証・認可およびアプリケーションを介した主要なユーザー操作に関する履歴を追記する。

| カラム | SQL Server型 | NULL | 内容 |
| --- | --- | --- | --- |
| UserActivityLogId | bigint IDENTITY(1,1) | 不可 | 主キー |
| UserId | uniqueidentifier | 可 | 特定できた場合のユーザー |
| OccurredAt | datetime2(3) | 不可 | 発生日時 |
| EventType | varchar(50) | 不可 | 認証・認可または操作イベント |
| ResultCode | varchar(20) | 不可 | 処理結果 |
| FailureReason | varchar(50) | 可 | 失敗・拒否理由コード |
| RequestPath | nvarchar(500) | 可 | 対象URLのパス |
| OperationTargetType | varchar(30) | 可 | 管理操作の対象種別。問い合わせ分類変更ではINQUIRY |
| OperationTargetId | varchar(100) | 可 | 管理操作の対象ID。問い合わせ分類変更ではInquiryId |
| OperationDetails | nvarchar(1000) | 可 | 記録を許可した変更項目と変更前後のコード値 |
| IpAddress | varchar(45) | 可 | 接続元IP |
| CorrelationId | uniqueidentifier | 可 | 相関ID |

- ユーザーを特定できないログイン失敗等ではUserIdをNULLとし、入力されたメールアドレスを代わりに保存しない。
- 記録対象はログイン成功・失敗、アカウントロック、ログアウト、アクセス拒否、およびアプリケーションを介したユーザー、ツール、お知らせ、バージョン、関連資料、問い合わせ、通知設定、お気に入り、メール送信、表示順変更、ロック解除等の主要操作とする。問い合わせ分類変更のEventTypeはINQUIRY_CLASSIFICATION_UPDATEとし、結果はResultCodeで記録する。その他のEventType、ResultCode、FailureReasonの具体的なコード値・組合せは詳細設計で定める。
- 問い合わせ分類変更ではOperationTargetTypeにINQUIRY、OperationTargetIdにInquiryId、OperationDetailsにカテゴリ・対象の変更前後のコード値だけを記録する。問い合わせ本文、管理者用備考、表示名、メールアドレス等はOperationDetailsへ記録しない。
- 認証・認可イベントではOperationTargetType、OperationTargetIdおよびOperationDetailsをNULLとする。管理操作以外でこれらの列を汎用的な入力内容の保存先として使用しない。
- パスワード、トークン、接続文字列、問い合わせ本文、管理者用備考、表示名、メールアドレス、ファイル内容等はOperationDetailsへ記録しない。最終利用日時、ログイン失敗回数等の自動更新、ログ自身、定期保守および一時データの変更は対象外とする。直接SQLによる変更は本テーブルで捕捉せず、運用作業記録で管理する。

### SystemErrorLogs

共通エラーおよびツール固有エラーの調査情報を追記する。

| カラム | SQL Server型 | NULL | 内容 |
| --- | --- | --- | --- |
| SystemErrorLogId | bigint IDENTITY(1,1) | 不可 | 主キー |
| ErrorId | uniqueidentifier | 不可 | 発生したエラー1件を識別する問い合わせ用番号 |
| ErrorCode | varchar(100) | 可 | ErrorCodesの文言を識別するコード。コードを特定できない標準例外ではNULL可 |
| OccurredAt | datetime2(3) | 不可 | エラー発生日時 |
| ApplicationName | varchar(100) | 不可 | Portal / CommonApi / Tool001等 |
| ToolId | varchar(20) | 可 | 実際にエラーが発生した対象ツール。共通エラーコードの所属とは別 |
| UserId | uniqueidentifier | 可 | 発生ユーザー |
| ErrorLevel | varchar(20) | 不可 | ERROR / CRITICAL等 |
| ErrorType | nvarchar(300) | 可 | 例外型 |
| ErrorMessage | nvarchar(2000) | 不可 | 発生時点のマスタ文言＋開発者が指定した関連情報 |
| StackTrace | nvarchar(max) | 可 | スタックトレース |
| RequestPath | nvarchar(500) | 可 | 発生したURLパス |
| HttpMethod | varchar(10) | 可 | GET / POST等 |
| CorrelationId | uniqueidentifier | 可 | 一連の処理を追跡するID |

- ErrorIdは発生ごとに生成し、一意制約を設定する。同じErrorCodeのエラーが複数発生してもErrorIdは異なる。
- ErrorIdは共通エラー画面を表示するエラーで利用者へ表示する。メール送信失敗でも生成するが、問い合わせの受付失敗は専用の受付文言で表示し、それ以外のメール失敗は画面表示しない。
- ErrorCodeは検索用に値を保存し、マスタ未登録・取得失敗時にもログを残せるようErrorCodesへの外部キー制約は設けない。
- ErrorMessageは取得時点の文言を保存する。後からマスタを変更しても過去のログは変更しない。
- 文字数上限を超える調査情報は安全に切り詰め、ログ記録を失敗させない。具体的な整形・切詰め方法は詳細設計で定める。

### ログ共通ルール

- 上記3テーブルには共通監査列とその更新トリガーを設けない。通常処理は追記のみとし、保持期間に従う定期削除は別に行う。
- 日時はUTC保存、画面・メール・運用出力はJST表示とする。
- ToolUsageLogs・UserActivityLogs・SystemErrorLogsの3テーブルには外部キー制約を設けない。UserId・ToolId・ErrorCode等は記録時点の識別値として保持し、参照先の変更・削除をログへ連鎖させない。既定の主キー・一意制約・CHECK制約は維持する。性能改善用の追加インデックスは現時点では設けず、第1節の方針に従う。
- RequestPathはクエリ文字列を含めない。パス中の認証トークン等も記録対象から除く。
- CorrelationIdは一連の処理で共通のGUIDを使用する。ErrorIdや各ログの主キーとは別の役割とし、相関対象がない場合はNULLを許可する。

- 内部ユーザーID、ツールID、発生日時、イベント種別、処理結果等を記録する。
- 必要に応じて相関IDを付与する。
- システムエラーログはSQL ServerのSystemErrorLogsテーブルに記録する。
- ファイルログやWindowsイベントログへの二重記録は行わない。
- DB接続障害等によってSystemErrorLogsへ書き込めない場合の代替ログは、費用対効果を考慮して初期実装には設けない。
- ツール別利用者数はToolUsageLogsをToolId単位で集計し、対象となるUserIdの重複を除く。DESKTOPはDESKTOP_DOWNLOADの全件、WEBはWEB_EXECUTEかつSUCCESSだけを対象とする。詳細は[ログ出力仕様](02_画面・機能設計.md#logs-usage)を正とする。
- 初期段階では集計専用テーブルを設けず、ToolUsageLogsから都度集計する。
- ToolUsageLogs・UserActivityLogs・SystemErrorLogsの明細は、選択したテーブルについてDBに残る全列・全件をTSV出力する。見出しはカラム名、列順は本節の列定義順とする。ToolUsageLogsのツール別利用者数は、対象イベントをToolId単位で集計してUserIdの重複を除き、ToolName・UserCountを出力する。
- 全期間集計・全明細出力・保持期間による削除にも、現時点では性能改善用のインデックスを追加しない。運用・検証で必要性が判明した場合に見直す。

- 保持期間と定期削除の対象は[要件定義](01_要件定義.md#retention)に集約する。
- 記録方法は[共通ログ実装](03_システム構成・開発標準.md#logging)、集計・出力は[ログ記録・ログ管理画面・TSV出力](02_画面・機能設計.md#logs-usage)を参照する。

## 9. 汎用コードマスタ（CodeMaster）

小規模な選択肢の表示名称、並び順および表示色を、一つのコードマスタで共通管理する。

| 項目 | 内容 |
| --- | --- |
| CodeType | コード区分。例：TOOL_STATUS、SITE_STATUS |
| CodeValue | 区分内で一意のコード値 |
| CodeName | 画面に表示する名称。汎用的なValue列ではなく、用途が分かる名称とする |
| SortOrder | コード区分内の表示順 |
| ColorCode | バッジ背景色。varchar(7)、#RRGGBB形式。色が不要な場合はNULL |

- CodeTypeとCodeValueの組み合わせを複合主キーとする。
- コード値は原則として変更・再利用せず、名称や並び順の変更と区別する。
- ColorCodeには有効な#RRGGBB形式だけを許可し、任意のCSS文字列は保持しない。
- 表示名称と色から権限や動作を判定しない。状態・権限等のコード値はC#側でも定数等で定義し、対応する処理を実装する。
- コード行の追加だけで新しい状態遷移や権限が有効になる構成にはしない。
- ツール分類マスタ（ToolCategories）およびFAQカテゴリマスタ（FaqCategories）は、個別マスタを維持する。
- 参照先はCodeValue単独ではなくCodeTypeとの組み合わせで特定する。DB制約を含む参照整合性の具体方式は詳細設計で決定する。

### 共通管理するコード区分

| CodeType | 対象 | 利用箇所 |
| --- | --- | --- |
| TOOL_STATUS | 一般公開、限定公開、非公開 | Tools.Status |
| SITE_STATUS | Public公開、Private公開 | SystemSettingsのSITE＋PUBLICATION_STATUS |
| TOOL_TYPE | デスクトップ、Web | Tools.ToolType |
| INQUIRY_CATEGORY | 質問、要望、意見、不具合報告、その他 | Inquiries.CategoryCode |
| INQUIRY_STATUS | 要対応、対応中、検討中、完了、対応不要 | Inquiries.Status |
| USER_ROLE | 一般ユーザー、システム管理者 | AspNetUsers.RoleCodeの表示名称 |

### 状態コード・表示色の初期設定案

| CodeType | CodeValue | CodeName | SortOrder | ColorCode |
| --- | --- | --- | --- | --- |
| TOOL_STATUS | PUBLIC | 一般公開 | 10 | #2E7D32 |
| TOOL_STATUS | PRIVATE | 限定公開 | 20 | #EADFFF |
| TOOL_STATUS | HIDDEN | 非公開 | 30 | #616161 |
| SITE_STATUS | PUBLIC | Public公開 | 10 | #2E7D32 |
| SITE_STATUS | PRIVATE | Private公開 | 20 | #6A1B9A |
- 上記の色は初期設定案であり、表示の読みやすさを確認して調整できる。

- 更新手順は[マスタ更新方針](05_導入・運用.md#master-data)、取得・描画処理は[共通UI](03_システム構成・開発標準.md#ui)を参照する。

## 10. システム設定（SystemSettings）

設定項目ごとに1レコードを保持する汎用設定テーブルとし、portalスキーマに配置する。固定ID・固定の公開状態列・案内文列は設けない。

| カラム | SQL Server型 | NULL | 内容 |
| --- | --- | --- | --- |
| SettingCategory | varchar(50) | 不可 | 設定区分 |
| SettingKey | varchar(50) | 不可 | 区分内の設定キー |
| SettingName | nvarchar(100) | 不可 | 管理用の名称 |
| SettingValue | nvarchar(2000) | 可 | 設定値。日付も文字列で保存 |
| Description | nvarchar(1000) | 可 | 用途・注意事項 |

- SettingCategory＋SettingKeyを複合主キーとし、自動採番は行わない。共通監査列とUpdateCountを適用する。
- 設定キーは変更・再利用せず、任意文字列の未入力はNULLとする。必須文字列は空文字・空白だけを許可しない。

| SettingCategory | SettingKey | SettingName | SettingValueの初期値・条件 |
| --- | --- | --- | --- |
| SITE | PUBLICATION_STATUS | サイト公開状態 | PRIVATE。PUBLICまたはPRIVATEのみ。NULL不可 |
| SITE | PRIVATE_MESSAGE | 入場制限時の案内文 | メンテナンス中です。NULLなら共通の既定文 |
| TEST | BUSINESS_DATE | テスト用業務日付 | NULL。指定時は実在する日付をYYYY-MM-DD形式で保存 |

- CodeMasterのSITE_STATUSは選択肢の表示名称・色を保持し、現在の状態はSITE＋PUBLICATION_STATUSのSettingValueへ保持する。
- 公開状態行の欠落・NULL・不正値・取得失敗時は入場を許可しない。PRIVATE_MESSAGEの欠落・NULLは既定文とする。案内文は未認証ユーザーにも表示するため機密情報を含めず、プレーンテキストとして扱う。
- TEST＋BUSINESS_DATEは開発環境の対応する業務処理だけで参照する。欠落・NULLなら実際のJST日付、不正な指定値は構成エラーとする。本番では参照せず実際のJST日付を使用する。
- テスト用日付は認証期限、ロック時間、ログ・監査日時、問い合わせIDの採番へ適用しない。環境区分・帯色は従来どおり設定ファイルで管理する。
- 設定は所定SQLで登録・変更し、キーごとの許可値・必須条件を検証する。公開状態の値はDBのCHECK制約でも保証する。画面・APIに設定更新機能は設けず、サイト管理はシステムのお知らせだけを扱う。ログイン前の任意の案内文の設定は追加しない。
- Commonが設定区分・キーから取得し、用途別に型変換・検証する。新しいキーの追加だけで機能を自動追加する構成にはしない。
- 運用は[サイト公開状態の変更](05_導入・運用.md#site-status-operation)と[マスタ運用](05_導入・運用.md#master-data)に従う。

## 11. エラーコードテーブル（ErrorCodes）

共通システムエラーとツール固有エラーの表示文言を管理する。portalスキーマに配置する。ログテーブルではないため、共通監査列を適用する。

| カラム | SQL Server型 | NULL | 内容 |
| --- | --- | --- | --- |
| ToolId | varchar(20) | 不可 | コードの所属。共通システムエラーには予約値SYSTEMを使用 |
| ErrorNo | int | 不可 | 所属内のエラー番号 |
| ErrorCode | varchar(100) | 不可 | 表示文言を識別する一意なコード |
| DisplayMessage | nvarchar(2000) | 不可 | 利用者向け表示文言 |
| ErrorLevel | varchar(20) | 不可 | ERROR / CRITICAL等の既定レベル |

- 主キーはToolIdとErrorNoの複合主キーとし、ErrorCodeに一意制約を設ける。
- ErrorNoは1〜99999とし、ツール用ErrorCodeはToolId、アンダースコア、5桁ゼロ埋めErrorNoから自動生成する。例：ToolId=T001、ErrorNo=1 → T001_00001。
- 共通システムエラーはToolId=SYSTEMで番号を管理し、既存の標準システムエラーコードをErrorCodeへそのまま登録する。標準コードの一覧・文言・番号の対応は初期マスタで定める。
- SYSTEMはコードの所属を表す予約値であり、Toolsへ架空のツールを登録しない。ErrorCodes.ToolIdにはToolsへの単純な外部キーを設けず、SYSTEM以外は所定の登録処理で実在ツールを検証する。
- ツール用コードの生成・形式検証は共通の登録SQL等へ集約し、手入力によるToolId・ErrorNoとの不一致を防ぐ。
- ツール固有コードと標準システムコードが衝突した場合は登録エラーとする。登録後はコードのキーを再利用・変更せず、文言・既定レベルの更新を基本とする。
- DisplayMessageはプレーンテキストとし、画面へはHTMLとして解釈させず表示する。ログ専用の関連情報はマスタ文言へ埋め込まない。
- SystemErrorLogs.ErrorIdは発生ごとのGUIDであり、本テーブルのErrorCode・ErrorNoと置き換えない。
- ErrorHandlingによる取得・画面表示・ログ生成は[共通ログ実装](03_システム構成・開発標準.md#logging)を参照する。


<a id="physical-columns"></a>

## 12. 物理列定義・採番の暫定仕様

以下は実装前の暫定定義とする。既定のログ・ErrorCodesの型と制約は維持する。個別Webツールの計算項目は対象外とする。

### 共通ルール

- 日本語の名称・文章はnvarchar、英数字コードはvarcharとする。外部キー列は参照先と型・長さを揃える。
- 任意文字列の未入力はNULLへ統一する。必須文字列はNOT NULLに加え、空文字・空白だけの値を許可しない。
- nvarcharの長さはUTF-16単位で扱い、画面・サーバー・DBの検証を揃える。
- 数値項目はすべて整数（小数0桁）。intは最大10桁、bigintは最大19桁の整数範囲内で保持し、表示桁数や固定桁コードとは区別する。現時点でdecimal列は設けない。
- フラグはbit、表示順・件数はint、ファイル容量はbigintとし、すべてNOT NULL。表示順・件数・容量は0以上とする。
- 日時はdatetime2(3)でUTC保存、表示はJSTとする。ReleasedAtはdate、IdentityのLockoutEndはdatetimeoffset(7)とする。
- 本文はプレーンテキストとする。nvarchar(max)の業務本文は上限10,000 UTF-16単位を入力検証とDB制約で保証する。Identity標準列・スタックトレースにはこの業務本文上限を適用しない。
- 既定済みの初期値は維持する。必須の名称・本文・分類等に不足値を補うDEFAULTは設けない。

### ID・採番

以下の主キー列はすべてNULL不可とする。

| 対象 | 型・採番 |
| --- | --- |
| AspNetUsers.UserId | uniqueidentifier、既定のDEFAULT NEWSEQUENTIALID()。UserManager登録時にDB生成 |
| Tools.ToolId | varchar(20)、管理者が登録SQLで手動指定。例T001。変更・再利用不可、SYSTEMは予約値 |
| ToolCategories.CategoryId／FaqCategories.CategoryId | 各テーブルでint IDENTITY(1,1) |
| ToolHistoryId／FileId／NoticeId／FaqId | 各テーブルでint IDENTITY(1,1) |
| AspNetUserClaims.Id | int IDENTITY(1,1) |
| Inquiries.InquiryId | char(12)、JST受付日YYYYMMDD＋日別連番4桁。例202609140001 |
| ログ3テーブルの主キー | 既定のbigint IDENTITY(1,1) |
| SystemErrorLogs.ErrorId | uniqueidentifier、発生ごとにアプリでGUID生成。一意制約 |
| CorrelationId | uniqueidentifier、相関処理開始時にアプリで生成し処理内で共有。相関対象なしはNULL可 |
| SystemSettings.SettingCategory＋SettingKey | varchar(50)＋varchar(50)の複合主キー。所定SQLで指定、自動採番なし |
| ErrorCodes.ErrorNo | 既定のint、1～99999。所属ごとに登録SQLで指定、IDENTITYなし |
| その他の複合主キー・主キー兼外部キー | 参照元の値を使用し、独自採番しない |

- 連番は欠番を許容し、削除済み番号を再利用しない。
- InquiryIdは毎日0001から開始し、年ではリセットしない。受付日は処理内で一度確定し、同時受付でも重複しないようDBトランザクションで日別採番を直列化する。採番管理の具体DDLは詳細設計で定め、単純なMAX+1だけで採番しない。
- 番号の確保は問い合わせレコードの保存とは別に確定する。問い合わせの保存が失敗・ロールバックしても確保済み番号を戻さず、欠番として再利用しない。保存失敗を理由とする自動再試行は設けない。利用者の新規送信時はその送信日の次の番号を採番する。
- 1日の採番上限は9,999件とし、保存失敗・メール失敗による欠番も消費済み番号に含める。上限到達後は受付エラーとする。別の表示番号は設けない。

## 13. ファイルアップロード制限

用途別の許可拡張子と1ファイルの容量上限を次の2テーブルで管理する。両テーブルはportalスキーマに配置し、第2節の共通監査列を適用する。以下の列型・採番は第12節と同じ暫定物理定義として扱う。

### FileUploadPolicies

| カラム | SQL Server型 | NULL | 内容 |
| --- | --- | --- | --- |
| PolicyId | int IDENTITY(1,1) | 不可 | 主キー |
| ScopeType | varchar(20) | 不可 | SITE：サイト共通、TOOL_COMMON：全ツール共通、TOOL：個別ツール |
| ToolId | varchar(20) | 可 | TOOLの場合だけ必須。Tools.ToolIdへの外部キー |
| PurposeCode | varchar(30) | 不可 | INQUIRY_ATTACHMENT、REFERENCE、APP、TOOL_INPUT |
| MaxFileSizeBytes | bigint | 不可 | 1ファイルの容量上限。0より大きい整数 |

- 初期の許可組合せはSITE＋INQUIRY_ATTACHMENT、TOOL_COMMON＋REFERENCE、TOOL_COMMON＋APP、TOOL＋TOOL_INPUTだけとする。CHECK制約でScopeType・PurposeCode・ToolIdの組合せを保証する。
- SITE・TOOL_COMMONではToolIdをNULLとし、ScopeType＋PurposeCodeを一意にする。TOOLではScopeType＋ToolId＋PurposeCodeを一意にする。条件付き一意インデックス等で保証する。
- 架空のサイト用ツールは作らない。個別ツール用ポリシーは実在ツールを参照し、ツール削除を連鎖させない。
- ツール別の参考資料・配布アプリの上書き設定、設定の優先順位やフォールバックは初期実装に設けない。

### FileUploadPolicyExtensions

| カラム | SQL Server型 | NULL | 内容 |
| --- | --- | --- | --- |
| PolicyId | int | 不可 | FileUploadPoliciesへの外部キー |
| Extension | varchar(20) | 不可 | 先頭ドット付きの小文字拡張子。例：.pdf |

- PolicyId＋Extensionを複合主キーとし、同じ拡張子の重複登録を防ぐ。独自採番は行わない。
- カンマ区切り・ワイルドカード・空文字は許可せず、1行に1拡張子を保持する。
- ポリシーと拡張子の登録・更新・削除は所定SQLで同一トランザクション内に行う。ポリシー削除時は拡張子を先に削除し、連鎖削除は設けない。
- ポリシー欠落、許可拡張子0件、不正設定、DB取得失敗時はアップロードを許可しない。

### 初期設定・適用範囲

| ScopeType | PurposeCode | ToolId | 容量・許可形式の初期値 |
| --- | --- | --- | --- |
| SITE | INQUIRY_ATTACHMENT | NULL | 10,000,000バイト。形式は[問い合わせ仕様](02_画面・機能設計.md#inquiries)。Excel・Wordの具体的な拡張子は残件 |
| TOOL_COMMON | REFERENCE | NULL | 100,000,000バイト。拡張子は[参考資料の初期設定](02_画面・機能設計.md#tool-admin) |
| TOOL_COMMON | APP | NULL | 500,000,000バイト。.zip、.msi、.exe |
| TOOL | TOOL_INPUT | 対象ツールID | ツール開発時に許可拡張子・容量を決定して登録 |

- 件数・保存期間・用途とツール種別の整合性は既存の業務ルールで検証する。問い合わせ添付1件、配布アプリはツールごとに最大1件、参考資料は複数という条件は本テーブルへ移さない。
- 設定の管理画面・更新APIは設けない。Commonによる取得・検証は[ファイル管理](03_システム構成・開発標準.md#temporary-files)、登録・変更は[マスタ運用](05_導入・運用.md#master-data)に従う。

### 共通の制約・更新削除方針

- 上記はON DELETE NO ACTION、ON UPDATE NO ACTIONとし、親の削除・キー変更を子へ連鎖させない。参照されている親の削除・キー変更は拒否する。Identity関連も同じ方針を明示的にマッピングする。
- NULL可の外部キーは値がある場合に参照先の存在を保証する。用途に応じた必須・NULLの切替は既定のCHECK制約・保存時検証を併用する。
- 有効状態・管理者権限は外部キーでは保証しない。担当者選択時の検証と、無効化・降格前の引継ぎは既定どおり維持する。過去の修正担当者・問い合わせ送信者は履歴として維持する。
- 子レコード自身の削除を禁止するものではない。参考資料の削除、メール失敗時の問い合わせ削除、お気に入り解除、ポリシー削除時の明細先行削除は既定の手順に従う。
- 外部キー列の型・長さは参照先と揃える。参照元列への性能改善用インデックスは追加しない。主キー・一意制約等に必要なものは第1節の方針に従う。
- 既存データへ制約を適用する場合は、孤立した参照がないことを確認し、既存行を含めて検証する。未検証の制約で済ませない。

### 対象外・残る設計

- log.ToolUsageLogs・log.UserActivityLogs・log.SystemErrorLogsには外部キーを設けない。
- ErrorCodes.ToolIdは予約値SYSTEMを含むためToolsへの外部キーを設けず、SYSTEM以外の実在ツール確認は既定の登録処理で行う。
- CodeMasterとのCodeType＋CodeValueによる参照整合性は別途詳細設計する。CodeValue単独への外部キーや、同名の列という理由だけの外部キーは追加しない。
- SystemSettingsのSettingValueと、ToolFiles.Extension等の保存済み属性を設定テーブルへ外部キーで結び付けない。設定値の検証・アップロード時の許可判定は既定のCommon・所定SQLで行う。
- 個別ツールの固有テーブルと日別採番管理の具体構造は対象外とし、定義時に関係を確定する。制約名・実際のDDL・EF Coreマッピングは実装時に具体化する。
