[資料一覧へ戻る](README.md)

システムの目的、対象範囲、利用者に提供する機能および品質上の条件を定義する。画面の詳細動作や実装手順は関連資料を参照する。

## 1. システム概要

### 1.1 目的

- 既存の営業支援用デスクトップツール群と、新たに開発するWebツールを一つのポータルへ集約する。
- 利用者がツールの実装方式を意識せず、同じサイトから必要なツールを利用できるようにする。
- 各ツールを独立したソリューションとして開発し、複数開発者による並行開発・保守を可能にする。
- 認証、ユーザー管理、ツール管理、お知らせ、通知、ログ、共通UI等はポータル側へ集約する。

### 1.2 想定利用規模

| 項目 | 想定 |
| --- | --- |
| 登録ユーザー数 | 約200名 |
| 同時利用ユーザー数 | 約5名 |
| 初期ツール数 | 約20ツール |
| 提供種別 | Webツール / デスクトップツール / 資料 |

### 1.3 初期対象外

- ツール単位の利用者権限管理
- ツール一覧のキーワード検索
- 利用状況集計のシステム内グラフ表示
- ポータル管理画面からのWebアプリケーション本体の配備
- 配布ファイルおよびマニュアルの旧版保存・世代管理、ファイル格納先の総容量・使用量管理
- 問い合わせメールへの一時添付とWebツールの処理用一時アップロードを除く、一般ユーザー向けファイルアップロードおよびファイルの恒久保存
- CI/CD
- ポータルおよび各ツールへのバックアップ機能実装
- 計算結果および帳票データの恒久保存
- 厳密なレスポンスタイムおよび可用性SLAの数値化

## 2. 機能要件

### 一般ユーザー向け機能

- メールアドレスとパスワードでログインし、ログアウトできる。
- メールの案内から初回パスワードを設定し、パスワードの変更・再設定ができる。
- パスワードを忘れた利用者は、自分で再設定用メールを請求できる。
- ユーザーの有効状態、権限、サイト公開状態およびツール状態に応じて利用を制限する。
- サイト公開状態はPublic公開とPrivate公開の2種類とし、Private公開ではシステム管理者だけが入場できる。
- ツール公開状態は一般公開、限定公開、非公開の3種類とする。一般公開は一般ユーザーとシステム管理者が参照・利用できる。限定公開は両者のツール一覧に薄いグレーと「限定公開」の名称で掲載し、一般ユーザーは詳細参照・利用不可、システム管理者は詳細参照・利用可能とする。非公開は両者の通常のツール一覧に表示せず、管理画面からの確認・編集だけを許可する。
- ポータルトップからツール一覧、サポートおよび権限に応じた管理機能へ移動できる。
- Webツール、デスクトップツールおよび資料提供型を区別せず、同じ一覧から探せる。
- ツールをお気に入りへ登録・解除し、自分のお気に入り一覧を利用できる。
- ツールの概要、備考、お知らせ、バージョン更新情報およびマニュアルを確認できる。
- 提供内容に応じてWebツールを使用し、デスクトップアプリケーションまたは関連資料を取得できる。資料提供型は関連資料だけを提供し、Web起動URLおよび配布アプリを持たない。
- システムお知らせと、お気に入りツールのお知らせのメール受信要否を設定できる。
- ポータルの利用マニュアルとFAQを同じ画面で確認できる。
- 問い合わせ・ご意見を送信でき、必要に応じて許可されたファイルをメールに添付できる。

### システム管理者向け機能

- サイト管理画面はシステムのお知らせの登録・更新・公開・メール送信に限定する。サイトのPublic公開・Private公開（限定公開）の切替と入場制限時の案内文の設定はDB運用で行い、サイト画面・APIからは変更できない。ログイン画面には初回利用案内と問い合わせ先を表示する。管理画面で任意のログイン案内を編集する機能は初期対象外とする。
- ユーザー管理から新規ユーザーのTSV取り込みを行い、検証・確認後に登録し、初回パスワード設定メールを送信する。詳細は[一括登録仕様](02_画面・機能設計.md#bulk-registration)による。
- ツールの基本情報、提供内容、バージョン、お知らせおよび状態を更新できる。バージョン履歴は編集可能とし、バージョン番号が最大の履歴だけ削除できる。ただし、現在のバージョンに選択中の履歴および最後の1件は削除できない。
- デスクトップアプリケーションはツールごとに最大1ファイルを保持し、提供内容から初回登録・差し替えできる。ファイル履歴と削除操作は設けず、切戻しは管理者が旧ファイルを手動で再アップロードする。バージョン履歴の登録・編集および現在のバージョンの選択は独立した手動操作とし、整合性は管理者が確認する。
- 新規ツールは管理画面から登録せず、所定の手動運用で非公開として登録する。現在のバージョン未選択や履歴0件を一般公開の禁止条件にはせず、表示データがない場合は画面上だけ`Ver.1.0.0`を補完表示する。
- すべての提供種別に関連資料を複数登録し、表示名の指定、差し替え、削除および並べ替えができる。関連資料にはテンプレート、申請書、マニュアル、計算根拠、過去の実績等を含める。資料提供型を一般公開する場合は関連資料を1件以上必須とする。
- システム・ツールのお知らせを登録・編集・公開し、明示的な操作でメール送信できる。
- ユーザーの追加、情報変更、無効化およびパスワード再設定案内ができる。登録後の権限変更はDB運用で行い、管理者はユーザー管理画面からログイン失敗によるロックを解除できる。30分経過によるロック満了も維持する。
- ユーザーの最終利用日時を確認できる。
- 問い合わせ一覧で問い合わせIDの完全一致検索、管理者用備考の部分一致検索、条件の絞り込み、本文のプレビュー確認、担当者・ステータス・備考の更新ができる。詳細画面では本文全体を表示し、同じ管理項目を更新できる。
- 管理者はログ管理画面でログ種別を選択し、ログ3種類の全列・全件明細をTSV出力できる。ツール利用ログでは抽出内容として明細またはツール別利用者数を選択できる。検索・その他の絞り込みは設けない。集計条件は[ログ出力仕様](02_画面・機能設計.md#logs-usage)に従う。
- 初期ユーザーをTSVから一括登録し、初回パスワード設定リンクをメールで案内できる。

### システム自動機能

- ツール利用履歴、ユーザーアクセスログ、システムエラーログを区別して記録する。
- ログイン失敗が規定回数に達したユーザーを一定時間ロックする。
- 問い合わせの登録後に、送信者と対象に応じた担当者へメールを送信する。
- メール送信失敗はシステムエラーログへ記録し、自動再送は行わない。問い合わせは失敗時にレコードを削除して受付失敗を表示し、利用者による新規送信を許可する。レコード削除失敗への追加対処は設けない。お知らせと初回設定・再設定メールは失敗表示を行わず、お知らせの手動再送と設定リンクの新規再発行は既定の条件で許可する。詳細は[メール送信ルール](02_画面・機能設計.md)に従う。
- 管理者が送信を指示したお知らせを、通知設定に応じた利用者へ送信する。
- 通常処理終了時に一時ファイルを破棄する。保持期間を超えたログはサーバーの定期タスクで削除し、異常終了後の残存ファイルは保守時の確認・清掃で対応する。

状態別の利用可否、画面項目、入力制限、送信条件および失敗時の動作は、[画面・機能設計](02_画面・機能設計.md)で定義する。

## 3. 非機能要件

### セキュリティ

- 設計判断の優先順は「実装・運用を軽くする → 利用者の利便性 → 追加のセキュリティ強化」とする。一般公開せず、重要度の高い個人情報を扱わない前提とするが、認証・権限確認、総当たりや過剰リクエストへの基本対策は維持する。
- 標準機能と既存のIIS・ネットワーク運用を優先し、独自の攻撃検知基盤や高度な防御機能を初期実装へ追加しない。非公開という前提はネットワークの到達制御で確認する。
- 総当たり対策はアカウントロックと接続元単位の試行制限を組み合わせる。DoSによる影響は要求頻度・サイズ・同時処理数等の上限で軽減し、大規模な回線飽和を伴う攻撃はアプリ単独の保証対象としない。

- HTTPSを使用し、未認証ユーザーから通常機能へのアクセスを制限する。
- 管理機能はシステム管理者のみ利用可能とする。
- サイト・ツールの状態と権限をサーバー側で確認し、直接URL、APIおよび保護対象ファイルからも制限を回避できないようにする。
- 認証・パスワード管理には標準機能を使用し、独自の暗号処理を実装しない。
- パスワードや認証トークン等の機密情報を不必要に表示・出力しない。
- DBユーザーには必要最小限の権限のみ付与する。
- 接続文字列やパスワード等をソースコードへ直接記述しない。
- SQLインジェクション、XSS、CSRFへの対策を実施する。
- 管理者のアップロード、問い合わせ添付およびWebツールの処理用一時アップロードは、用途別のファイル制限テーブルから許可拡張子・1ファイル当たりの最大容量を取得し、Commonでサーバー側検証を行う。設定がない場合や取得できない場合は許可しない。制限設定の変更は所定SQLで行い、管理画面は設けない。

認証の実装、Cookie、トークンおよび鍵の取扱いは、[認証構成](03_システム構成・開発標準.md#authentication)を参照する。

### 対応クライアント

- 会社支給のWindows端末を対象とする。
- 会社標準のMicrosoft Edgeを対応ブラウザとする。

### 可用性・性能

- 登録ユーザー約200名、同時利用約5名を前提とする。
- 大規模な分散システムやオートスケーリングは前提としない。
- 保守性と運用のしやすさを優先する。
- 画面ごとの厳密なレスポンスタイムは定義しない。
- 通常操作に支障がないことを検証環境で確認する。
- 長時間計算、大量データ処理、大容量帳票生成はツール単位で要件を定める。

### 共通エラー処理

- 本番環境では、例外の詳細およびスタックトレースを画面へ表示しない。
- 利用者には共通エラー画面と問い合わせ用の識別番号を表示する。
- 問い合わせ用の識別番号をシステムエラーログへ記録する。
- ポータルおよび各Webツールで共通のエラー表示形式を使用する。
- 共通システムエラーおよびツール固有エラーの表示文言をエラーコードテーブルで管理する。文言を識別するエラーコードと、発生したログ1件を識別する問い合わせ番号は区別する。

### 障害分離

- 一つのWebツールの障害によって、ポータルや他のWebツールを停止させない。
- サイトへの入場が許可されている場合は、ツール停止中もポータルを利用できる構成とする。一覧・詳細・お知らせの参照にはツール公開状態に応じた制御を適用する。
- Webツールごとに独立して停止、更新、再起動できる構成とする。
- メール送信の失敗によって、お知らせの登録・更新を失敗させない。
- 共通API障害時の影響範囲を設計工程で明確にする。

### 保守性・拡張性

- ポータルと各ツールを個別のソリューションに分割する。
- ツール単位で改修、テスト、リリースできる構成とする。
- 共通処理は共通APIまたは共通ライブラリとして提供する。
- 各ツールの実装方式を可能な限り統一する。
- ツール開発用の標準テンプレートとサンプルツールを用意する。

<a id="retention"></a>

### データ・ログ保持

- 計算結果および帳票データは原則としてシステム側へ保持しない。
- 問い合わせの添付ファイルはメール送信時だけ一時保存し、恒久保存しない。
- 計算結果、帳票内容、パスワード、接続文字列、認証情報をログへ記録しない。
- 入力内容のログ記録範囲は共通要件として一律に確定せず保留とし、各ツール開発者がツールの仕様として判断する。エラーログへ追加する関連情報は開発者が指定できるが、上記の機密情報等の記録禁止は引き続き適用する。
- ツール利用履歴は原則として削除せず保持する。
- ユーザーアクセスログは6か月間保持する。
- システムエラーログは6か月間保持する。
- 保持期間を超えたユーザーアクセスログおよびシステムエラーログは定期削除する。

<a id="theme"></a>

### 環境識別・画面テーマ

- 開発環境と本番環境は設定ファイルの値によって判定する。
- 環境の判定をビルド構成、URLまたは利用者の選択だけに依存させない。
- 画面上部の帯は、本番環境では青、開発環境では彩度と明度を抑えた落ち着いた赤を既定色とする。
- 利用者に環境区分を意識させないため、帯に「本番環境」「開発環境」等の環境名は表示しない。
- 本文領域には社内システム統一テーマを固定して適用し、テーマを切り替える設定は設けない。
- 開発環境では赤い帯、本番環境では青い帯を固定表示する。
- ポータルおよび各Webツールで同じ環境判定と帯の表示ルールを使用する。
- 最上部の帯は画面スクロール時も上部へ固定し、各メニューとそのドロップダウンは文字数によらず同じ幅で表示する。
- 利用者ごとのテーマ選択およびダークモード等は対象外とする。
- サイト公開状態、ツール状態等の業務上の状態を表示する場合は、色だけで表現せず表示名称を併記する。ただし、サイト入場制限案内画面では一般ユーザーに公開状態の名称を表示せず、案内文を表示する。環境区分を示す帯も表示名称の併記対象外とする。
- コードごとの表示色は、環境を示す帯の色および画面全体のテーマ設定とは分離する。
