| 領域 | 技術 |

### 開発上の留意事項

- 新規開発では.NET Frameworkではなく.NET 10 LTSを使用する。
- 社内で使用中のASP.NET、VB.NET、.NET Framework 4.7とは構成や開発方式が異なることに留意する。
- 開発開始前に標準テンプレート、サンプルツール、コーディング規約を用意する。
- Visual Studio Codeで使用するC#拡張機能の機能とライセンスを確認する。
- .NET SDKのバージョンを統一する。

## 2. 全体構成・責任分界

```text
営業支援ポータル
│
├─ Portal
│   ├─ 認証・ユーザー管理
│   ├─ ツール・お知らせ管理
│   ├─ サイト公開状態に基づく入場制御
│   ├─ お気に入り・通知
│   ├─ 問い合わせ・問い合わせ管理
│   └─ 共通API・共通UI
│
├─ Tool001
├─ Tool002
├─ Tool003
│   ...
└─ Tool020
```

### ポータル側の責務

- 認証・認可
- ユーザー管理
- ツール情報・状態管理
- サイト全体の公開状態に基づく入場制御と入場制限時の案内表示。公開状態・案内文の設定はDB運用に限定し、サイト画面・APIに設定の更新機能は設けない。
- サイト公開状態、ツール状態およびユーザー権限に基づく共通利用制御
- デスクトップアプリケーション配布
- マニュアル配布
- お気に入り
- システム・ツールのお知らせ
- メール通知
- 問い合わせ受付・問い合わせ管理
- デスクトップツールのダウンロード要求履歴の記録
- ログ記録と管理者向けのログ明細・ツール別利用者数のTSV出力
- 共通UI・共通API・共通ライブラリ
- ツールへの遷移

### 各ツール側の責務

- ツール固有画面
- 業務ロジック・計算処理
- 業務データの登録、更新、検索
- 帳票作成・ダウンロード
- ファイル生成
- ツール固有の入力チェックとエラー処理
- 共通DLLのメソッドを使用したWebツール起動・計算実行履歴の登録
- 共通の入口処理によるサイト公開状態・ツール状態・ユーザー権限の確認と直接URLアクセスの制御
- 使用した一時ファイルの削除

## 3. URL構成案

```text
https://sales-support/
├─ /                       ポータルトップ
├─ /tools                  ツール一覧
├─ /tools/favorites        お気に入りツール
├─ /tools/T001             Tool001詳細
├─ /tools/T001/app         Tool001 Webアプリ
├─ /support                サポート
├─ /support/inquiries      問い合わせ・ご意見
├─ /settings               個人設定
├─ /admin                  管理機能
├─ /admin/site             サイト管理（システムのお知らせ）
├─ /admin/tools            ツール選択
├─ /admin/tools/T001       ツール編集（お知らせ・バージョン・基本情報・提供内容）
└─ /admin/inquiries        問い合わせ管理
```

ポータルをIISの一つのサイトのルートアプリケーションとして登録し、各Webツールを同じサイト配下の個別アプリケーションとして登録する。利用者には同一ドメイン配下の一つのサイトとして提供する。

- インプロセスホスティングを使用し、ポータルと各Webツールへそれぞれ専用のアプリケーションプールを割り当てる。
- 各Webツールは別ソリューションの発行成果物を個別の物理フォルダーへ配置し、独立して停止・更新・再起動する。
- IIS登録とポータルへの提供URL登録は[配布・配置方針](05_導入・運用.md#deployment)に従う。

## 4. アプリケーション・ソリューション構成

```text
Controller
    ↓
Service
    ↓
EF Core（DbContext）
    ↓
SQL Server
```

- ControllerはHTTPリクエスト、画面遷移、入力受付を担当する。
- Serviceは計算処理等の業務ロジックを担当する。
- アプリケーションのDB操作はEF Coreを基本とし、ServiceからDbContextを直接利用する。
- 検索・結合・集計はLINQ、登録・更新・削除はEF Coreの機能で実装する。通常処理用のSQL実行共通ライブラリや汎用Repository層は設けない。
- 複雑な処理はまずEF Coreで表現し、SQLへの変換や性能に問題がある場合だけ、担当機能内でEF Core経由のパラメーター化SQL・ビュー・DB関数等の利用を検討する。
- DBの初期構築・マスタ登録・運用更新に使用するSQLスクリプトは、アプリケーションのDB操作方針とは別に扱う。
- Dependency Injectionを利用して各層を疎結合にする。

### ソリューション構成

```text
SalesSupport/
├─ .gitignore
├─ global.json
├─ SalesSupport.Common.slnx
├─ SalesSupport.Portal.slnx
├─ Tool001.slnx
├─ Tool002.slnx
└─ src/
   ├─ Common/
   │  └─ SalesSupport.Common/
   │     └─ SalesSupport.Common.csproj
   ├─ Portal/
   │  └─ SalesSupport.Portal.Web/
   │     └─ SalesSupport.Portal.Web.csproj
   ├─ Tool001/
   │  └─ <Tool001のプロジェクト>
   └─ Tool002/
      └─ <Tool002のプロジェクト>
```

- ソリューションファイルはXML形式の`.slnx`を使用し、リポジトリ直下に置く。
- `SalesSupport.Common.slnx`には`SalesSupport.Common`プロジェクトだけを登録する。
- `SalesSupport.Portal.slnx`には`SalesSupport.Common`と`SalesSupport.Portal.Web`を登録し、`SalesSupport.Portal.Web`から`SalesSupport.Common`への`ProjectReference`を設定する。
- 各ツールは個別の`.slnx`（例：`Tool001.slnx`）で管理する。ツールのソリューションには`SalesSupport.Common`と対象ツールのプロジェクトだけを登録し、依存方向は`対象ツール -> SalesSupport.Common`とする。
- ポータルおよび各ツールからCommonをソースプロジェクトとして直接参照する。Commonからポータルまたは各ツールを参照してはならない。
- `bin/`と`obj/`は生成物であり、ソース管理および構成例の対象外とする。
- 各ツールのソリューションを分離し、複数開発者が互いのツールへの影響を抑えて並行開発できる構成とする。

DbContext配置・トランザクションは[Common詳細設計](10_Common詳細設計.md)、DB変更管理の残件は[検討事項](06_検討事項.md#repository)を参照する。

## 5. 認証構成

- ASP.NET Core IdentityとCookie認証を使用する。
- ユーザークラスは`IdentityUser<Guid>`を継承した`ApplicationUser`とする。
- ロール系テーブルを使用せず、`IdentityUserContext<ApplicationUser, Guid>`を基礎とする。
- ログインIDにはメールアドレスを使用し、IdentityのUserNameにもメールアドレスを設定する。
- 表示用の氏名は独自列のDisplayNameへ保持する。
- 権限は独自列のRoleCodeでUSERまたはADMINを管理し、認証Cookieのロールクレームへ設定する。
- RoleCodeまたはIsActiveを変更した場合はSecurityStampを更新し、変更前の認証Cookieを継続利用できないようにする。
- ログイン、ログアウト、初回パスワード設定、パスワード変更およびパスワード再設定の画面はポータル側に設ける。
- 各Webツールはパスワードを取り扱わず、ポータルと共有する認証Cookieを検証する。
- ポータルと各Webツールで、認証スキーム、Cookie名、Cookieパス、Data Protectionのアプリケーション名およびキーストレージを共有する。
- Data ProtectionキーはIISの各対象アプリケーションプールから参照できる共通領域へ保存し、必要なアクセス権限だけを付与する。
- ユーザー情報の登録・更新、メールアドレス変更、パスワード再設定および管理者によるロック解除にはUserManagerを使用する。ロック解除はポータルの管理者専用処理とし、LockoutEndのクリアとAccessFailedCountのリセットを同一トランザクションで確定する。ConcurrencyStampによる競合検出を適用し、他のユーザー属性を上書きしない。
- 登録後のRoleCode変更だけは運用上の例外としてDBから行い、画面・管理APIに変更処理を設けない。変更時はSecurityStampとConcurrencyStampも更新し、既存Cookieの権限を継続利用させない。具体的な手順は[導入・運用](05_導入・運用.md#master-data)に従う。
- パスワードのハッシュ化・検証・ロック・再設定はIdentity標準機能を使用し、独自の暗号処理は実装しない。
- パスワード変更時はSecurityStampを更新し、既存セッションを無効化する。
- Identity管理テーブルの同時更新はConcurrencyStampで検出する。
- 管理者は利用者の現在のパスワードおよびパスワードハッシュを表示・取得できない。
- パスワードとパスワードハッシュを画面・メール本文・ログへ出力しない。
- 初回設定・再設定トークンは、設定リンクとしての受渡し以外に画面・メール本文へ表示せず、ログにも記録しない。
- 認証CookieはSecure・HttpOnlyを有効にし、非永続、SameSite=Lax、Path=/、Domain未指定（現在のホストのみ）とする。最大8時間・有効期間60分の標準スライド更新は画面仕様に従い、Cookieの有無だけで認証を許可しない。更新要求にはASP.NET Core標準のCSRF対策を適用し、GETでデータを更新しない。
- Cookieの有効期間は60分とし、対象の操作要求でASP.NET Core標準のスライド更新を使用する。最後の操作から厳密に60分の保証は求めない。初回認証時刻は保護された認証チケットへ保持し、更新時にも維持する。Commonで初回認証から最大8時間の上限を確認する。Portalと各ツールは同じCookieを共有し、最終操作時刻を同期する専用DBテーブルは設けない。静的ファイル取得・自動ポーリングを延長対象にしない。
- Common.Authenticationは認証設定、ログインユーザー取得、Cookie・有効状態・権限・SecurityStampの検証、サイト・ツールの利用制御を担当する。Portalはログイン・ログアウト・パスワード設定／再設定・ユーザー管理の画面と業務処理を担当し、Identity APIを使用する。各ツールはCommonの検証処理を組み込む。
- 未認証の画面要求はPortalのログイン画面へ案内し、ログイン後は検証済みのサイト内戻り先へ遷移する。API要求はリダイレクトによるHTML応答ではなく適切な未認証・権限不足応答を返す。
- 初回設定・再設定トークンには有効期限を設け、一回の設定完了で無効化する。
- 初回設定と通常の再設定はトークンの用途と有効期限を分け、期限は[画面・機能設計](02_画面・機能設計.md#login)に従う。初回設定用の長い期限を通常の再設定へ適用しない。
- 初回設定・再設定の最新発行番号をAspNetUserTokensへユーザー・用途別に保持する。Identityのトークン保護・期限検証と最新発行番号の照合を組み合わせ、再発行時に番号を更新する。設定完了時は番号を消費し、同じリンクの同時使用でも一度だけ完了するようパスワード更新と同一トランザクションで確定する。専用履歴テーブル・管理画面は設けない。
- ログインには接続元単位の試行制限を適用する。プロキシ経由では信頼できるプロキシの情報だけを使用して接続元を判定し、社内の共有接続元からの利用を考慮して閾値を定める。
- ログイン・再設定メール請求等の頻度制限にはASP.NET Coreの標準機能を優先する。計算・アップロード等は処理特性に応じて同時処理数・要求サイズ・タイムアウトを制限し、無制限に処理を待機させない。
- 接続元単位の制限はポータルのASP.NET Core標準レート制限をメモリ内・固定時間窓・待機キューなしで実施し、プロセス再起動によるカウント消失を許容する。初期値は[ログイン仕様](02_画面・機能設計.md#login)に従う。アカウント単位の失敗回数・ロックはIdentityのDB管理を維持する。
- 再設定メールのアカウント単位の間隔制限はAspNetUserTokensの最終受付時刻で管理し、並行要求でも一度だけ受付する。送信失敗でも受付時刻を戻さない。実際の発行処理はポータルへ集約する。
- サイト全体への過剰な通信はIIS・ネットワーク側の既存機能と分担し、アプリ内に独自のDoS検知・遮断基盤を構築しない。制限値は通常利用と既定のアップロード上限を満たすよう検証する。
- 単一Windowsサーバーを前提に、Data Protectionキーは配備フォルダー・Web公開領域外の共通フォルダーへPersistKeysToFileSystemで永続化し、ProtectKeysWithDpapi(protectToLocalMachine: true)でマシン単位に暗号化する。関係するIIS実行アカウントには鍵の参照・生成に必要な権限、運用管理者には管理権限を付与し、その他のアクセスを制限する。鍵の生成・ローテーションは標準機能へ任せ、利用中の旧鍵を手動削除しない。

画面動作は[ログイン・パスワード関連画面](02_画面・機能設計.md#login)、カラムと採番は[ユーザーデータ](04_DB設計.md#users)、未確定パラメーターは[検討事項](06_検討事項.md#identity)を参照する。

## 6. 共通利用制御の実装

- 限定公開ツールの一覧掲載可否と詳細・起動・取得可否は分けて判定する。一般ユーザーに一覧掲載を許可しても詳細等を許可しない。
- 判定ルールは[画面・機能設計の共通利用制御](02_画面・機能設計.md#access-control)を参照し、画面・ツールごとに独自の利用可否表を実装しない。
- 認証情報とユーザーの有効状態・権限を検証した後、SystemSettingsのサイト公開状態を確認し、入場可能な場合だけ個別ツールの状態を確認する。
- 保護対象の各リクエストでDBのIsActive・RoleCode・SecurityStampを取得し、Cookie内のSecurityStampと照合する。不一致・無効ユーザーは認証を拒否し、権限はDBの最新値で判定する。Identityの既定の定期検証間隔だけには依存しない。
- ユーザー状態・権限・SecurityStampとサイト・ツールの公開状態はリクエストをまたいでキャッシュしない。同一リクエスト内では取得結果を共有し、DB参照の重複を避ける。ブラウザーの画像・CSSキャッシュとは別に扱う。
- 各Webツールに共通処理を必ず組み込み、ポータルを経由しない直接URL、業務APIおよび保護対象ファイルの取得にも適用する。
- 直接入力・ブックマーク・共有リンクでも同じ共通利用制御を実行する。ポータル画面のクリック履歴やRefererヘッダーを認可条件にせず、認証情報と現在のユーザー・サイト・ツールの状態に基づいて判定する。
- IISでポータルサイト配下に登録したことだけでは認証・認可の適用済みと扱わない。各Webツールの入口とポータルのファイル取得経路で共通利用制御を実行する。
- ポータルのアプリケーションダウンロード要求および参考資料の配信にも同じ判定を適用する。
- 未認証で必要な経路の例外は画面・機能設計に従い、管理者向けの独自バイパスは設けない。
- 状態変更はログイン済みユーザーの次のリクエストにも反映し、既に実行中の処理の強制中断は行わない。
- 公開状態・ツール状態を取得できない場合、または未定義のコード値の場合は、制限を解除して処理を継続しない。
- DB上の表示名称や色ではなく、定義済みコード値と検証済みの権限を使って判定する。

## 7. 共通ライブラリの構成

クラス配置、公開メソッド、入出力、DI、Entity・DbContext、要求処理、エラー処理と検証計画は[Common詳細設計](10_Common詳細設計.md)を参照する。本節は責任分界と基本方針を定義する。

`SalesSupport.Common`は一つのクラスライブラリプロジェクトとし、次の構成要素を名前空間およびフォルダーで分離する。

| 構成要素 | 役割 |
| --- | --- |
| Configuration | 環境区分、保存先等の設定取得と設定値の検証 |
| MasterData | コードマスタの選択肢、表示名称、並び順、表示色の取得 |
| ErrorHandling | 例外の共通処理、利用者向けエラーへの変換、Loggingとの連携 |
| Mail | メール本文のテンプレート、宛先・添付の設定、送信処理 |
| DataExport | TSV・CSVの生成、文字コード・見出し・区切り文字の統一、数式解釈への対策 |
| HttpClients | HTTP API呼出し、タイムアウト設定、通信エラーの共通処理 |
| DateTime | 日時の取得、タイムゾーン変換、表示形式の統一 |
| Authentication | 認証情報の取得・検証と共通利用制御 |
| Logging | 利用履歴・アクセスログ・エラーログの共通記録 |
| FileStorage | 一時・永続ファイルの保存・読込・削除と、処理終了時の一時ファイル削除。残存ファイルの清掃は運用で実施 |
| UI | ヘッダー、ナビゲーション、テーマ、状態バッジ、共通エラー画面 |
| Validation | 共通入力検証 |
| Contracts | 共通API・共通メソッドの受渡し定義 |

- 上記の正式な名前空間は`SalesSupport.Common.Configuration`等の`SalesSupport.Common.<名称>`とする。初期構成では構成要素ごとのプロジェクト分割を行わない。
- 本資料群の`Common.dll`は`SalesSupport.Common`プロジェクトが生成する`SalesSupport.Common.dll`を指す。
- ポータルと各ツールは、同じリポジトリ内の`SalesSupport.Common.csproj`を`ProjectReference`で参照する。初期構成ではCommonをローカルNuGetパッケージとして参照しない。
- DateTime構成要素の型名はSystem.DateTimeと混同しない名前にする。
- DB接続設定はアプリケーションからDependency Injection等で渡し、Common.dllへ接続文字列や認証情報を埋め込まない。
- 配布時の更新・検証・発行手順は[手動リリース](05_導入・運用.md#release)に従う。
- 各機能の利用例を標準テンプレートまたはサンプルツールに含める。

### EF Coreと各機能の責務

- Commonに独自のDB操作基盤プロジェクトは設けず、接続管理・検索結果の型変換・変更追跡・保存にはEF Coreを使用する。
- Logging、MasterDataは共通機能として維持し、専用メソッドの内部でEF Coreを使用する。呼出元がログやコードマスタの検索・更新処理を重複実装しないようにする。
- EntityとDbContextはCommon、Portal、各ツールへ責務に応じて配置する。Commonには認証・マスタ・公開状態判定・ログ・ファイル制限など共通機能が必要とする定義、Portalには問い合わせ・お知らせ・FAQ・管理機能などの定義、各ツールには固有の業務定義を置く。Commonへ全テーブルのEntityを一括集約しない。
- 同じ業務テーブルを複数ツールが参照する場合、各ツールに必要な列を持つEntityとマッピングを定義してよい。主キー・列型・長さは実テーブルと一致させる。単純な参照の違いだけを理由にツール別SQLビューを必須としない。
- 共有テーブルのDDLと変更担当は一か所で管理し、各ツールから重複して作成・変更しない。スキーマ変更時は全参照元を確認する。同じテーブルを複数ツールが更新する場合は、業務検証と同時更新の規則を統一し、必要に応じて更新処理を共通化する。
- ツール固有テーブルのエンティティとDbContextは各ツール側に置き、Serviceから利用する。Commonに全ツールのテーブル定義を集めない。
- DbContextはアプリケーションのDIへ登録し、接続設定を外部設定から渡す。全ユーザーで単一のDbContextを共有せず、同じインスタンスで並列DB操作を実行しない。
- 複数操作を一括確定する範囲は業務処理側で決める。複数DbContextやIdentityをまたぐ更新のトランザクション方式は詳細設計で定める。
- DB生成の監査列とUpdateCountに合わせてEF Coreのマッピング・同時更新検出を設定する。
- Identity管理テーブルの更新は引き続きUserManager等のIdentity管理機能を使用し、一般のServiceから直接更新しない。
- ログ記録失敗時に再帰的なログ記録を行わない。

### 共通機能と業務ルールの分担

- Mailは送信の仕組みを担当し、通知対象の判定や送信タイミングはポータル側の業務処理で決定する。
- Mailは送信失敗をシステムエラーログへ記録し、成功・失敗・結果不明を呼出元が判定できる結果を返す。Mail自身は再送・画面表示を行わない。問い合わせのレコード削除・受付失敗表示・新規送信、お知らせの手動再送等はポータル側の業務処理で画面仕様に従って実施する。HttpClientsも副作用を伴う操作を無条件に再試行しない。
- DataExportはTSVの整形を担当し、ログ出力では値中の改行・タブを半角スペースへ置換して1レコード1行にする。数式対策は置換後の値へ適用する。ポータルのServiceでは明細取得と集計を分け、今後の集計方法を個別に追加できる構成とする。ログ管理用の管理者専用ダウンロード経路を設け、共通ユーザーAPIとは分離する。
- ErrorHandlingはエラーの変換・処理を担当し、画面への描画はUI、記録はLoggingが担当する。

## 9. ログ実装

- Webツール利用履歴の登録にはHTTP APIを設けず、Common.dllが提供する非同期メソッドを使用する。
- 共通メソッドは少なくともツールID、イベント種別、処理結果を受け取り、認証情報から内部ユーザーIDを補完してToolUsageLogsへ登録する。
- Webツール起動は各Webツールの共通入口処理から、計算実行は各ツールの処理完了箇所から共通メソッドを呼び出す。
- ポータル・各Webツールのシステムエラーログを登録する。
- ツール開発者が一行程度のメソッド呼び出しで記録できるようにする。
- ログ記録の失敗によって、Webツールの計算処理そのものを失敗扱いにしない。
- デスクトップツールのダウンロード要求はポータル側で記録する。
- ポータルはWebツールの利用履歴を生成せず、ToolUsageLogsの参照・集計だけを担当する。
- WEB_OPENは認可後にツールの入口画面を正常に開いた要求ごとに1件記録する。再読込・別タブも記録し、静的ファイル取得・ツール内部の画面遷移ごとには記録しない。WEB_EXECUTEは計算要求が成功・失敗で終了したときに1件、DESKTOP_DOWNLOADは認可された配布アプリのダウンロード要求時に1件記録する。起動履歴を利用人数と同一視せず、既定の利用者数集計を維持する。
- ユーザー操作ログは、ポータルの認証処理、ポータル・各Webツールの共通利用制御処理、およびアプリケーションを介した主要なデータ変更で記録する。対象にはユーザー、ツール、お知らせ、バージョン、関連資料、問い合わせ、通知設定、お気に入り、メール送信、表示順変更およびロック解除を含める。
- 問い合わせ分類変更の操作ログには問い合わせID、変更項目、変更前後のコード値、操作ユーザー、結果、発生日時を記録し、問い合わせ本文、管理者用備考、表示名、メールアドレス等は記録しない。ログ記録失敗で問い合わせ更新を失敗させず、ログ失敗を再帰的に記録しない。
- パスワード、トークン、接続文字列、問い合わせ本文、ファイル内容等の秘密情報・大量データは操作ログへ記録しない。最終利用日時や試行回数等の自動更新、ログ自身、定期保守、一時データは操作ログの対象外とする。DBへ直接行った変更はアプリケーションの操作ログでは捕捉せず、運用作業記録で管理する。
- デスクトップツールからログAPIを呼び出すことは求めない。
- Action Filterまたは簡単な共通メソッド呼び出しで記録できる構成とし、ツール開発者が個別にログ送信処理を作り込まない。
- 共通のイベント種別、処理結果、相関IDの形式を使用する。
- 計算結果はログへ保存しない。入力内容の記録範囲は[データ・ログ保持方針](01_要件定義.md#retention)に従い、ツール開発者の判断事項とする。

### ErrorHandlingとエラーコードの連携

- ErrorHandlingはToolIdとErrorNoの組合せ、またはErrorCodeを受け取り、ErrorCodesから表示文言・既定エラーレベルを取得する。両方を指定して不一致になるAPIは設けない。具体的なメソッド名・型は共通契約の詳細設計で定める。
- 共通エラーとツール固有エラーを同じ処理で扱う。コードの所属ToolIdと、実際に処理していたツールのToolIdは別の情報として扱う。
- エラー発生ごとにErrorIdを生成し、取得した文言とErrorIdを画面表示用に返す。画面の描画はUI、ログの書込みはLoggingが担当する。
- ツール開発者はコードに加え、ログ専用の関連情報と必要に応じて例外を渡せる。関連情報は画面表示文言へ追加しない。
- ログのErrorMessageには発生時点のマスタ文言と関連情報を結合して記録する。例：`入力ファイルを処理できませんでした。[処理段階：入力検証][行番号：12]`。`(取得した文言)[入力データ：テスト０１]`という形式も構成できるが、入力値を含めるかはツール開発者の判断事項とする。
- 例外情報・関連情報からパスワード、認証トークン、接続文字列等を除去し、列の上限に収まる形へ整形する。ログの関連情報から画面表示文言を生成しない。
- コード未登録・文言取得失敗時はコード内に用意した共通文言を使用する。取得できた範囲のエラーコード・例外情報でログ記録を試み、マスタ取得失敗による再帰的なエラー処理を行わない。
- ログ記録に失敗しても再帰的な記録・代替ログは行わない。画面表示用の共通文言はDBなしでも返せるようにする。
- メール送信失敗はログ記録経路を使用し、ErrorHandlingから再送処理を起動しない。問い合わせの受付失敗表示はポータル側の業務処理で行う。お知らせ・設定リンクメールの失敗表示禁止は維持する。

記録イベントとTSV出力は[ログ記録・ログ管理画面・TSV出力](02_画面・機能設計.md#logs-usage)、保存先と集計元は[ログテーブル](04_DB設計.md#logs)、保持期間は[要件定義](01_要件定義.md#retention)を参照する。

## 10. 環境設定・共通UI

### 設定の配置

- DB接続、環境区分、一時・永続ファイルのルート保存先、SMTP接続、From／Reply-To、開発用送信先、Portalの公開URL、共有認証・Data Protection設定、アプリ名・ToolId、通信タイムアウト・要求上限・信頼するプロキシは設定ファイルまたは配置環境から渡す。値は環境構築時に設定できるようにし、必須値の欠落・不正は起動時に検出する。
- 環境によらず固定するCookie名・認証スキーム等はCommonの定数として統一してよい。変更が必要な項目だけ外部設定にする。DB・SMTPの秘密情報やData Protectionキーをソース管理へ含めない。
- サイト公開状態・案内文・テスト用業務日付はSystemSettings、表示名・順序・色はCodeMaster、エラー文言はErrorCodesで管理する。アップロード容量はFileUploadPolicies、許可拡張子はFileUploadPolicyExtensionsで管理し、汎用設定テーブルや設定ファイルへ重複保持しない。

### 共通UI

- Common.DateTimeは実際の時刻とテスト用業務日付を別の取得処理にする。開発環境の対応業務処理だけがTEST＋BUSINESS_DATEを参照し、欠落・NULLなら実際のJST日付、不正値なら構成エラーとする。本番では設定を参照しない。認証期限・ロック・ログ・監査日時・問い合わせ番号は常に実際の時刻を使用する。

- 環境識別・本文テーマの見た目は[要件定義](01_要件定義.md#theme)を参照する。
- 環境区分はWeb.configから渡す専用設定`Portal__EnvironmentCode`の`PRODUCTION`または`DEVELOPMENT`とし、共通設定クラスから参照する。未設定または許可値以外は起動時の構成エラーとし、ASP.NET Coreの実行環境名やURLから推測しない。
- 環境区分は利用者が画面から変更できないようにする。
- 本文には社内システム統一テーマを固定して適用し、テーマ切替用の設定は設けない。
- 環境判定、固定テーマの適用および帯表示は共通UIへ実装し、ポータルと各Webツールで再利用する。
- 利用者別テーマ選択とダークモードは対象外とする。
- 本番環境は青、開発環境は長時間表示しても刺激が強くならないよう彩度と明度を抑えた赤の帯を表示し、帯の中や周辺に環境名を示す文字は表示しない。共通UIの開発環境初期色は濃色`#7f3f46`から淡色`#a85b61`のグラデーションとする。
- 独自CSSで背景色や文字色を固定せず、Bootstrapのテーマ機能とCSS変数を優先して使用する。
- 単一のSalesSupport.CommonプロジェクトをMVCのViewsを扱えるRazor Class Library構成へ変更し、共通C#処理とUIを同じプロジェクトで提供する。既存プロジェクトの削除・再作成は不要とし、名前・ProjectReferenceを維持してSDK等の設定を変更する。
- 共通レイアウト、ヘッダー、フッター、ナビゲーション、Bootstrap設定、エラー画面、CSS・JavaScriptをCommonで提供する。Portalと各ツールは共通レイアウトを使用し、画面本文・タイトル・パンくず等を渡す。配置先のサブパスを考慮してURLを生成する。
- 共通ヘッダーにはトップへのリンク、ツール一覧、サポート、権限に応じた管理者用画面のドロップダウンおよびユーザーメニューを配置する。ドロップダウンはマウス操作だけに依存せず、クリックとキーボードでも操作できるようにする。
- 共通ヘッダーは画面上部へ固定し、各メニュー項目とドロップダウンは文字数によらず同じ幅とする。
- パンくずリストは共通ヘッダー直下かつ画面タイトルの上に配置し、下層画面へトップ画面と同じメニューカードを重複配置しない。
- CodeMasterのCodeNameとColorCodeを使用して状態等の共通バッジを描画し、各画面で名称や色を重複定義しない。
- ColorCodeはバッジ背景色に使用し、初期色はモックを優先する。固定CSSでマスタ値を上書きしない。文字色は背景色に応じて白／濃色を選ぶ。未設定の場合は画面側の標準表示を使用する。
- 背景と文字の読みやすさを確保し、色だけでなく表示名称も併記する。
- コードごとの色は、環境帯や本文テーマとは分離する。
- CodeMasterの取得は共通メソッドを使用し、値の形式と初期設定は[コードマスタ](04_DB設計.md#code-master)を参照する。

## 11. ファイル管理・一時ファイル取扱い制約

### 共通ファイル管理

- SalesSupport.Common.FileStorageを使用し、一時ファイルと永続ファイルの保存・読込・削除を共通化する。
- 保存時に一時・永続の区分を明示し、保存領域を分離する。処理終了時の自動削除は一時ファイルだけを対象とする。アプリに期限切れファイルの定期削除機能は設けず、残存ファイルは保守時に確認・清掃する。
- 永続ファイルは配布アプリケーションやマニュアル等、各機能の仕様で保存が認められたファイルを対象とし、更新・削除は各機能の操作と保存方針に従う。
- 保存先はアプリケーションの設定から渡す。ファイル操作は指定された保存領域内に限定し、利用者が任意の物理パスを指定できないようにする。
- ファイルの利用権限は呼出元で共通利用制御に従って確認する。
- 永続ファイル対応によって、処理結果・帳票データ・問い合わせ添付の保存期間を変更しない。

### アップロード制限の取得・検証

- SalesSupport.Common.FileStorageにポリシー取得・アップロード検証を集約し、EF CoreでFileUploadPoliciesとFileUploadPolicyExtensionsを参照する。新しいCommonプロジェクトや専用HTTP APIは追加しない。
- 用途と必要な場合のToolIdを渡し、許可拡張子一覧とMaxFileSizeBytesをまとめて返す。例：GetAsync(InquiryAttachment)、GetAsync(Reference, toolId)、GetAsync(App, toolId)、GetAsync(ToolInput, toolId)。具体的な公開型・メソッド名は詳細設計で定める。
- TSVユーザー取込はSITE＋USER_IMPORT、問い合わせ添付はSITE＋INQUIRY_ATTACHMENT、参考資料・配布アプリはTOOL_COMMON、処理用入力はTOOLの該当設定を取得する。参考資料・配布アプリではToolIdを渡しても個別設定へ切り替えず、対象ツール・用途の検証に使用する。
- 用途とToolIdはサーバー側の処理・認可済みの対象から決定し、利用者が指定するPolicyIdや拡張子一覧で制限を切り替えない。
- 画面の許可形式・容量の案内と、保存前のサーバー側検証は同じ設定取得処理を使用する。ファイル名の最終拡張子を小文字化して完全一致で照合し、実際のファイル容量を検証する。ブラウザー側の制限だけで許可しない。
- アップロード要求ごとにDBから現行設定を取得し、同一要求内で共有する。リクエスト間キャッシュは初期実装に設けない。設定欠落・不正・拡張子0件・取得失敗時はアップロードを拒否する。
- 件数、認証・公開状態、APPがDESKTOP専用であること、保存期間・清掃は各機能の既定ルールを維持する。

- 許可拡張子はDB設定だけから取得し、.xls・.html・.htmの固定禁止を設けない。HTML参考資料はContent-Disposition: attachmentで返し、ブラウザー内での表示・実行用に配信しない。複数ファイル構成はZIPとして扱う。

### 配布アプリ・参考資料の保存と取得

- メタデータは[ToolFiles](04_DB設計.md#tools)、登録操作・拡張子・容量の初期値は[提供内容](02_画面・機能設計.md#tool-admin)を正とする。
- 実ファイルはWeb公開フォルダー・アプリケーション配置フォルダーの外の専用保存領域へ格納する。
- DBには保存領域を基準とした相対パスを保持する。例：`Site/Tool1/Files/(FileId)/システム生成ファイル名.pdf`。これはWeb公開URLではない。
- FileIdと物理ファイル名をシステムで生成し、差し替え時はFileIdを維持して新しい物理ファイル名を使用する。元のファイル名は表示・ダウンロード用として別に保持する。
- 取得要求はFileIdを受け付ける保護されたポータル経路で処理する。所属ツール、ユーザー状態・権限、サイト・ツールの公開状態を確認してからファイルを返す。
- 相対パスの解決後も専用保存領域内であることを検証し、利用者に任意のパスを指定させない。
- 差し替えは新ファイルの仮保存、正式保存、DB更新確定、旧ファイル削除の順に行う。DB更新に失敗した場合は旧ファイル・旧参照を維持し、新ファイルを清掃する。旧ファイル削除だけに失敗した場合は新参照を維持し、残存ファイルの清掃対象とする。
- 参考資料の削除はDB更新確定後に実ファイルを削除する。削除失敗時の残存ファイル清掃手順は詳細設計で定める。配布アプリの明示的な削除操作は提供しない。
- IISとアプリケーションの要求サイズ上限は、各機能のファイル上限に加えてフォーム送信の付加情報を受け付けられる値とする。機能ごとの容量制限は別途サーバー側で検証する。

### 一時ファイルの制約
- WebツールではExcel等の処理用一時アップロードを認める。入力ファイルは恒久保存せず、処理に必要な間だけメモリまたは一時領域で扱い、処理終了時に破棄・削除する。
- 一時ファイルはWeb公開・アプリケーション配置フォルダーの外へ保存する。
- ツールごとに保存領域を分離する。
- 利用者が指定したファイル名を物理ファイル名として直接使用しない。
- 一時ファイルIDまたはランダムなファイル名を使用する。
- 処理用一時アップロードの許可拡張子と最大ファイルサイズは、ツールごとにTOOL_INPUTポリシーへ登録し、Commonで取得・検証する。
- 問い合わせ添付ファイルはメール送信に必要な間だけ一時保存し、メールへ直接添付する。
- 一時保存領域に実行権限を付与しない。
- 正常・異常にかかわらず、処理終了時に一時ファイルを削除する。
- 問い合わせメールは一回だけ送信を試行し、失敗時の再送を目的として一時ファイルを保持しない。
- 処理結果および帳票データを恒久保存しない。
- 異常終了・削除失敗で残った一時ファイルや未参照の永続ファイルは、保守時に運用担当者が使用中・DB参照中でないことを確認して清掃する。アプリ内の自動修復・残存ファイル監視・起動時清掃は設けない。正常処理での一時ファイル破棄・旧ファイル削除は維持する。
- ファイル内容と物理パスをログへ記録しない。
- 問い合わせ添付の種類・容量・保存方針は[問い合わせ仕様](02_画面・機能設計.md#inquiries)と[問い合わせデータ](04_DB設計.md#inquiries)を参照する。
