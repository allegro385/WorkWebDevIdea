# 営業支援ポータル 開発サーバー導入手順

[資料一覧へ戻る](README.md) · [導入・運用方針](05_導入・運用.md)

本書は、**新しい開発専用Windowsサーバー**にPortalを初回導入し、必要なWebツールを追加する際の作業順です。対象サーバーやDBへ自動で設定を加えるスクリプトではありません。実値を決める箇所は作業票へ記入し、接続先を確認してから実行してください。既存DBの更新・既存IISサイトの上書きには流用せず、変更内容に対応する移行手順を別途作成します。サンプル見積ツールの専用SQLは任意の開発用データです。

## 1. 作業前に決める値と必要なソフト

| 項目 | 作業前の確認・記入欄 |
| --- | --- |
| Windows Server | 製品名・版・ビルド、x64、.NET 10のサポート対象、更新・再起動可否：＿＿＿＿ |
| Webサイト | DNS名、HTTPS証明書、443番の通信許可、既存IISサイトとの競合：＿＿＿＿ |
| データベース | 開発専用SQL Serverのホスト・インスタンス・DB名、接続方式、DB作成・スキーマ適用権限：＿＿＿＿ |
| SMTP | 開発用のホスト、ポート、TLS、認証要否、送信元、受信先：＿＿＿＿ |
| 配置先 | アプリ、共通設定、鍵、一時・永続ファイルのフォルダーと容量：＿＿＿＿ |
| 担当者 | IIS・証明書・DB・SMTP・バックアップの担当者：＿＿＿＿ |

必要なソフト・機能は次のとおりです。**サーバーでビルドしない構成なら、SDKとソース一式はビルド端末だけに置きます。**

| 場所 | 必要なもの | 用途 |
| --- | --- | --- |
| 開発サーバー | サポート対象のx64 Windows Server、Web Server（IIS）ロール、.NET 10 Hosting Bundle（ASP.NET Core Module V2を含む） | IISでASP.NET Core 10の発行物を動かす。IISを有効化してからHosting Bundleを導入し、要求される再起動を行う |
| ビルド端末 | `SalesSupport/global.json`に合う.NET SDK **10.0.401**、ソース取得手段 | `restore`・`build`・`test`・`publish`。IISで動かすだけならSDKは不要 |
| DB管理端末 | SQL Serverへ接続するSSMS、または`sqlcmd` | 開発専用DBの作成と版付きSQLの手動適用 |
| 接続先 | SQL Server、開発用SMTPサーバーまたは検証用受信環境 | DB処理、初回設定・再設定・通知メールの検証。SMTPを用意しない場合はメール送信検証は完了扱いにしない |

SQL Serverの製品・版、Windows Serverの版、証明書発行方法、SMTPの具体的な値はリポジトリで固定していません。導入先の管理者と確定してください。`.NET SDK`と`Hosting Bundle`は別製品です。導入後、ビルド端末の`dotnet --list-sdks`で10.0.401、サーバー側のIISでASP.NET Core Module V2を確認します。インストーラーは組織で承認された配布元から取得します。

## 2. 作業記録と配備前の確認

リポジトリの[プロジェクト操作履歴](../作業記録/プロジェクト操作履歴.md)へ、予定するソフト導入、IIS・権限・環境変数の変更、DB作成・SQL適用、ビルド・テスト・発行・起動を**実行前に記入**し、実行後に各結果を追記します。日時はJST、対象ホスト・DB名、作業ディレクトリ、コマンド、変更前後、切戻し方法、残存物を記録します。接続文字列、パスワード、トークンは記録しません。

サーバーが既に使われている場合は既存IISサイト・バインド・アプリケーションプール・DBの一覧を確認し、名前とポートの衝突を避けます。既存業務DBに`001_CreateTables.sql`を適用しないでください。DBとファイルのバックアップ先・復元担当を確認します。

## 3. ビルド、テスト、発行

リポジトリルートで次を実行します。`<発行先>`はビルド端末上の空の作業フォルダーに置き換えます。Portalだけを入れる場合、ツールの行は省きます。

```powershell
dotnet --list-sdks
dotnet restore SalesSupport/SalesSupport.Portal.slnx
dotnet build SalesSupport/SalesSupport.Portal.slnx --no-restore
dotnet test SalesSupport/SalesSupport.Portal.slnx --no-restore
dotnet publish SalesSupport/src/Portal/SalesSupport.Portal.Web/SalesSupport.Portal.Web.csproj -c Release -o <Portal発行先>
```

Webツールを入れる場合は、ツールごとの`.slnx`に対して同じ`restore`・`build`・`test`を行い、そのWebプロジェクトを別の空フォルダーへ`publish`します。例は`SalesSupport/SampleEstimate.slnx`と`SalesSupport/src/SampleEstimate/SalesSupport.SampleEstimate.Web/SalesSupport.SampleEstimate.Web.csproj`です。テンプレートそのものは業務用として配置しません。Commonを変更したリリースではPortalと影響を受ける全ツールを個別に再発行します。発行物、ソース版、実行結果を紐付けて保管します。

## 4. 開発専用DBの初期構築

DB管理者が**開発専用の空DB**を作り、接続先ホストとDB名を再確認します。接続文字列を設定するアカウントにはアプリの実行に必要な権限を与えます。DDLをアプリ起動時に自動適用しません。

初回は[SQL手順](../SalesSupport/sql/README.md)に従い、`SalesSupport/sql/001_CreateTables.sql`、`002_SeedMasterData.sql`の順で適用します。`sqlcmd`の例は同READMEにあります。`001`は空DB専用です。`900_SeedDummyData.sql`は任意で、事前に管理者と一般ユーザーが必要です。使う場合は同READMEのDB名確認手順に従います。サンプルツールを配置する場合のみ、[サンプル専用SQL手順](../SalesSupport/sql/sample/README.md)の環境標識・許可標識を設定し、`910_CreateSampleEstimate.sql`を適用します。本番DBへ開発用SQLを適用しません。

SQLの適用結果と対象DB名、初期マスタの有無を確認します。既存DBの差分更新が必要なら版付き移行SQLとバックアップ・切戻し手順を先に作成します。

## 5. サーバーフォルダーと設定

配置例です。既存ディレクトリに合わせて変更できますが、共通設定、鍵、保存領域は禁止パスワード一覧を含めてWeb公開領域・アプリ配置先の外に置きます。

```text
D:\SalesSupport\
├─ apps\portal\       Portalの発行物
├─ apps\SAMPLE-ESTIMATE\  ツールの発行物（配置する場合）
├─ config\            salessupport.common.json、禁止パスワード一覧
├─ keys\              Data Protectionキー
└─ storage\temp\、storage\files\
```

アプリ実行IDには`apps`への読取り・実行権、`config`への読取り権、`keys`への鍵生成・読取りに必要な権限、`storage`の対象領域への必要な書込み権を与えます。運用管理者以外から共通設定と鍵を見られないようACLを確認します。アプリケーションプールごとに必要な領域だけ許可します。鍵は同一Windowsサーバー上でDPAPIにより保護されます。鍵フォルダーを消すと既存Cookie等を復号できなくなるため、配備時に消さずバックアップ対象とします。

[開発用雛形](../SalesSupport/config/salessupport.common.Development.sample.json)を`D:\SalesSupport\config\salessupport.common.json`等へコピーし、[設定一覧](../SalesSupport/config/README.md)に従って実値を記入します。最低限、開発専用DBの接続文字列、`Portal:EnvironmentCode=DEVELOPMENT`、実際のHTTPS公開URL（末尾`/`付き）、鍵・保存先、開発用SMTP、`DevelopmentRecipient`を確認します。雛形の`localhost`・`example.invalid`はサーバー運用値ではありません。実値入りファイルをリポジトリや作業記録へ含めません。

各アプリの環境変数`SalesSupport__CommonConfigPath`は、**その発行物の実行フォルダーからの相対パス**です。上の配置ならPortalとツールの両方で`../../config/salessupport.common.json`を指定します。設定ファイル内の`KeyDirectory`・`Storage:*Root`は**設定ファイルがあるフォルダーからの相対パス**です。Portalには`SalesSupport__Password__ForbiddenListPath=../../config/<禁止リスト名>`も設定し、実在するUTF-8の1行1件ファイルを参照させます。禁止リストの内容・更新担当は導入先で決定します。絶対パスは受け付けません。

各Webツールにはさらに`SalesSupport__Application__ToolId`と`SalesSupport__Application__Name`を設定します。前者はDBのToolIdと一致させます。後者はログに使う表示名です。共通設定を変更したらPortalと全Webツールを再起動します。

## 6. IISへ配置

1. IISロールを有効化し、その後に.NET 10 Hosting Bundleを導入します。インストーラーの要求に従ってIISまたはサーバーを再起動し、ASP.NET Core Module V2が使えることを確認します。
2. 開発用DNS名のHTTPS証明書をサーバーへ登録し、IISサイトの443番バインドに割り当てます。利用端末から証明書と名前が一致することを確認します。
3. Portal用の専用アプリケーションプールを作り、.NET CLRバージョンを「マネージドコードなし」にします。Portalの発行物を`apps\portal`へ配置し、サイトのルートアプリケーションに割り当てます。発行物に含まれる`web.config`を保持し、その`<environmentVariables>`に`ASPNETCORE_ENVIRONMENT=Development`、`SalesSupport__CommonConfigPath`、`SalesSupport__Password__ForbiddenListPath`を設定します。`web.config`や設定画面へ秘密値を直接記載しません。
4. Webツールごとに別のアプリケーションプールを作り、同じIISサイトの`/tools/<ToolId>/app`へアプリケーションとして登録します。物理フォルダーは各ツールの発行物に分けます。各ツールの`web.config`に`ASPNETCORE_ENVIRONMENT=Development`、共通設定パス、ToolId、表示名を設定します。サイトの単なる仮想ディレクトリとしては登録しません。
5. 各プールの実行IDに第5節のACLを適用します。IISのサイト、アプリケーション、プールが起動することとWindowsイベントログの起動エラーを確認します。リバースプロキシを使う場合は、信頼するプロキシのIPだけを共通設定の`KnownProxies`へ設定し、転送ヘッダー・HTTPS認識を検証します。

IIS登録だけではPortalのツール一覧へ追加されません。WebツールのToolId、`WEB`種別、起動URL、所有管理者、公開状態、必要なアップロードポリシーを[導入・運用方針](05_導入・運用.md#master-data)に従ってDBへ登録します。新規ツールは`HIDDEN`で登録し、確認後に必要な公開状態へ変更します。サンプルツールは第4節の専用SQL手順を使います。

## 7. 最初の管理者と動作確認

Portalを停止してから、**Portalの発行物と同じ構成・同じ開発DBを使う状態**で[初期管理者コマンド](../SalesSupport/src/Portal/SalesSupport.Portal.Web/README.md#最初の管理者を作成する)を対話実行します。ソースとSDKのある端末で実行する場合は、通常のPortal設定・共通設定への相対パスをその端末の実行フォルダーに合わせ、接続先DB名を確認してから次を実行します。

```powershell
dotnet run --project SalesSupport/src/Portal/SalesSupport.Portal.Web -- bootstrap-admin
```

サーバーの発行物から実行する場合は、Portalを停止し、同じ環境変数・設定を適用した対話シェルから`dotnet SalesSupport.Portal.Web.dll bootstrap-admin`を実行します。設定パスはDLLのあるフォルダー基準です。実行後はPortalを起動します。パスワードをコマンド引数やログへ書かず、対話入力します。IdentityユーザーをSQLで直接作成しません。

一般ユーザーのログイン試験が必要なら、Portalの[開発専用`add-test-user`手順](../SalesSupport/src/Portal/SalesSupport.Portal.Web/README.md#ローカル試験用の一般ユーザーを追加する)を使います。ASP.NET Core環境`Development`と共通設定の`DEVELOPMENT`を確認します。通常のユーザー登録は管理画面から行います。

確認結果を操作履歴に残します。

- HTTPSでPortalのログイン画面を開ける。ブラウザーに証明書警告が出ない。
- 初期管理者でログインでき、開発環境の赤帯が表示される。SQL Serverへの接続・管理画面のデータ表示を確認する。
- 再設定・初回設定メールが**開発用受信先だけ**へ届く。SMTPを用意していない場合は未検証として記録する。
- ツールを配置した場合は、Portalからの起動とツールURLへの直接アクセスで共有Cookie、公開状態、権限制御を確認する。未認証・無効ユーザーや`HIDDEN`の入場拒否も確認する。
- 添付を使う場合はアップロード条件、保存・取得・一時ファイル削除を確認する。アプリログとIIS・Windowsイベントログを確認する。

ビルド・単体テストの成功は、IIS・実DB・SMTP・共有Cookieの結合確認の成功を意味しません。確認できなかった項目は未検証として記録します。

## 8. 失敗時の停止・切戻し

起動やログインに失敗したら公開状態を変更せず、IISの対象アプリケーションプールを停止し、イベントログ・設定ファイルの存在、相対パス、ACL、DB接続、環境区分を確認します。秘密値をログや画面へ出さないでください。

アプリの更新を戻す場合は、対象プールを停止し、保管した直前の**アプリ全体の発行物**と対応する設定を復元して再起動します。Common DLLだけを差し替えません。DBを変更した場合の復元可否は事前バックアップと移行SQLの内容で判断し、既存DBへ初期構築SQLを再実行しません。鍵フォルダーは保持します。IIS・DB・設定の変更結果と切戻し結果を操作履歴へ追記します。
