# 営業支援ポータル 開発サーバー導入手順

[資料一覧へ戻る](README.md) · [導入・運用方針](05_導入・運用.md)

本書は、**新しい開発専用Windowsサーバー**にPortalを初回導入し、必要なWebツールを追加する際の作業順です。対象サーバーやDBへ自動で設定を加えるスクリプトではありません。実値を決める箇所は作業票へ記入し、接続先を確認してから実行してください。開発中は後方互換・データ移行を行いません。DB構造を変更した場合は新しい開発DBを作成します。既存IISサイトの更新は[手動リリース](05_導入・運用.md#release)に従います。サンプル見積ツールの専用SQLは任意の開発用データです。

## 1. 作業前に決める値と必要なソフト

| 項目 | 作業前の確認・記入欄 |
| --- | --- |
| Windows Server | 製品名・版・ビルド、x64、.NET 10のサポート対象、更新・再起動可否：＿＿＿＿ |
| Webサイト | DNS名、HTTPS証明書、443番の通信許可（申請・反映時期）、既存IISサイトとの競合：＿＿＿＿ |
| データベース | 開発専用SQL Serverのホスト・インスタンス・DB名、接続方式、DB作成・スキーマ適用権限：＿＿＿＿ |
| SMTP | 開発用のホスト、ポート、TLS、認証要否、送信元、受信先：＿＿＿＿ |
| 配置先 | アプリ、共通設定、鍵、一時・永続ファイルのフォルダーと容量：＿＿＿＿ |
| 担当者 | IIS・証明書・DB・SMTP・バックアップの担当者：＿＿＿＿ |

必要なソフト・機能は次のとおりです。**サーバーでビルドしない構成なら、SDKとソース一式はビルド端末だけに置きます。**

| 場所 | 必要なもの | 用途 |
| --- | --- | --- |
| 開発サーバー | サポート対象のx64 Windows Server、Web Server（IIS）ロール、.NET 10 Hosting Bundle（ASP.NET Core Module V2を含む） | IISでASP.NET Core 10の発行物を動かす。IISを有効化してからHosting Bundleを導入し、要求される再起動を行う |
| ビルド端末 | `SalesSupport/global.json`に合う.NET SDK **10.0.401**、ソース取得手段 | `restore`・`build`・`test`・`publish`。IISで動かすだけならSDKは不要 |
| DB管理端末 | SQL Serverへ接続するSSMS、または`sqlcmd` | 開発専用DBの作成と初期構築SQLの手動適用 |
| 接続先 | SQL Server、開発用SMTPサーバーまたは検証用受信環境 | DB処理、お知らせ・問い合わせメールの検証。SMTPを用意しない場合はメール送信検証は完了扱いにしない |

SQL Serverの製品・版、Windows Serverの版、証明書発行方法、SMTPの具体的な値はリポジトリで固定していません。導入先の管理者と確定してください。`.NET SDK`と`Hosting Bundle`は別製品です。導入後、ビルド端末の`dotnet --list-sdks`で10.0.401、サーバー側のIISでASP.NET Core Module V2を確認します。インストーラーは組織で承認された配布元から取得します。

## 2. 作業記録と配備前の確認

リポジトリの[プロジェクト操作履歴](../作業記録/プロジェクト操作履歴.md)へ、予定するソフト導入、IIS・権限・環境変数の変更、DB作成・SQL適用、ビルド・テスト・発行・起動を**実行前に記入**し、実行後に各結果を追記します。日時はJST、対象ホスト・DB名、作業ディレクトリ、コマンド、変更前後、切戻し方法、残存物を記録します。接続文字列、パスワード、トークンは記録しません。

サーバーが既に使われている場合は既存IISサイト・バインド・アプリケーションプール・DBの一覧を確認し、名前とポートの衝突を避けます。既存業務DBに`001_CreateTables.sql`を適用しないでください。DBとファイルのバックアップ先・復元担当を確認します。

## 3. ビルド、テスト、発行

リポジトリルートで次を実行します。`<発行先>`はビルド端末上の空の作業フォルダーに置き換えます。Portalだけを入れる場合、ツールの行は省きます。

```powershell
dotnet --list-sdks
dotnet restore SalesSupport/SalesSupport.Portal.slnx
dotnet build SalesSupport/SalesSupport.Portal.slnx --no-restore
dotnet test SalesSupport/SalesSupport.Portal.slnx --no-restore
dotnet publish SalesSupport/src/Portal/SalesSupport.Portal.Web/SalesSupport.Portal.Web.csproj -c Release -o <Portal発行先>
```

Webツールを入れる場合は、ツールごとの`.slnx`に対して同じ`restore`・`build`・`test`を行い、そのWebプロジェクトを別の空フォルダーへ`publish`します。例は`SalesSupport/SampleEstimate.slnx`と`SalesSupport/src/SampleEstimate/SalesSupport.SampleEstimate.Web/SalesSupport.SampleEstimate.Web.csproj`です。テンプレートそのものは業務用として配置しません。Commonを変更したリリースではPortalと影響を受ける全ツールを個別に再発行します。発行物、ソース版、実行結果を紐付けて保管します。

## 4. 開発専用DBの初期構築

DB管理者が**開発専用の空DB**を作り、接続先ホストとDB名を再確認します。接続文字列を設定するアカウントにはアプリの実行に必要な権限を与えます。DDLをアプリ起動時に自動適用しません。

初回は[SQL手順](../SalesSupport/sql/README.md)に従い、`SalesSupport/sql/001_CreateTables.sql`、`002_SeedMasterData.sql`の順で適用します。`sqlcmd`の例は同READMEにあります。`001`は空DB専用です。`900_SeedDummyData.sql`は任意で、事前に管理者と一般ユーザーが必要です。使う場合は同READMEのDB名確認手順に従います。サンプルツールを配置する場合のみ、[サンプル専用SQL手順](../SalesSupport/sql/sample/README.md)の環境標識・許可標識を設定し、`910_CreateSampleEstimate.sql`を適用します。本番DBへ開発用SQLを適用しません。

SQLの適用結果と対象DB名、初期マスタの有無を確認します。DB構造変更時も最新の初期構築SQLを新しい空の開発DBへ適用し、試験データを新規作成します。旧DBからの引継ぎや差分移行SQLの作成は行いません。接続先設定を新しい開発DBへ合わせ、対象アプリを同じ仕様の版で配備します。

## 5. サーバーフォルダーと設定

配置例です。既存ディレクトリに合わせて変更できますが、共通設定、鍵、保存領域はWeb公開領域・アプリ配置先の外に置きます。

```text
D:\SalesSupport\
├─ apps\portal\       Portalの発行物
├─ apps\SAMPLE-ESTIMATE\  ツールの発行物（配置する場合）
├─ config\            salessupport.common.json
├─ keys\              Data Protectionキー
└─ storage\temp\、storage\files\
```

フォルダーの作成と権限の付与には[`scripts/Initialize-SalesSupportFolders.ps1`](../SalesSupport/scripts/README.md#配置先のフォルダーを準備する)を使えます。アプリ実行IDには`apps`への読取り・実行権、`config`への読取り権、`keys`への鍵生成・読取りに必要な権限、`storage`の対象領域への必要な書込み権を与えます。運用管理者以外から共通設定と鍵を見られないようACLを確認します。アプリケーションプールごとに必要な領域だけ許可します。鍵は同一Windowsサーバー上でDPAPIにより保護されます。鍵フォルダーを消すと既存Cookie等を復号できなくなるため、配備時に消さずバックアップ対象とします。

[開発用雛形](../SalesSupport/config/salessupport.common.Development.example.json)を`D:\SalesSupport\config\salessupport.common.json`等へコピーし、[設定一覧](../SalesSupport/config/README.md)に従って実値を記入します。最低限、開発専用DBの接続文字列、`SalesSupport:EnvironmentCode=DEVELOPMENT`、実際の公開URL（末尾`/`付き）、鍵・保存先、開発用SMTP、`DevelopmentRecipient`を確認します。HTTPSのバインドと443番の通信許可がまだない場合は、`SalesSupport:Site:TransportMode`を`Http`にし、公開URLをhttpで記入します（[HTTP運用](05_導入・運用.md#transport-operation)）。雛形の`localhost`・`example.invalid`はサーバー運用値ではありません。実値入りファイルをリポジトリや作業記録へ含めません。

各アプリは**その発行物のフォルダー（コンテンツルート）からの相対パス**`../../config/salessupport.common.json`を既定として共通設定ファイルを読みます。上の配置ではPortalとツールのどちらも`SalesSupport__CommonConfigPath`の設定は不要です。配置が異なる場合だけ、同じ基準の相対パスを環境変数で指定します。設定ファイル内の`KeyDirectory`・`Storage:*Root`は**設定ファイルがあるフォルダーからの相対パス**です。絶対パスは受け付けません。

各Webツールにはさらに`SalesSupport__Application__ToolId`と`SalesSupport__Application__Name`を設定します。前者はDBのToolIdと一致させます。後者はログに使う表示名です。共通設定を変更したらPortalと全Webツールを再起動します。

## 6. IISへ配置

1. IISロールを有効化し、その後に.NET 10 Hosting Bundleを導入します。インストーラーの要求に従ってIISまたはサーバーを再起動し、ASP.NET Core Module V2が使えることを確認します。
2. 開発用DNS名のHTTPS証明書をサーバーへ登録し、IISサイトの443番バインドに割り当てます。利用端末から証明書と名前が一致することを確認します。証明書または443番の通信許可がまだ用意できない場合は、80番のバインドだけで公開し、共通設定の`SalesSupport:Site:TransportMode`を`Http`にします。許可が整った時点で443番のバインドを追加し、`Https`へ戻します。
3. Portal用の専用アプリケーションプールを作り、.NET CLRバージョンを「マネージドコードなし」にします。Portalの発行物を`apps\portal`へ配置し、サイトのルートアプリケーションに割り当てます。発行物に含まれる`web.config`を保持します。標準配置以外では、プロジェクトの`web.config`で`SalesSupport__CommonConfigPath`を設定してから発行します。`web.config`や設定画面へ秘密値を直接記載しません。
4. Webツールごとに別のアプリケーションプールを作り、同じIISサイトの`/tools/<ToolId>/app`へアプリケーションとして登録します。物理フォルダーは各ツールの発行物に分けます。各ツールの`web.config`にはプロジェクトで設定したToolIdと表示名が出力されます。再発行で消えないよう、配置先のファイルを直接編集しません。`ASPNETCORE_ENVIRONMENT`と`SalesSupport__Tool__ExecutionMode`は設定しません（単独開発はHTTPS専用で自端末からの要求しか許可しないため、サーバーでは使いません）。サイトの単なる仮想ディレクトリとしては登録しません。
5. 各プールの実行IDに第5節のACLを適用します。IISのサイト、アプリケーション、プールが起動することとWindowsイベントログの起動エラーを確認します。リバースプロキシを使う場合は、信頼するプロキシのIPだけを共通設定の`KnownProxies`へ設定し、転送ヘッダー・HTTPS認識を検証します。

IIS登録だけではPortalのツール一覧へ追加されません。WebツールのToolId、`WEB`種別、起動先のパス（`/tools/<ToolId>/app`）、所有管理者、公開状態、必要なアップロードポリシーを[導入・運用方針](05_導入・運用.md#master-data)に従い、[ツール登録SQLのひな形](../SalesSupport/sql/README.md#新しいツールを登録する)でDBへ登録します。新規ツールは`HIDDEN`で登録し、確認後に必要な公開状態へ変更します。サンプルツールは第4節の専用SQL手順を使います。

## 7. ユーザーの登録と動作確認

管理者と一般ユーザーは、[管理コマンド`import-users`](../SalesSupport/src/Portal/SalesSupport.Portal.Web/README.md#ユーザーを一括登録する)でTSVから登録します。ソースとSDKのある端末で実行する場合は、通常のPortal設定・共通設定への相対パスをその端末の実行フォルダーに合わせます。

```powershell
dotnet run --project SalesSupport/src/Portal/SalesSupport.Portal.Web -- import-users .local/users.tsv --dry-run
```

サーバーの発行物から実行する場合は、同じ設定を適用した対話シェルで`dotnet SalesSupport.Portal.Web.dll import-users <TSVファイル>`を実行します。共通設定ファイルの既定パスはコンテンツルート基準で、`dotnet`コマンドでは現在のフォルダーがコンテンツルートになるため、`apps\portal`へ移動してから実行します。表示された接続先のDB名と環境区分を確認し、`--dry-run`の結果を確認してから登録します。平文パスワードを含むTSVは登録の確認後に削除します。IdentityユーザーをSQLで直接作成しません。

確認結果を操作履歴に残します。

- HTTPSでPortalのログイン画面を開ける。ブラウザーに証明書警告が出ない。`TransportMode`が`Http`の期間はHTTPで開けることを確認し、HTTPSは未検証として記録する。
- 試験用の管理者でID・パスワード確認後、DevelopmentRecipientへ届くメールOTPを入力してログインでき、開発環境の赤帯が表示される。SQL Serverへの接続・管理画面のデータ表示を確認する。OTPの任意30日記憶、再送・期限・ロックと、ツール直接URLからの認証・復帰も確認する。SMTPを無効にしたままログイン確認を行わない。
- お知らせ・問い合わせメールが**開発用受信先だけ**へ届く。SMTPを用意していない場合は未検証として記録する。
- ツールを配置した場合は、Portalからの起動とツールURLへの直接アクセスで共有Cookie、公開状態、権限制御を確認する。未認証・無効ユーザーや`HIDDEN`の入場拒否も確認する。
- 添付を使う場合はアップロード条件、保存・取得・一時ファイル削除を確認する。アプリログとIIS・Windowsイベントログを確認する。

ビルド・単体テストの成功は、IIS・実DB・SMTP・共有Cookieの結合確認の成功を意味しません。確認できなかった項目は未検証として記録します。

## 8. 失敗時の停止・切戻し

配置時によくある原因は次のとおりです。

| 起きたこと | 原因 | 対処 |
| --- | --- | --- |
| 単独モードのままクライアントから開けない、httpsへ転送される | 単独開発はHTTPS専用で、他の端末からの要求も拒否する | クライアントからの確認は連携モードで行う |
| 起動時に`Storage:PermanentRoot`のエラーで止まる | 保存領域のフォルダーがない、または権限がない | エラーの理由を確認し、第5節のスクリプトで作成と権限の付与を行う |
| DB接続で「信頼されていない機関によって証明書チェーンが発行されました」 | SQL Serverが自己署名の証明書を使っている | 開発環境の接続文字列へ`TrustServerCertificate=True`を付ける |
| 認証モードや通信方式の変更が効かない | キーを`SalesSupport`の直下に書いている | `SalesSupport:Site`の下へ書く |
| 起動時に`Portal:BaseUrl`のエラーで止まる | `TransportMode`とスキームが異なる、または末尾の`/`がない | スキームをそろえ、末尾を`/`にする |
| 共通設定ファイルを変えてもツールへ反映されない | 設定は起動時に読む | Portalと全ツールのアプリケーションプールをリサイクルする |

起動やログインに失敗したら公開状態を変更せず、IISの対象アプリケーションプールを停止し、イベントログ・設定ファイルの存在、相対パス、ACL、DB接続、環境区分を確認します。秘密値をログや画面へ出さないでください。

アプリの更新を戻す場合は、対象プールを停止し、保管した直前の**アプリ全体の発行物**と対応する設定を復元します。Common DLLだけを差し替えません。DB構造が異なる場合は、戻す版の初期構築SQLで別の空の開発DBを作成し、試験データを新規作成して接続先を合わせます。データの逆移行や既存DBへの初期構築SQLの再実行は行いません。現行のセキュリティ要件を満たすことを確認して再起動します。鍵フォルダーは保持します。IIS・DB・設定の変更結果と切戻し結果を操作履歴へ追記します。
